## 結果の概観

主結果は定理1（B2）です。おおまかには、次の4つを仮定します。

- z3が充足不能な問いにだけ `unsat` と答えること
- 証明器が、z3の各答えを、それを尋ねた検査の答えとして受け取ること
- ビルドが実行の範囲で `T_β(M, σ)` を返すこと（主張I1）
- 符号化が後述の意味で忠実であること

このとき `proved: R` は、証明の範囲 `Sc(M, β)` のどの範囲 `β'` でも、`T_{β'}(M, σ)` の到達可能なすべての状態で `R` が成り立つことを意味します。

`Sc(M, β)` は、モデルがエラーなしにビルドできる範囲すべてです。エンティティごとのスロット数はどれでもよく、Intの上限 `m'` は「モデルが書く最大のIntリテラル」から「ビルドできる最大値」まで動きます。最大値は255で、nullableなInt列があれば254です（`DomainTooLarge`）。状態が詰め込める幅を超えるなら、さらに小さくなります（`StateTooWide`）。`σ` は実行のスコープ（D24）で、モデル全体とは限りません。証明を主張する行は、すべてこの範囲を表示します。

定理を支える部品と、その支えの強さは次のとおりです。

| 部品 | 支え |
|---|---|
| `unsat` についてのz3の健全性 | 仮定 |
| 印字したテキストが元の `Expr` を意味する（H2） | 型付きの項ビルダーとその単体テスト。それを超える部分は仮定 |
| 各答えを尋ねた検査のものとして読む（H4） | z3の出力の約束事として仮定。読み手はそれ以外の行で閉じて失敗する。読み手を動かすテストはない |
| 残した集合が符号化に対して帰納的（命題4） | コードからの証明 |
| ステップの刈り込みが健全（補題F5） | コードからの証明 |
| 符号化が `T_{β'}` を過大近似する（命題2） | コードを読んだ証明の概略。比較は毎回の証明で実行時検査。差分テスト、参照インタプリタ、コーパスの例 |
| 定義が範囲について一様（補題U₀） | D1〜D12 を読めば直ちに従う |
| ビルドが `T_β(M, σ)` を返す（I1） | 全体としては論証していない。コーパスのヘッダと、言語の部分集合での参照インタプリタ |
| ビルドが定義と同じ場所でだけ範囲を読む（補題U） | 証明の概略。読んだ箇所の一覧はCIが照合する。毎回の証明が、表示範囲を決めたビルドを実行の系と比べる |
| 前提が充足可能 | F1、F2、`I ≠ ∅` から従う。`unsat` のときだけカナリアで実行時に検査 |
| Houdiniが最大の帰納的な部分集合を残す | 一般には偽（命題5）。健全性は残した集合にしか依存しない |

## 記法

ここで新しく入る記号だけを挙げます。

- `β = (n, m)` は実行の範囲（D1）です。証明器は `TransitionSystem::build(M, β, σ)` が返す系 `T` を受け取ります。`T` が `T_β(M, σ)` であるのは、I1が `β` で成り立つときです。`T_{β'}` は常にD13が `β'` で定義する系を指し、ビルドの出力ではありません。
- `Enc` は `T` をSMT-LIB 2で書いた符号化（`core/prove/encode.rs::Enc`）です。値域を宣言する `Decl`、初期状態の `Init`、アクション `a` ごとのステップ関係 `Step_a`、状態式を枠 `F ∈ {Pre, Post}` で読む `⟦φ⟧^F`、どこかの行が `φ` を破るという `Viol(φ, F)` からなります。
- **候補**は、証明器が残すかもしれない式 `ψ` です。`T` の規則（D16）、組み込みの補題、採掘した補題、CTI（帰納法の反例）から作った節のどれかです。
- `reads(ψ)` は `ψ` が読む変数、`writes(a)` は `a` が書く変数の集合です。
- 候補の集合 `K` が **`Enc` に対して帰納的** であるとは、次の2つが成り立つことです。初期条件として、各 `ψ ∈ K` で `Decl ∧ Init ∧ Viol(ψ, Pre)` が充足不能です。帰結条件として、各 `a` と各 `ψ ∈ K` で `Decl ∧ Step_a ∧ ⋀_{χ∈K} ⟦χ⟧^Pre ∧ Viol(ψ, Post)` が充足不能です。
- `𝔄(s)` は、ある `T_{β'}` の状態 `s` を `Enc` の記号の解釈として読んだ構造です（定義1）。

## 符号化

### 項ビルダーと答えの読み手

`core/prove/smt.rs` はSMT-LIBの項をデータとして組み立てます。`Expr` は自分のソートを持ち、各コンストラクタは受け取るソートを検査し、括弧は1つのプリンタがすべて書きます。ソートを誤る項は、デバッグビルドではpanicします。リリースビルドではz3が拒否して `SolverError` になり、実行は判定なしに `z3 failed` で失敗します。どちらでも `proved` には化けません。ソートは正しいが意味が `Expr` と違う印字は、この仕組みでは捕まりません。これが仮定H2です。

z3はソルバーごとに1つの `z3 -in -smt2` プロセスとして証明の間ずっと生きています。`Z3::exec` はコマンドの束の後にマーカー（`MARK`）をechoさせ、マーカーの行までを読みます。`Solver::check_sat` は `rlimit` の設定、`(check-sat)`、`rlimit` の解除を1つの束で送り、最初の行を答えとして読みます。答えは `sat`、`unsat`、`unknown`/`timeout` のどれかで、それ以外の行、`(error` で始まる行、標準出力の終了は `SolverError` です。

H4（各答えを尋ねた検査のものとして読む）は、z3が束のコマンドを順に処理してマーカーを1回だけ出し、`assert` などのコマンドには何も出さないときに成り立ちます。`SolverError` は `run_proof` まで伝わって実行を失敗させるので、エラー後のセッションは使われず、答えが1束ずれることもありません。コードから見えないのは、形は正しいが別の検査に属する答えだけです。`exec` と `check_sat` を直接動かす単体テストはなく、すべての証明テストがz3 5.1.0に対してこれらを使っています。

### 行数を限らない表し方

各エンティティ `E` は解釈されないソート `E<i>` になり、ソートの要素が行です。要素の個数を縛るものはなく、`Enc` のモデルは何個の行を持ってもかまいません（無限個でもよい）。これが「行が何個あっても」を表す仕組みです。各ソートには、未リンクの任意キーの値 `nil<i>`（行ではなく、存在は `absent`）と、任意でないキーが既定値のときに指すスロット0の `zero<i>` があります。

行の変数 `v` は単項関数 `v<k> : E<i> → Int`（値域の添字）になり、キーなら `E<i> → E<j>` です。後状態は `v<k>_n` を読みます。`now` は `Int` 定数です。印（`Run`、`Raised`）と駆動される命題も、列と同じく行の関数です。

### 値域、初期状態、ステップ

`Decl` は前状態のすべての行について値域を主張します。有限の値域の変数は `0 … size-1` に入り、そのサイズは `β` に依存しません。Int型の変数（Int、Money、Decimal、Date、DateTime。nullableも含む）は `≥ 0` で、**上限がありません**。任意でないキーは `nil` にならず、`now ≥ 0` です。後状態の関数は前状態の項、リテラル、値域に縛った新しい定数から定義するので、構成上、値域に収まります。

`Init` はD4の開始値をすべての変数と行に主張し、`now = 0` とします。符号化が書けない既定値（0以外の固定スロットを指すキー）があると `Init` は `Unsupported` になり、すべての候補が `Unknown` で落ちます。

`Step_a` は、ネイティブ検査器の `each_successor` と同じ順で組み立てます。

1. **パラメータ**: `nil` 以外の新しい定数です。`New` は行が存在しないことだけを主張します。`T` は存在しない最小のスロットを取りますが（D7）、符号化は存在しない行ならどれでも取ります。
2. **効果**: 作成、代入、遷移先が1つの遷移を、効果の順に適用します。
3. **削除**: 他の効果の後です。列は既定値に戻り、キーと印は残ります（D8、D10）。
4. **分岐**: 削除の後です。遷移先が複数ある遷移とすべての `Choose` は、新しい定数になり、その値は許す値に限ります（`Enc::one_of`）。削除された行では飛ばします。
5. **ガード**: 前状態で主張します。ただし `Tick` の `now < m` ガードは落とします。

効果が書かない変数は前状態の関数のままなので、後状態が前状態と違うのは `writes(a)` の変数だけです。これが補題F5の中身です。

### 述語と比較の照合

`Enc::pred` は `Pred` を節ごとにたどり、`Forall`/`Exists` は存在する行を量化します。`Count{E, φ, op, k}` は `at_least(k)`、つまり「`φ` を満たす互いに異なる `k` 個の存在する行」から組み立てます。どちらの極性でも厳密なので、必要な `at_least(j)` がすべて `j ≤ 8`（`COUNT_WITNESSES`）なら6つの比較はどれも厳密です。それを超えると `Unsupported` で、`≥ 8` と `< 8` は書けますが `> 8`、`≤ 8`、`== 8`、`!= 8` は書けません。

`Enc::compare` はネイティブの `expr.rs::compare`（D5）を場合ごとに写した2つ目の実装です（対応表は原文の [Predicates](https://github.com/manji-0/rdra-ish-dsl/blob/169cdf3fb49bbcaf0c7d452c32a57da18720fdd0/docs/theory/z3.md#predicates)）。規則を証明するか補題を残すすべての証明は、この2つを互いに照合します。これを翻訳検証（translation validation、`compare_tv.rs::compare_faults`）と呼びます。比較の形（演算子と両辺の種類）ごとに、`Enc::compare` が書く項を、実行の範囲での両辺のすべての値（nullを含み、各辺最大257個）について地の評価器（ground evaluator、`smt/eval.rs::eval`）で評価し、`expr.rs::compare` の値と一致することを求めます。食い違いは故障です。証明のすべての規則が `unproved` になり、結果は `tool_error` です。

### 畳み込み、拡幅、Unsupported

述語やステップの意味を変える仕組みが3つあり、影響が違います。

**畳み込み（folding、ビルダー）**: `lists_whole_domain` は、Enum、Bool（とそのnullable形）、null-or-present、存在の変数で、すべての値を列挙した `in` を `true` に、`not in` を `false` に置き換えます。これらの値域は `β` に依存しないので、置き換えはどの `β'` でも厳密です。Int、nullableなInt、キーの値域は値の個数が `β` で決まるので、決して畳み込みません（B3）。

**拡幅（widening、符号化）**: 次の3つは、`T_β` より多くの振る舞いを持つように符号化します。

- `New` パラメータは存在しない行をどれでも取る
- `Tick` にガードがなく、Int型の変数と `now` に上限がない
- Int型の変数の「すべての数」の選択を、`c ≥ from`（任意の数）か、`from` 未満で列挙された値のどれか、として符号化する

3つ目のために、ビルダーは「すべての数」の選択を、`β` に依存しない形 `Effect::Choose { numbers: Some(Numbers { from, .. }) }` で記録します。展開した `values` も持ち、探索器、TLC、生成コードはそちらを読みます。`Enc::one_of` は `numbers` と、`from` 未満の列挙値（どの範囲でも同じ）だけを読み、`c ≥ from ∨ ⋁ { c = t : t は列挙値、値 < from }` と書きます。`numbers` のない `Choose` は `⋁ { c = t }` で、どの範囲でも同じ値しか持ちません。

`numbers` が入るのは、nullableなInt型列への `sets(.., col == present)`（`from = 1`）とコピー（`from = 0`）です。`.when` 付きの `sets(.., col == null)` が同じ列の `.when` 付き `present` と1つの `Choose` にまとまると、`from = 1` の横にnull（添字0）が列挙されます。`present` の書き込みに `.when(C)` が付くと、`arm_guards` は数の選択を1本の腕 `next.n != null ∧ C` として書くので、ガードも `β` の値を名指ししません。

**Unsupported**: 符号化が書けない構成は、現れる場所で扱いが決まります。

- ガードの中： そのガードを落とします（`note: not encoded …`）。連言肢を落とすと、ステップは増えるだけです
- 書き込みの中： 書く値を、値域だけに縛った新しい定数にします（`Enc::havoc`）。本当の値も含むので、ステップは増えるだけです
- 候補の中： 規則は `out of scope` になって試されず、補題は黙って捨てます

規則を近似することは決してありません。規則に `Unsupported` があれば `Verdict::OutOfScope` で、弱めた式にはしません（B7）。

### 範囲についての一様性

符号化が読むのは、範囲 `β` でのビルドの出力 `T` だけです。一方、定理1は他の範囲 `β'` の系 `T_{β'}(M, σ)` についての主張です。そのため、`T` が `T_β(M, σ)` であること（`β` でのI1）と、`T_{β'}` と `T_β` の違いが符号化の覆う範囲に収まることの2つが要ります。

**補題U₀（定義の一様性）**: Intリテラルがすべて `m'` 以下なら、`T_{β'}(M, σ)` と `T_β(M, σ)` は同じエンティティ、変数、アクション、規則を持ちます。例外はD1〜D12が範囲を読む箇所だけです。数値列とキーの値域、D4のIdentity開始とD7のスロット、D8のnullable数値列への `present` の選択、D12の `Tick` のガード `now < m'` です。

**補題U（ビルドの一様性）**: `β'` でビルドがエラーを出さず、Intリテラルがすべて `m'` 以下なら、返る系は `T` と同じです。違ってよいのは次の3項目だけです。

1. Intの値域は `m'+1`（nullableなら `m'+2`）個、キーの値域は `n'_P`（`+1`）個の値を持つ
2. Int型の値域の全値で埋めた `Choose` は `m'` での値を列挙する
3. `Tick` のガードは `now` を `m'` と比べる

`Enc` はこの3項目を覆います。Int型の値域を `≥ 0`、キーを任意サイズのソートとして書き、「すべての数」の選択を `numbers` から `c ≥ from` で書き、`Tick` のガードを落とすからです。補題Uの証明の概略は、`core/build` で `int_max` とスロット数を読む箇所をすべて読むことです（原文の [Uniformity in the bound](https://github.com/manji-0/rdra-ish-dsl/blob/169cdf3fb49bbcaf0c7d452c32a57da18720fdd0/docs/theory/z3.md#uniformity-in-the-bound)）。

この概略を支える検査が2つあり、それぞれ覆わないものがあります。

- **読んだ箇所の一覧**: CIの `check` ジョブは `scripts/check-int-bound-sites.py` で、コード中の `int_max`、`Domain::of_number`、`Domain::size` の箇所を原文の一覧と照合します。箇所が増減すると失敗するので、概略を読み直すきっかけになります。ただし保つのは一覧であって補題ではありません。別名のヘルパー経由の読み取り、項目内の2度目の読み取り、`arm_guards` のような派生した読み取り、スロット数は見えません。
- **毎回の証明での比較**: `int_range` は表示範囲を候補の範囲でビルドして見つけます。エラーのないビルドはそれぞれ（表示範囲の両端を含む）、`prove/uniform.rs::same_up_to_bound` で実行の系と比べます。比較器は補題の主張から書いたもので、3項目以外の一致を求めます。違いは故障で、結果は `tool_error` です。覆うのは `int_range` がビルドした範囲だけで、両端の間の範囲は概略に頼ります。

エスカレーション用の `same_system` は、エンティティのid、変数の個数、規則の名前と位置だけを比べ、変数そのもの、ガード、効果は比べません。

## 符号化の忠実性

**定義1（状態の構造）**: `T_{β'}` の状態 `s` に対し、`𝔄(s)` は `E<i>` をスロット `[n'_E]` と余分な要素 `⋆_E` として解釈します。`nil<i>` は `⋆_E`、`zero<i>` はスロット0、`v<k>(i)` はスロット `i` での `s(v)[i]` の添字です。ステップ `s →_{a,b} s'` に対する `𝔄(s, b, s')` は、さらにパラメータ、後状態の関数、新しい定数を、そのステップの値で定めます。

**命題2（B1、過大近似）**: `β` でI1を仮定します。このとき `Sc(M, β)` のどの `β'` でも次が成り立ちます。

- (F1) `T_{β'}` のどの状態 `s` でも `𝔄(s) ⊨ Decl`
- (F2) どの初期状態 `s ∈ I_{β'}` でも `𝔄(s) ⊨ Init`
- (F3) `T_{β'}` で `s →_{a,b} s'` なら `𝔄(s, b, s') ⊨ Step_a`
- (F4) 符号化できる述語 `φ` の符号化を `𝔄` が満たすことと、`expr.rs::eval` が真を返すことが同値

直観的には、本当の系のどの状態とどのステップも符号化のモデルとして現れる、ということです。符号化の側に余分な状態やステップがあってもかまいません。証明の概略は、F3を補題U₀ と「`Enc::step` と `each_successor` が同じ更新を同じ順で適用する」ことから、F4を `φ` についての帰納法と比較の対応表から確かめるものです。この概略を超える証拠は、B1の項にまとめます。

**前提の充足可能性**: F1、F2、`I_β ≠ ∅` から `Decl ∧ Init` は充足可能です。符号化のバグでこれが充足不能になると、すべての規則が `proved` になりかねません。そこで毎回の証明は最初にカナリアの候補 `false` を検査します。これは初期条件で落ちるはずで、生き残ったら規則を1つも証明せず、すべて `Unproved::Premise` にします。カナリアが生き残るのは `unsat` のときだけで、前提にz3が `unknown` と答える場合は捕まりません。4つのモデルでMBQIを有効にしたz3 5.1.0が `Decl ∧ Init` を `sat` としたのは、抜き取り確認であって保証ではありません。

## 帰納法とHoudini

### 相対帰納法

状態規則 `R` は単独では帰納的でないことがよくあります。`R` が成り立つが到達可能でない状態から、あるステップが `R` を破りうるからです。そこで `R` を含む集合 `K` をまとめて帰納的と示し、他の要素に補題の役をさせます。`prove` はこの集合を候補の中からHoudini（FlanaganとLeino, 2001）で探します。すべての候補から始め、初期条件か帰結条件の検査で破れる候補を落とし、何も落ちなくなるまで繰り返します。縮むだけの集合の上での、`k = 1` の帰納法です。

### ラウンド

`prove_round` は1回のHoudini探索を次の手順で行います。

1. **候補**: `refuted` でない選択された規則、組み込みの補題、採掘した補題、前のラウンドのCTIの節です。採掘した補題には待ち段階0、1、2があります。1に入るのは細かい補題と数え上げです。2に入るのは∀∃です。
2. **活性化リテラル**（activation literal）: 各候補 `k` に `act_k ⇒ ⟦ψ_k⟧^Pre` をソルバーごとに1回だけ宣言し、帰結条件の検査は現在の要素の `act_k` を主張します。待ち段階のリテラルは、その段階が加わるときに初めて宣言します。
3. **初期条件**: 候補ごとに1回、その段階が加わる前に検査します。`sat` と `unknown` のどちらでも落ちます。
4. **帰結条件**: アクションを巡回し、`reads(ψ_k) ∩ writes(a) ≠ ∅` の要素だけを検査します（`breaks`）。このような要素を、`a` が「当たる」要素と呼びます。`sat` と `unknown` のどちらでも落ちます。落ちた候補は、そのアクションの残りの検査の間は主張したままにします。そのため、答えは検査の順に依存しません。何も落ちない巡回まで繰り返します。
5. **待ち段階**: 規則が初期条件の後で落ちたら次の段階を加え、落ちた規則を集合に戻して手順4をやり直します。落ちた補題は戻りません。
6. **CTI**: 落ちた規則ごとに、ソルバー0を `(reset)` し、MBQIを有効にして、残した集合と規則の前状態の式を主張して問います。

CTIの段階が新しい節を作ったら、さらに最大 `STRENGTHEN_ROUNDS = 2` 回の完全なラウンドを回し、最後のラウンドの結果を使います。

手順3〜5は `smt.mbqi false` で走ります。モデルに基づく量化子の具体化（MBQI）がなくても、z3はE-matchingで `unsat` を示せます。`Decl` が量化子を含むので、充足可能な問いのほとんどは `unknown` になり、その候補は `sat` と同じく落ちます。MBQIは完全性のための仕組みです。切っても充足可能な問いが `unsat` になることはないので、`proved` は1つも変わりません。全サンプルを1ソルバーで証明した計測では、同じ結果のまま150 sが68 sになりました。CTIの段階はモデルが要るので、MBQIを戻します。

### ステップの刈り込みと残した集合

**補題F5（B6）**: `reads(ψ) ∩ writes(a) = ∅` なら `Decl ∧ Step_a ⊨ ⟦ψ⟧^Pre ⇔ ⟦ψ⟧^Post` です。`Enc::step` が後状態の関数を変える効果と、`cone.rs::effect_writes` が列挙する効果が一致するので、関数が変わる変数はすべて `writes(a)` に入ります。したがって、当たらない要素の検査を飛ばしても何も失いません。この刈り込み（pruning）の証明は原文の [Step pruning](https://github.com/manji-0/rdra-ish-dsl/blob/169cdf3fb49bbcaf0c7d452c32a57da18720fdd0/docs/theory/z3.md#step-pruning) にあります。

**命題4（B5）**: H1とH4の下で、ラウンドが残す集合 `K` は `Enc` に対して帰納的です。すべての要素は初期条件を通っていて、手順4のループは、集合がずっと `K` のまま全アクションで当たった要素がすべて `unsat` だった巡回の後でしか抜けません。当たらない要素は補題F5で保たれます。帰結条件の式のモデルは、活性化リテラルを `K` で真、他で偽とすれば、検査した問いのモデルに拡張できます。そのため、問いが `unsat` なら帰結条件は成り立ちます。

`unknown` は候補を決して助けず、落ちたものとして扱います（B12）。`SolverError` は証明全体を中断します。

### 最大性

**命題5**: z3の答えがすべて厳密なら、最初の段階は待ち0の候補の最大の帰納的な部分集合を求めます。しかし最終の `K` が、提示したすべての候補の最大の帰納的な部分集合とは限りません。理由は4つです。

1. `unknown` は落ちたものとして扱います。そのため、実は充足不能な問いでも、z3が諦めれば候補が落ちます。その頻度はわかっていません。formal-verification.mdの `unknown` の数は充足可能な問いと未決の問いを分けていないので、どちらの証拠にもなりません。
2. 段階が加わる前に落ちた補題は、加わった補題があれば帰納的になったかもしれませんが、戻りません。
3. 段階が加わるのは規則が初期条件の後で落ちたときだけです。
4. CTIのラウンドは候補を増やしてやり直し、最後のラウンドの結果を使います。

どれも健全性には触れず、健全性は命題4だけに依存します。影響するのは、どの規則が証明され、どの `lemma:` 行が出るかです。

## 健全性定理

**定義3（証明の範囲）**: 範囲 `β`、スコープ `σ` の実行について、`Sc(M, β)` は、`TransitionSystem::build(M, β', σ)` がエラーを出さず、モデルのIntリテラルがすべて `m'` 以下である範囲 `β' = (n', m')` の集合です。2つ目の条件は1つ目から従います。範囲外のリテラルは `IntLiteralOutOfBounds` というエラーだからです。

D1により `1 ≤ n'_E ≤ 255`、`1 ≤ m' ≤ 255` です。`m'` に依存するビルドエラーは、どれも実行の `m` の片側でだけ起きます。`IntLiteralOutOfBounds` は最大のリテラル未満、`DomainTooLarge` はnullableなInt列があって254超、`StateTooWide` は詰め込んだ状態が幅を超える `m'` 以上です。そのため実行のスロット数では、`Sc(M, β)` の `m'` は1つの区間 `L … M` になります。

`Claim::of` はビルドして見つけたこの区間を、`for any number of rows and every --int-range-max from L to M, in the whole model`（スコープ付きなら `in the selected scope: <flags>`）と表示します。この文言はヘッダ、すべての `proved:` 行と `lemma:` 行、`OK:` 節、`--deny-unproved` のエラーに出ます。Int値の変数を持たない系は範囲を表示しません。区間は実行のスロット数でだけ求めるので、より大きい `n'` では区間内の `m'` で `StateTooWide` になることがあります。その組では系 `T_{β'}` が存在しないので（D1）、表示した主張は空虚に覆います。

**定理1（B2）**: 次を仮定します。

- (H1) z3は充足不能な問いにだけ `unsat` と答える
- (H2) `smt.rs` が印字するテキストは、元の `Expr` を意味する
- (H3) `Sc(M, β)` のすべての `β'` で命題2が成り立つ
- (H4) 証明器はz3の各答えを、それを尋ねた検査の答えとして受け取る
- (H5) `β` でI1が成り立つ。つまりビルドは `T_β(M, σ)` を返し、`Enc` はそれを符号化する

このとき `verify --prove` が `proved: R` と表示すれば、`Sc(M, β)` のすべての `β'` で `T_{β'}(M, σ) ⊨ R`（D16）です。この定理はH3を条件にしていて、H3は証明の概略であり、検査済みの事実ではありません。

証明は、`proved` の規則が帰納的な集合 `K`（命題4、または証明書なら命題7）に入ることから始まります。`T_{β'}` の有限トレースの長さについての帰納法で、各状態で `K` のすべてが成り立つことを示します。基底はF1、F2と初期条件の検査から、段階はF1、F3、帰結条件の検査、補題F5から従います。最後にF4で `⟦R⟧^Pre` がD16そのものになります。

仮定についての注意です。

- **スコープ**: `--buc`、`--without-usecase`、`--without-buc`、`--actor` の下では、符号化した系に外したアクションがないので、`proved` はモデル全体について何も言いません。証明を主張する各行が `in the selected scope` と書きます。
- **Int値**: `Enc` の中ではInt型の変数はすべての非負整数を動きます。上限が255を超える `T_{β'}` は存在しないので、表示範囲はビルドできる最大の `m'` で止まります。負の値はどちらにも含みません。
- **インスタンス数**: `Enc` には個数がないので、ビルドがエラーを出さないどの `n'` でも成り立ちます。255を超える個数は `T` が定義する系ではありません。
- **前提**: `Decl ∧ Init` が充足不能でも、H3がF1とF2を含むので結論は形式的には従います。危険なのはH3が偽であることで、それは差分テストとカナリアで表に出ます。

**系6（B16 の後半、証明で判定するcone）**: `BfsCone::decided_by_proof` は、違反なしにメモリ上限で止まった安全性のconeを、`after` アサーションがなく、すべての不変条件が `ProofRun::proved` に入っていれば `ok` にします。`β ∈ Sc(M, β)` なので、定理1の仮定の下でそれらは `T_β(M, σ)` で成り立ちます。誤った `proved` はこの `ok` も誤らせ、実行時にそれを捕まえるものはありません。`--max-states` で止まったconeを変えないのは、定理の限界ではなく選択です。持ち上がらなかった違反を持つconeはツールエラーのままです。

## 候補と信頼基盤

命題4はどの候補の集合でも成り立つので、候補の出所が `proved` を不健全にすることはありません。出所が影響するのは、どの規則が証明されるかだけです。`proved` の信頼基盤はH1〜H5です（H5は証明器ではなくビルドの主張I1です）。候補、採掘の結果、CTI、利用者の補題は、どれも信頼基盤に入りません。

### 組み込みの補題

エンティティごとに「存在しない行は既定値を持つ」と「どのアクションも削除しないエンティティの行は削除されていない」を、キーごとに「存在する行のキーは存在しない親を指さない」を提示します。1つ目は、`Enc` は存在しない行を固定しないが、`T` は既定値で行を作るので必要です。すべて待ち0です。

### 採掘した補題（B9）

`mine.rs::mine` は、各エンティティconeと選択した各規則のconeを、`T` と（ビルドできれば）1インスタンス版の `mining_twin` でBFS探索します。各探索は最大 `STATE_CAP = 50,000` 状態で、到達したすべての状態が示すことを候補にします。

| 形 | 待ち |
|---|---|
| 存在する行が、coneの行変数について到達したパターン（最大64）のどれかである。各列の値と値の組 | 0 |
| 子の行と親の行の組（全体、親の列ごと） | 0 |
| 同じ親を指す2つの子の行が、到達したパターンの組のどれかである | 0 |
| 子の1列と親の1列（組で含意されないときは2列） | 1 |
| 数え上げ: 数え上げガードのステップが書く値を持つ親の行は、そのキーの子を最大または最小で `k` 個持つ。最大は `k ≤ 7`、最小は `k ≤ 8` | 1 |
| ∀∃: `E` の存在する行が `a` を持つ間は、`F` のある存在する行が `b` を持つ（両者の間にキーはない）。実行の範囲からだけ採掘する | 2 |

採掘した補題は有限のインスタンスからの推測です。invisible invariantsやDistAI、DuoAIのデータ駆動の推論と同じやり方です。他の範囲では偽かもしれず、上限で止まった探索に依存するかもしれません。Houdiniは他と合わせて帰納的なときだけ残すので、誤った採掘や上限付きの採掘は証明を失わせるだけで、健全性は失わせません。探索の順は固定で、候補はスレッドに依存しません。

### CTIの節（B10）

規則が落ちると、`strengthen.rs` はCTIのモデルの前状態を読みます（`diagram`）。存在する行、その列と印を固定するリテラル、キー、同じエンティティの2行が異なること、です。リテラルが `LITERAL_CAP = 40` 個以下なら、節 `¬(l_1 ∧ … ∧ l_r)` を初期条件と、残した集合に規則を加えたものに対する帰結条件で検査します。通れば、通る限りリテラルを決まった順に1つずつ落とし、使わない束縛を削ります（`generalize`、`trim`）。これはIC3の帰納的一般化で、フレームや先行状態への再帰はありません。生き残った節は次のラウンドの普通の候補です。規則を仮定に使って得た節なので、それだけでは何も証明せず、Houdiniが他の候補と一緒に決めます。

### 利用者の補題（`.lemma()`）

`.lemma()` を付けた規則は、他と同じ選択された規則です（待ち0、規則の `rlimit`）。`proved: lemma …` か `unproved: lemma …` と表示し、規則の数からは外します。規則なので、他と合わせて帰納的なときだけ残り、信頼基盤に何も足しません（B11）。初期条件の後で落ちれば待ち段階を開きます。証明書は、利用者の補題も含むすべての規則を残すときだけ再利用します。

補題は他の規則と違い、印を読めます。`E.in_run(UC)` はD10の実行印を、`E.raised(Ev)` はD11のラッチを読みます。符号化はこれらを列と同じく読み、信頼基盤は増えません。

`verify` は補題からBFSのconeを作らず、エスカレーションもしません。ただし補題の読む変数が他の選択された規則のconeに入っていれば、そのconeが補題を検査し、偽の補題は `refuted` で実行を失敗させます。BFSが違反に届かなければ、Houdiniが偽の補題を `not inductive` として落とし、助けるはずだった規則は補題なしで判定されます。

### 残した補題を探索した状態で確かめる

テストに限り、規則を証明するか補題を残すすべての証明は、残した補助の補題（組み込み、採掘、CTI）を評価します。評価する状態は、採掘と同じconeを実行の範囲でもう一度走らせて届いた状態です（`explored.rs::lemma_faults`）。`RDRA_ISH_CHECK_LEMMAS=1` のときか `rdra-ish-core` のテストビルドで動きます。費用がかかるので、利用者の `verify` では動きません。補題を破る状態は故障で、証明は規則を1つも証明せず、coneも判定せず、結果は `tool_error` です。raiseの印を外すcone（`cone_leaves_marks`）は全体の系が届かない状態に届くことがあるので読みません。読むどのconeにも収まらない補題は検査しません。この検査は読んだ状態の外で誤っている `proved` を見ないので、B16の後半は変わりません。

## proved以外の判定

- **`unproved: R: not inductive`（B17）**: CTIの段階は `Step_a`、残したすべての候補、`⟦R⟧^Pre`、`Viol(R, Post)` を主張し、モデルを表示します。前状態は `Enc` のモデルで、到達可能とは限りません。CTIは帰納法の反例であり、反例ではありません。`β` を超える行やInt値を持つこともあります。
- **`unproved: R: z3 gave up on A`（B12）**: 初期状態が符号化できないか、問い直しやMBQIを有効にしたCTI検査が `sat` にならなかった場合です。何も主張しません。
- **`unproved: R: an initial state violates it`**: `Init ∧ Viol(R, Pre)` が充足可能です。モデルは `I_β` より多くの行を持ちうるので、ある `T_{β'}` の違反であるのは、それが初期状態に対応するときだけです。
- **`out of scope: R: why`**: `R` が符号化できません。何も主張しません。
- **``unproved: R: the canary `false` survived initiation …``**: 前提が `unsat` で、どの規則も証明しません。ビルダーか符号化のバグで、モデルの性質ではありません。

反例（D23）はBFSかTLCから来るもので、z3からは来ません。

## 予算、ソルバー数、決定性

`ProveOptions::default` は、規則（利用者の補題を含む）に `rlimit = 20,000,000`、組み込み・採掘・CTIの補題に `lemma_rlimit = 2,000,000` を設定します。formal-verification.mdの "Budgets"（z3 5.1.0）によると、候補を残す検査が使った量は規則で最大161,000単位（上限の1/124）、補題で116,000単位（1/17）で、4ソルバーでは補題が144,000（1/14）でした。`proof_equivalence.rs` はすべての検査を計量します。残す検査が上限の10分の1を超えるか、検査が上限に達するか（`canceled`）、答えた検査が10分の9を使うと失敗します。

`rlimit` は時間ではなくz3内部の仕事量を数えるので、検査の答えは負荷に依存しません（B13、B14）。依存するのは次の3つです。

1. z3のバージョン： `VERIFIED_Z3 = ["5.1.0"]`（`flake.nix` と `flake.lock` で固定）。他のバージョンや読めないバージョンでは注意を出します。
2. 問いのテキスト： 符号化で決まります。
3. ソルバーの履歴： 各ソルバーは別のプロセスで、`violated_each` は検査を添字でソルバーに配ります。各ソルバーが受け取るコマンドの列は符号化とソルバー数だけで決まり、スレッドのタイミングには依存しません。

したがって、z3のバージョンとソルバー数が同じなら、証明は符号化の決定的な関数です。これはz3が同じ入力に決定的であることを仮定しています。ソルバー数は `RDRA_JOBS`、なければ `min(cores, 8)` なので、マシンごとに違います。ソルバー数からの独立は経験的な事実です。food-permit-opsの補題の検査には、1〜6ソルバーでz3が自分から諦め、3ソルバーでは上限に達するものがあります。どちらも `unknown` なので判定は同じですが、履歴が検査の使う量を変えることを示しています。

## 証明書キャッシュ

`cli/src/prove.rs` は、モデルと規則の選択ごとに、利用者のキャッシュディレクトリにファイルを1つ置きます。中身は、z3のバージョン行、ラウンドのダイジェスト、前回の証明が残した集合の添字です。ダイジェストはタグ、rdra-ishのバージョン、オプション、`Decl`、`Init`、すべての `Step_a`、各候補の出所・`rlimit`・待ち・式から作ります。ファイルは自分のチェックサムを持ち、壊れたものは無視します。`RDRA_ISH_NO_PROOF_CACHE` で無効にできます。

**命題7（B15）**: 再利用した証明書で規則が `proved` になるのは、証明書の名指す集合が現在の `Enc` に対して帰納的なときだけです。`reusable` が `K` を受け入れる条件は4つです。すべての添字が現在の候補であること、すべての規則が `K` にあること、`K` の各候補が初期条件を通ること、各アクションで当たる要素がすべて `K` のリテラルの下で `unsat` になることです。これは命題4の最後の巡回そのものです。

証明はダイジェストを使いません。ダイジェストは、再利用が**出力を変えない**ことを保つためのものです。ダイジェストが同じなら同じラウンドを送ったので、決定的なz3なら同じ集合を残し、出力はバイト単位で同じです。検査の順や落ち方の決め方はハッシュするテキストに現れないので、変えたらタグ（`rdra-ish proof certificate 3`）を手で上げる必要があります。証明書はCTIの節を持たないので、CTIを必要とした証明は毎回キャッシュを外します。再利用に失敗したら、ソルバーをリセットして通常のHoudiniを走らせます。

## BFSとの相互作用

**反駁**: `refuted.rs::refuted` は、同じ実行の安全性のconeが違反した不変条件を名前と位置で集め、`refuted` として `prove` に渡します。これらは候補にならず、`refuted: R (BFS counterexample at k instances)` と表示します。`k` は必要ならエンティティごと（`Order=1 Payment=2` など）に出ます。

**命題8（B16 の前半）**: 候補を取り除いても `proved` が不健全になることはありません。さらに、(a) BFSの違反が `Sc(M, β)` のある `β'` で `T_{β'}(M, σ)` の到達可能な状態であり、(b) z3の答えがすべて厳密なら、`R` を取り除いても他の規則の判定は変わりません。(a) と定理1から `R` はどの帰納的集合にも入らないので、厳密なHoudiniはそれを落とします。その落ち方が待ち段階を開いても、より大きい開始集合での厳密なHoudiniは前の集合の上位集合を残します。

どちらの仮定も保証されてはいません。前者は、coneが保証する違反か洗練したconeで再発見した違反（D23）しか数えないことと、I1に頼ります。後者がなければ、`R` の有無で検査の順と中身が変わり、`unknown` の出方が変わりえます。どちらの場合も誤った `proved` は出ません。

**エスカレーション**: z3が `unproved` とした規則で、自身の安全性のconeが違反なしに最後まで走った場合、coneを `n+1` と `n+2` インスタンスで再探索します。格納量は最初の10倍（`GROWTH`）とメモリプールの残りまでに抑え、再ビルドした系は `same_system` を通る必要があります。見つかった違反はトレース付きのエラーとして実行を失敗させ、他のBFSの反例と同じ位置づけです。エスカレーションは有界の証拠を足すだけで、`proved` を変えません。

**上限で止まったcone**: メモリ上限に達したconeは、中の検査がすべて証明済みなら `ok` になります。証明の出力への検査（比較の照合、補題Uの比較、テスト時の補題の検査）はどれも、どの実行も届かなかった状態でだけ誤っている `proved` を見ません。そのような `proved` は、止まったconeを `ok` にしてしまいます。

証明は安全性のconeの後に始まり、性質とモデル全体の段階と並行して走るので、安全性の段階の `refuted` だけを使います。CTIは `Enc` の状態で到達可能とは限らず、BFSの反例は `T` のトレースです。設計上、ツールは両者を突き合わせません。

## 再現例

原文には、main `91524792` のリリースビルドとz3 5.1.0での出力を引用した再現例が7つあり、どれもテストかコーパスの例としてリポジトリにあります。Intの拡幅を押さえる2つを紹介します。モデル全文と残りの例（スコープ付きの証明、延期できないビルドエラー、nullableな列の上限、偽の `.lemma()`、前提の抜き取り確認）は原文の [Reproductions](https://github.com/manji-0/rdra-ish-dsl/blob/169cdf3fb49bbcaf0c7d452c32a57da18720fdd0/docs/theory/z3.md#reproductions) を参照してください。

**上限を超える `.when` 付き `present` 書き込み**（`z3_guarded_present_past_the_top`）

```rdra
entity Item "i" {
  id: Int @pk
  open: Bool @default(true)
  n: Int @null
}
usecase Add "a"
usecase Fill "f"
creates(Add, Item)
updates(Fill, Item)
condition IsOpen "o"
holds(IsOpen, Item.open == true)
sets(Fill, Item.n == present).when(IsOpen)
forbidden(Item, n > 5)
```

`--int-range-max 5 --instance-count 1` では規則は `T_β` で成り立ちますが、z3は `unproved: Forbidden_Item_0: not inductive; Fill(Item#1) breaks it …` と表示します。符号化した `Fill` は任意の数を書くからです。`--int-range-max 7` ではBFSが `n=6` で `refuted` にします。ガードが `β` での値を列挙していたら、符号化は `n` を5以下に縛る補題を残せてしまい、上限7で偽の規則を上限5で `proved` と表示するところでした。

**`.when` 付き `null` と `.when` 付き `present`**（`z3_guarded_null_beside_present`）

```rdra
entity Item "商品" { id: Int @pk  k: Int @null  n: Int @null }
usecase Add "追加"
usecase Bump "増加"
usecase Fill "記入"
creates(Add, Item)
sets(Add, Item.n == 1)
updates(Bump, Item)
sets(Bump, Item.k == present)
updates(Fill, Item)
condition Small "小さい"
holds(Small, Item.k <= 5)
condition Big "大きい"
holds(Big, Item.k > 5)
sets(Fill, Item.n == present).when(Small)
sets(Fill, Item.n == null).when(Big)
forbidden(Item, n == null)
```

2つの `sets` が、nullを横に列挙した「すべての数」の `Choose` にまとまります。`--int-range-max 5` では `k` が5を超えないので規則は `T_β` で成り立ちますが、`one_of` が列挙したnullを残すので、z3は `not inductive` とします。`--int-range-max 6` ではBFSが `k=6, n=null` で `refuted` にします。選択を `c ≥ from` だけで符号化していたら、nullを書くステップがなく、誤って `proved` と表示するところでした。

- **未解決の穴**: 一覧には記載がありません。

### B16 BFSとの相互作用

- **命題**: 同じ実行の安全性のconeが違反した規則は `refuted` で、試さず、他の判定も変えません。規則を反駁するのは、coneが保証する違反か、洗練したconeか厳密なconeが見つけた違反だけです（A2）。メモリ上限で止まったconeは、中のすべての規則が証明済みなら証明で `ok` にできます（`after` アサーションと `--max-states` は除く）。
- **証拠**: P-sketch（前半は命題8、後半は系6で、`β` でのB2に頼る）、D。Dは狭くテストだけです。`RDRA_ISH_CHECK_LEMMAS=1` の下で残した補助の補題を採掘のconeが届く状態で評価する検査と、どちらの証明の検査も上限に達していないことを表明する差分テストです。
- **仮定**: 前半は、BFSの違反が本物であることと、z3の答えが厳密であること。後半は定理1の仮定すべて。
- **未解決の穴**: MBQIなしのラウンドでz3が自分から諦めた検査は数えるだけで表明しないので、「すべての答えが厳密」は上限についてしか確かめていません（どちらにしても `proved` は誤りません）。誤った `proved`（B1の故障）は止まったconeを誤った `ok` にし、それを見る実行時検査はありません。補題の検査はテストでしか動かず、採掘のconeが届く状態しか読みません。どの実行も届かない状態でだけ誤っている証明は、この検査を通ります。

### B17 CTIの意味

- **命題**: CTIは、その規則、すべての証明済みの規則、残したすべての補題が成り立つ状態（到達可能とは限らない）からのステップで、CTIの行はそう書きます。
- **証拠**: none written（構成から）、D（1つのテスト）。
- **仮定**: 追加なし。
- **未解決の穴**: 一覧には記載がありません。

### B18 `proved` が覆うもの

- **命題**: `proved` は状態規則だけを覆い、`after` アサーション、時間性質、デッドロック、witnessは覆いません。
- **証拠**: none written（構成から。`run_proof` は `Target::Invariant` だけを受け取る）。最も近いテストは、z3がconeの規則を証明しても、そのconeの `after` アサーションが `not decided` のままであることを確かめるものです。
- **仮定**: 追加なし。
- **未解決の穴**: これを直接表明するテストはありません。

## 妥当性への脅威

上の各項の穴と重ならないものを中心に挙げます。

- **忠実性は論じたもので、検査したものではない**（B1）: 次の場合にだけ問題になる食い違いは見えません。より大きい範囲、大きいcone、サンプルとコーパスのどれにも現れない構成です。ある構成が差分テストに届くのは、どこかのサンプルかコーパスの例がそれを持ってからです。
- **一様性は論じたもので、検査したものではない**（B2）: `arm_guards` が `Choose` の列挙を2度読むような派生した読み取りは、コードを読む確認で特に見落としやすく、CIの一覧照合にも落ちません。ビルダーが規則やガードに `β` を読み込む変更は、広いIntの軸の差分テストか参照インタプリタがたまたま届かない限り、テストを落とさずに他の範囲で定理1を壊します。`β` での系と大きい `m` での系を比べる実行時検査ならこの種類を捕まえますが、`same_system` はそれをしません。
- **z3**（H1）: 問いは決定可能な断片の外にあります（解釈されないソート上のInt値の関数、∀∃の補題とガードでの量化子の交替）。そのため `unknown` は想定内で、証明を失わせるだけです。`unsat` を誤って答えるz3のバグは誤った `proved` を生み、`proof_equivalence` がそれを見るのはBFSが違反に届くときだけです。
- **マシンをまたぐ決定性**（B13、B14）: すべてのマシンでソルバー数が一致するか、経験的なB14が成り立つことに頼ります。
- **スコープ**（B2）: 部分実行のフラグの下の証明は、より小さい系の証明です。`--entity` の下では、延期したビルドエラーも符号化した系に残ります。延期するのは選択した対象の厳密なconeのエンティティにかかわらないエラーだけなので、規則の判定はエラーの有無で同じです。
- **プリンタと構文解析器**（H2、H4）: モデルの読み手（`Sexp`、`read_cti`、`strengthen::diagram`）はCTIと候補の節にしか影響せず、`proved` には影響しません。
- **証明で判定する止まったcone**（B16）: 系6は、`proved` だけを根拠として、メモリ上限で止まったconeを `ok` にします。そのため、誤った `proved` は誤った `ok` を生みます。

## 関連研究

候補のループはHoudini（FlanaganとLeino, FME 2001）で、`k = 1` の帰納法（Sheeranら、 FMCAD 2000）に強化の補題を組み合わせます。CTIの一般化はIC3/PDR（Bradley, VMCAI 2011、Eénら、 FMCAD 2011）から借りています。小さいインスタンスからの採掘はinvisible invariants（Pnueliら、 TACAS 2001）、DistAI（OSDI 2021）、∀∃に広げたDuoAI（OSDI 2022）と同じ考え方です。Ivy（PLDI 2016）と違い、この符号化はInt列と∀∃があるので決定可能なEPRに収まりません。MBQI（Geとde Moura, CAV 2009）は、Houdiniのラウンドでは切り、CTIの段階では有効にします。書誌と、UPDR、IC3PO、LahiriとQadeerの研究との関係は原文の [Related work](https://github.com/manji-0/rdra-ish-dsl/blob/169cdf3fb49bbcaf0c7d452c32a57da18720fdd0/docs/theory/z3.md#related-work) にあります。
