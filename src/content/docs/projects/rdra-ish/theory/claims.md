原文の行はとても長く、1行に証拠の説明、コードの位置、テスト名がすべて入っています。この解説は行を訳しません。行の読み方を説明したあと、各行について次の4つだけを日本語で示します。

- ID
- 主張の要旨（1〜2文）
- 証拠の種類
- 未解決の穴の要旨（なければ「なし」）

## 行の読み方

### ID と記法

- **ID** は `I`、`A`、`B`、`N`、`T` のいずれかと番号です。それぞれテーマ `(0)` 構築、`(a)` cone、`(b)` z3、`(c)` ネイティブ、`(d)` TLCに対応します。
- `D1` から `D25` は行ではありません。[意味論と記法](/projects/rdra-ish/theory/semantics/) の定義です。
- **Claim**（主張）は意味論の記法で書かれています。`(a)` から `(d)` では、`T` は `TransitionSystem::build` が返す系です。
- `T` が定義上の `T_β(M)`（D13）や、スコープ付きの `T_β(M, σ)`（D24）と一致するのは、主張I1が成り立つときに限ります。`(a)` から `(d)` の行は構築された系についての主張で、I1を仮定するのは明記した箇所だけです。
- `C` はcone `T|W`（D15）、`R` は独立した部分ライフサイクルで縮約したcone、`Q` は実行をスロットの置換で割った商です。
- `⊨` は「判定が `ok`」、`⊭` は「判定が `counterexample`」を表します。

### 証拠の種類

| 記号 | 名前 | 意味 |
|---|---|---|
| `P-full` | 紙の上の証明 | 読者が一歩ずつ確かめられる論証 |
| `P-sketch` | 証明の概略 | 依拠する事実を名指しするが、導出はしない |
| `M` | 機械検査 | Kaniハーネス、shadow twin、debugや `shadow` ビルドが毎ステップ行う検査、Lean 4の証明のいずれか |
| `D` | 差分テスト | エンジンコーパス、サンプル比較、ランダムモデルの掃引、参照インタプリタ、ミューテーション実行のいずれか。行ごとにテストを名指しする |
| `R` | 実行時検査 | 利用者の実行のたびに自分の出力で主張を確かめ、破れたらツールエラーを出すかモデルを拒む |
| `A` | 仮定 | プロジェクトが検証しない部品に依拠する（z3、TLC、JVM、TLA+ 変換の忠実さ、rlimitの決定性） |
| none written | 論証なし | コードの構成上は成り立つように見えるが、それを論じる文書がない |
| none | 証拠なし | 証拠が見つからない |

`M` の中身には注意が要ります。

- Kaniハーネスは、Rustの関数を、ある範囲までのすべての入力について有界モデル検査します。
- shadow twinは参照実装です。`--features shadow` ビルドが高速版と並べて実行し、違いがあればパニックします。比べるのはCIの実行が与える入力だけです。
- twinが確かめるのは2つの実装どうしの一致で、仕様との一致ではありません。
- Leanの証明（`proofs/lean/`）は、仮定から定理を導く論証を検査します。対象は抽象的な遷移系か、ガードと効果の構文から読み書き集合を計算するアクションのモデルです。
- LeanはRustのコードを読みません。コードが仮定を満たすことも、コードのアクションがモデル化した構文であることも示しません。

`R` は「その種類の誤った答えが出力されない」ことの証拠です。答えが正しく計算されたことの証拠ではありません。

### テストが走る場所の印

原文のTests列には、テストがCIのどこで走るかを示す印が付きます。印のないテストは、CIのdebugの `test` ステップで、プルリクエストとmainのたびに走ります。`(main only)` はmainだけ、`(release jobs)` はリリースビルドのジョブだけで走ります。`(with TLC)` と `(with z3)` はそのツールを必要とし、CIでは無ければ失敗にします。ほかの印と細かな規則は、upstreamの [How to read a row](https://github.com/manji-0/rdra-ish-dsl/blob/169cdf3fb49bbcaf0c7d452c32a57da18720fdd0/docs/theory/claims.md#how-to-read-a-row) にあります。

## (0) 構築

<!-- constrained-by ./semantics.md -->

upstream: [(0) The build](https://github.com/manji-0/rdra-ish-dsl/blob/169cdf3fb49bbcaf0c7d452c32a57da18720fdd0/docs/theory/claims.md#0-the-build)

意味論は、モデルのテキストから `T_β(M)` を定義します（D1〜D13、D24）。どのエンジンも構築が返す1つの系を読みます。そのため、構築が定義からずれるとすべての判定が一斉に動き、エンジンどうしの一致ではそれを示せません。これが共通モードの故障です。このテーマは3行で、テーマ文書はありません。I1は構築全体です。I2とI3は、構築が意図して与える言語の読み方で、モデルを書く人が予想しないかもしれないものです。

| ID | 主張の要旨 | 証拠 | 未解決の穴 |
|---|---|---|---|
| I1 | 構築がエラーを報告しない限り、`TransitionSystem::build(M, β, σ)` は定義どおりの `T_β(M, σ)` を返す。変数と値域、基底値、初期状態、ユースケースで名前を付けたステップ、各状態での規則の真偽が定義と一致する。 | none written, D, R | 下の注を参照 |
| I2 | 比較のnullは二値で読む（D5）。`x != 3` はnullの `x` で成り立ち、`not (x < 3)` は `⊥` で成り立つが `x >= 3` は成り立たない。論理的な `@derived` だけは三値で読む。lintの `negated-order-admits-null` がこの落とし穴を警告し、各判定は書かれたとおりのモデルに対して正しい。 | D | この警告を出すサンプルやコーパスのモデルがない。 |
| I3 | 検証は参照アクションを実行しない。`cascade`、`set_null`、`set_default` の外部キーでは、deleteは1行だけを消し、子とそのキーは残る。構築は `DeleteLeavesChildren` と `DeleteLeavesChildKeys` の警告でそう伝える。 | D | SQLエクスポートは `ON DELETE CASCADE` などを書く。そのため規則がモデルでは `ok` でも、そのデータベースでは破れることがある。アクションを実行するかは持ち主の判断とされている。 |

I1の証拠と穴は次のとおりです。

- 構築全体を論じた文書はありません（none written）。あるのは構成要素ごとの読みです。z3の文書のLemma U（`core/build` での範囲の使用箇所）、TLCの文書の構成ごとの論証、各定義の **Implemented by** 注記です。注記は場所の案内で、読みではありません。
- R: 忠実に符号化できないモデルを、構築は拒みます。256値を超える列の値域は `DomainTooLarge`、パックした状態に収まらない幅は `StateTooWide`、1つの `(var, param)` に2回書くアクションは `ConflictingEffects` です。
- D: T7の手書きのコーパスヘッダ89個が、名指しのモデルについてモデルから `T` への変換を確かめます。参照インタプリタの対象外では、これがCIで唯一の検査です。
- D: 参照インタプリタ（`core/tests/reference/`）は、構築器を使わずに `SemanticModel` を読み、素の値で総当たりに探索します。初期状態、到達可能な状態、アクションで名前を付けた辺、規則名、違反集合を、ネイティブの実行と比べます。対象は20,000状態以下の系です。z3の `proved` も、範囲を広げた参照の実行で確かめます。
- 参照インタプリタが扱う言語の部分集合と、拒む構文の一覧は、原文のEvidence列に詳しく書かれています。
- 穴： 部分集合の外や20,000状態を超える系、性質の判定については、モデルから `T` への変換を確かめるのは手書きの期待値だけです。それも名指しのモデルに限られます。
- 穴： 参照インタプリタは、パーサ、`build_model`、規則名、どのInt列を数として読むかを構築と共有します。
- 穴： 意味論の文書は、どのモデルが整形式かを、コードのエラー診断の一覧から取っています。

## (a) coneと縮約

テーマ文書： [coneと縮約](/projects/rdra-ish/theory/cones/) · upstream: [(a) Cones of influence and reductions](https://github.com/manji-0/rdra-ish-dsl/blob/169cdf3fb49bbcaf0c7d452c32a57da18720fdd0/docs/theory/claims.md#a-cones-of-influence-and-reductions)

影響範囲のcone（cone of influence）、部分ライフサイクルの縮約、インスタンス対称性、範囲と上限についての28行です。ここでの「解放されたスロット（freed slot）」は、coneが読まないエンティティをcone内のアクションが作る場合を指します。「取り残したraiseの印」は、coneがraiseの印を含めない場合です。

### cone の厳密さと過大近似（A1〜A7）

| ID | 主張の要旨 | 証拠 | 未解決の穴 |
|---|---|---|---|
| A1 | 安全性coneの厳密さ。解放されたスロットと取り残した印がない不変条件や `after` のcone `C` では、`Reach(C) = π_W(Reach(T))` が成り立つ。したがって `C ⊨ R ⇔ T ⊨ R` で、`C` のトレースは `T` のトレースに持ち上がる。 | P-full, R, M, D | リリースビルドはステップの書き込みを1つずつ検査するが、ステップ全体は検査しない。全体の比較はdebugと `shadow` ビルドだけ。ステップが `Wr(a)` だけを変えることを示すKaniハーネスはなく、`each_successor` に対するものは数分で終わらなかった。 |
| A2 | 過大近似のcone。スロットを解放するか印を取り残すconeでは `Reach(C) ⊇ π_W(Reach(T))` なので、`C ⊨ R ⇒ T ⊨ R` だけが言える。反例は範囲を超えるスロットを要するか、イベントの順序が禁じる実行かもしれない。そのため、coneがそのトレースを裏付けるまで数えず、`recheck_on` でconeを広げて実行し直し、最後は `exact_target_cone` に戻る。 | P-full, R, D | 裏付けの検査は、検査対象と `pred_reads` などのコードを共有する。裏付けのあるトレースが一歩ずつ持ち上がることはCorollary A28′ の証明で、検査ではない。呼び出し側がトレースへの注釈を先に済ませることは、コードを読んだ確認。イベントなしでユースケースを走らせる反例を持つサンプルやコーパスのモデルはない。 |
| A3 | カウント付きトリガーのカウンタはconeから落ちない。raiseする側を含むconeは、必ずハンドラも含む。 | P-full, R, D | なし |

| A5 | 3つの実行の手順。`Plain` の `Cone_P` が成り立てば `ok`、`WfNext` の `Cone_P_WF` が破れれば `counterexample` とする。`Cone_P_WF` が成り立っても、`ok` はconeが書かれる変数をすべて保つときだけで、そうでなければ `T` 上の `RdraSpec_P` が判定するか `not decided` になる。 | P-full, P-sketch, D | 手順の1と3はA8とA15に依存する。入れ子の縮約や `H` までの実行では、概略にとどまる入れ子の場合に依存する。平らな縮約では、コードから読んだ `Lemma6Hyp` のフィールドに依存する（A8）。 |

| A7 | `can_reach` のconeは厳密。書き手をすべて保ち、作られるスロットをすべて数え、縮約しない。 | P-full, D | なし |

### 部分ライフサイクルの縮約（A8〜A17）

| A8 | 部分ライフサイクルの縮約。関係 `(t, s) ~ (t, rep(class(s)))` は発散を区別しない停滞双模倣で、`T` 側の変数と `obs` を保つ。したがって `R` と `C` は、nextを含まないCTL* 式すべてで一致する。不変条件、witness、`Runs_*`、arm、`after` アサーション、デッドロック、`Plain` の `Cone_P` がこれに含まれる。 | P-full, P-sketch, R, M, D | 下の注を参照 |

A8の未解決の穴は長いので、要点だけを挙げます。

- `Lemma6Hyp` のうち、どの実行も検査しないフィールド `exact` は、コードを読んだ確認です。`Twin::FoldHolds` は2つの実装を比べるだけです。
- node foldや、ビットを共有するfold群では、`lemma6_faults` が検査するのは `cover`、`eff_s`、`X` のガードの数だけです。ガードを1つずつ対応させてはいません。別のガードを読むとステップが増えるだけで、それは反例の再生が拒みます（N16）。
- Leanが証明するスロットの構文とコードの対応は、コードを読んだ確認です。`candidate_slots` の振る舞い、`each_successor` がLeanの意味論どおりに構文を実行すること、`fold_of`、`restrict_to`、`holds_fast` がモデルどおりであることがこれにあたります。
- LeanのLemma 6のモデルは、foldごとに1ビットで、node foldを持ちません。モデルと実際の差のうち3つは紙の上で、残る1つは毎回の構築で確かめます。

- ガードの読みの分割や、ステップが `Wr(a)` だけを書くことを示すKaniハーネスはありません。

## (b) z3による証明

テーマ文書： [z3による証明](/projects/rdra-ish/theory/z3/) · upstream: [(b) Theorem proving with z3](https://github.com/manji-0/rdra-ish-dsl/blob/169cdf3fb49bbcaf0c7d452c32a57da18720fdd0/docs/theory/claims.md#b-theorem-proving-with-z3)

この節のすべての行は、次の3つを仮定します。

- **H1**: z3が `unsat` と答えるのは、充足不能な問い合わせに対してだけ。
- **H2**: 証明器が出力するSMTのテキストは、もとの `Expr` を意味する。`prove/smt.rs` の単体テストを超えては仮定。
- **H4**: 証明器は、各答えを、それを尋ねた検査の答えとして受け取る。`Z3::exec` は出力をエコーした目印まで読み、`Solver::check_sat` は最初の行を答えとして読む。

`core/prove/` でKaniハーネスを持つのは `Enc::one_of` だけで（B1）、shadow twinはありません。`Enc::compare` は `expr.rs::compare` を再実装したもので、後者のKaniハーネスはSMT側に届きません。そこで、規則を証明するたびに、実行の範囲のすべての値の組で両者を比べます（R、B1）。証明は、表示するIntの範囲を作った構築と、実行の系とをLemma Uまで比べます（R、B2）。テストの実行（利用者の実行ではない）は、残した補助の補題を、採掘に使ったconeが届く状態で評価します（D、B16）。検査に失敗すると `tool_error` で、規則は1つも証明されません。

以下で `Enc_n` は、エンティティごとに任意の行数を持つ `T` のz3符号化です。`Enc` は、すべての `n` を一度に表す符号化です（エンティティごとに解釈されないソートを使う）。

## (c) ネイティブ検査器

### 持ち上げの途中に残るパニック

upstream: [Panics left on a lift's way](https://github.com/manji-0/rdra-ish-dsl/blob/169cdf3fb49bbcaf0c7d452c32a57da18720fdd0/docs/theory/claims.md#panics-left-on-a-lifts-way)

A16、N13、N16は、持ち上げの検査の失敗をすべてツールエラーにします。それでも、持ち上げと探索のコード（`reduce/lift.rs`、`reduce/partition.rs::Succ`、`explore/` の各ファイル）には `expect`、`panic!`、`unreachable!` が残っています。これらはリリースビルドでもパニックします。どれかが失敗するとコマンドが止まりますが、再生できないトレースを出力することはありません。この小節は、それぞれを検査されない内部の不変条件として挙げ、成り立つ理由か依拠する仮定を添えています。原文は4つに分けています。

- **持ち上げの中**: `lift_stop` の前提条件、持ち上げたラッソの状態列が空でないこと、`lift_stop` の閉路探索、`after` 違反の `steps.last()`、デッドロックのトレース、`faulted` の `unreachable!` です。それぞれ、呼び出し側が渡すものや構築の仕方から成り立つ理由が書かれています。
- **持ち上げ前の探索の中**: 対称性の下の活性探索（`explore/orbit/liveness.rs`）での置換と、対の探索の検索です。通常の実行の活性探索（`explore/liveness.rs`）にも対応するものがあります。どれも、探索自身が作った隣接関係や、公平と印を付けた成分の中でだけ検索するので見つかる、という理由です。
- **呼び出し側の前提条件**: 活性の探索が `eventually` と `leads_to` 以外の形でパニックすること、`decide_property` が性質を自分のconeの系で見つけること、縮約や群を読む関数がそれを持つ実行からだけ呼ばれることです。
- **それらのファイルの外で、持ち上げの途中にあるもの**: `lift` は拡張した部分ライフサイクルを作り直して探索し直すので、`Extended::build` やその補助関数の `expect` に届きます。これらは縮約を作ったときに成り立っていたので、作り直しが同じものを再現すれば成り立ちます。そこで `Extended::rebuild_checked` が作り直しをdigestと照合し、違えば `ReplayError::Rebuilt` などで何も持ち上げません。ただし `build` の `expect` が先に失敗すると、照合の前にコマンドが止まります。
- 同じ小節には、正準形の `split` の `expect`（数え上げで成り立つ）、再生の `states.last()`、`base_state` と `Tick` の `expect` も挙がっています。

ステップ関係、BFS、状態ストア、群のコードのパニックは、N1〜N4のもので、この一覧には含みません。件数の変換、直前に挿入した項目の検索、同じ実行が作った表の添字なども、記録上の細部として省いています。
