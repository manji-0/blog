このページは、rdra-ishの設計判断を8つ取り上げ、それぞれの仕組みと理由を説明したうえで評価します。コマンドの使い方は [使い方](/projects/rdra-ish/usage/) と [CLI リファレンス](/projects/rdra-ish/cli-reference/) にあります。ここでは「なぜこの形なのか」と「どこで困るのか」に絞ります。

対象：main `169cdf3`（v3.0.0以降の未リリース版）。

このページは最初v1.0.0を対象に書き、リリースごとに評価し直してきました。前回はv3.0.0を対象に書きました。今回は、その評価の1つずつについて、mainが解消したのか、形を変えたのか、残したのかを確かめ直しています。mainはまだリリースされていません。ここに書く挙動は、次のリリースまでに変わり得ます（`docs/compatibility.md`）。

事実は、mainの `README.md`、`CHANGELOG.md`、`docs/`、`samples/` で確かめられるものに限ります。v3.0.0以降の変更は `CHANGELOG.md` の `Unreleased` 節から、それ以前の記録は各版の節から引きます。ソースのパスは、これらの文書が挙げているものを引きます。v3.0.0の評価でソースから確かめた事実のうち、mainの文書で確かめ直せないものは「v3.0.0のソースでは」と断って残します。ファイルパスはリポジトリ [rdra-ish-dsl](https://github.com/manji-0/rdra-ish-dsl/tree/169cdf3fb49bbcaf0c7d452c32a57da18720fdd0) のルートからの相対パスです。評価の部分は筆者の判断であり、「〜と考えます」のように書き分けます。

mainには `docs/theory/` が加わりました。検証器の保証を命題として書き、それぞれの証拠と仮定を示す文書群です。この評価では、プロジェクト自身が何を未解決と見ているかの出典として使います。`docs/theory/README.md` は、自身がmainの `91524792` を記述すると書いています。日本語の解説は [検証の理論](/projects/rdra-ish/theory/) にあります。

## 取り上げる判断

| # | 判断 | 主に効く場所 |
|---|---|---|
| 1 | 1つのテキストモデルと、すべての出力と検査器が読む1つの遷移系 | モデル全体 |
| 2 | 有界の `check` / `states` と、2インスタンスの `verify` | 日常のレビューループ |
| 3 | ネイティブ検査器を判定者にし、z3の証明とTLCを添える | 形式検証 |
| 4 | 互換性契約と、2回のメジャーリリース | 構文・判定・名前の安定性 |
| 5 | `codegen` と `check --code` でモデルをコードへ延ばす | 実装との接続 |
| 6 | 出力の種類ごとのfail-closed | 生成系サブコマンド |
| 7 | nullと一意性と削除の意味をSQLにそろえる | 判定の意味 |
| 8 | 保証を命題と証拠で書き出し、読みを実行時の検査に置き換える | 判定の信頼性 |

選んだ基準は、振る舞いを広く決めているものと、誤った安心を生む危険が大きいものです。1から3は検証結果の意味を決めます。4は利用者が背負う移行コストを決めます。5と6はツールが何を出し、何を止めるかを決めます。7は、検証の結果がデータベースや生成コードと同じことを言っているかを決めます。8は、その判定が何に支えられているかを、利用者が確かめられるかを決めます。8はmainで新しく取り上げました。

v1.x版で扱った「Stage 0–7を1つの仕様から生成する」判断は外しました。順序は `crates/rdra-ish-core/src/refinement/order.rs` の `ORDER` 1つに保たれ、2026-11-21の判断でも10段のまま据え置かれています（`docs/vision.md`）。評価を変える材料がないためです。

## 1. 1つのテキストモデルと1つの遷移系

### 仕組み

モデルの正は `.rdra` のテキストです。要素は `actor` や `usecase` のような宣言で、要素間の関係は `performs(Customer, BucOrder)` のような述語で書きます。図は正ではありません。`diagram` はMermaidテキストを出し、図から事実を読み戻せるよう `docs/cli-reference.md` の「Encoding contract」が書式を定めます。`crates/rdra-ish-cli/tests/diagram_contract.rs` がそれを全サンプルで検査します。

ライフサイクルは、同じモデルから1つの遷移系 `TransitionSystem`（`crates/rdra-ish-core/src/lifecycle/`）として組み立てます。mainでこれを読むものは次のとおりです（`docs/vision.md`、`docs/state-derivation.md`、`docs/codegen.md`）。

| 読み手 | 読み方 |
|---|---|
| `states` / `check` | 1インスタンスでBFS |
| `verify` | 2インスタンスでネイティブ検査器が探索して判定 |
| `verify`（既定。`--no-prove` で止める） | z3の式に符号化して帰納法で証明 |
| `export --kind tla`、`verify --with-tlc` | TLA+に印字してTLCが探索 |
| `codegen` | TypeScript / Rust / Goの型と遷移関数に印字 |
| `codegen --lang rust --verus`（実験的） | Verusの仕様と証明に印字 |
| 言語サーバー | 編集のたびに `check` の探索を1インスタンスで回す |
| `diagram --kind state` | 到達状態を図に描く |

`docs/state-derivation.md` は「No second reading of the model exists, so the engines cannot disagree on what a use case does.」と書いています。`docs/vision.md` も、TLA+の出力器は遷移系を印字するだけだと書いています。出力器 `crates/rdra-ish-emit/src/tla/mod.rs` の冒頭も、mainで「It reads the system and nothing else」のままです。

### 理由

`docs/vision.md` は、RDRAが要件・論理データ・設計を別の工程に置いていることを確認したうえで、rdra-ishはそれを1つのモデルで扱うと書いています。名前の "ish" はその選択だという説明です。

| 層 | 正の出典 | ツールが保証すること |
|---|---|---|
| 要件 | RDRA 3.0 | RDRAの規則が要求する接続がそろい、未定義・未接続がない |
| 論理データ | 著者のRDRASpecの対応規則 | DBML / SQL DDL / JSON Schema / OpenAPIを生成できる正規化された関係モデル |
| ライフサイクル | rdra-ish | 有界の範囲で、制約を破る到達状態がなく、宣言した状態に到達できる |

`docs/vision.md` は、ドメインコードも範囲に入れています。物理設計はSQL DDLまでで、そこから先は範囲外です。

### 評価

テキストを正にしたことで、差分レビューと型検査と生成物の再生成が素直に成り立ちます。RDRAが重視する「つながっていない要素を見つける」作業とテキストDSLは相性がよいと考えます。

遷移系を1つにした判断は、mainでも最も効いている判断だと考えます。読み手はさらに増えました。z3の証明が既定の `verify` に入り、Verusの出力と言語サーバーの検査も同じ遷移系を読みます。どれも同じ遷移系を読むので、図・表・検証・コードの食い違いは構造的に起きません。読み手が増えるほど、この判断の価値は上がります。

代償は3つあります。

1つ目は、図の空間配置を捨てたことです。互換性契約はレンダラの配置を対象外と明記しています（`docs/compatibility.md`）。業務担当者と同じ図を囲んで話す使い方には向かないと考えます。

2つ目は、RDRAとのずれです。`docs/rdra-ish-interpretation.md` はBUC・業務フロー・UCをRDRAとは違う責務で読むと明言し、`docs/vision.md` の表もRDRA 3.0の要素ごとに対応を書いています。差分が文書化されている点は評価できますが、RDRA準拠のツールとしては扱えないと考えます。

3つ目は、解釈の誤りがすべての読み手に同時に効くことです。mainでは、プロジェクト自身がこれを最大の残存リスクの1つに挙げています。判断3と判断8で扱います。

## 2. 有界の check / states と verify

### 仕組み

`check` と `states` は、遷移系を幅優先探索（BFS）で網羅します。不変条件やエンティティビューごとに、その対象が読む変数だけを集めた「cone of influence」を作り、coneごとに探索します。境界は次のとおりです（`docs/cli-reference.md`）。coneが判定を保つ理由は [coneと縮約](/projects/rdra-ish/theory/cones/) にあります。

| 項目 | `check` / `states` | `verify` |
|---|---|---|
| エンティティあたりのインスタンス数 | 1（`--instance-count`） | 2 |
| エンティティごとのインスタンス数 | `--instances <Entity>=<n>` | 同左 |
| Int / Money / Date などの値域 | `0..5`（`--int-range-max`） | 同左 |
| coneあたりの状態数の上限 | なし（`--max-states` で指定） | 同左 |
| メモリの上限 | 4GiB（`--memory`） | 16GiB |
| 時間性質 | 評価しない（`note:` を出す） | すべての形を評価 |
| 任意の行数での証明 | しない | 状態の規則をz3で証明する（z3がなければ飛ばす） |

上限は状態数ではなく、メモリで止まります。上限に達したconeは結果を部分的なまま通しません。`check` では `MemoryCapReached_<E>` などのerrorになり、`verify` では `not decided` になります。最終行には境界が入ります。mainの `verify` は、証明した規則の数も最終行に足します（`docs/formal-verification.md`）。

```
OK: no errors within 1 instance per entity, Int 0..5
OK: no errors within 2 instances per entity, Int 0..5; 2 of 2 rules proved for any number of rows, in the whole model
```

1インスタンスで見えないものを補う検査も入っています。

| 検査 | 何を知らせるか | 重大度 |
|---|---|---|
| `Vacuous_<name>` | 規則が対象とする行が存在しない、ガードが一度も成り立たない、などで規則が何も言っていない | warning |
| `UnjoinedWrite_<UseCase>_<A>_<B>` | 1つのUCが、書かないエンティティを介してだけつながる2つのエンティティを書く。1インスタンスでは別の行を書く実行が見えない | warning |
| `multi-rule-unscoped`（lint） | 複数エンティティの規則に `.along(...)` がない。1インスタンスでは組み合わせが1つしか見えない | warning |
| `UnwrittenConstrainedVar_<E>_<column>` | どのUCも書かない列を規則が読む | warning |

mainの `verify` は、さらに境界の外を1段見ます。証明が残した規則のうち、BFSが通したものを、そのcone上でインスタンスを1つ増やして、さらに2つ増やして調べ直します（`docs/formal-verification.md` の「Escalation past the bound」）。そこで見つかった反例はerrorになり、`--deny-unproved` がなくても実行を失敗させます。

### 理由

`docs/vision.md` は、TLAPSによる無限の証明を範囲外とし、「Verification is bounded model checking by rdra-ish's own checker, and the bounds are part of every result」と書いています。`check` の既定を1インスタンスにした理由そのものは、記録には見当たりません。日常のループに置く `check` を軽く保つための判断だと推測しますが、これは推測です。

### 評価

境界を結果の一部として印字する設計と、上限到達を通さない設計は誠実です。状態数の上限をメモリの上限に替えたことで、マシンの性能ではなくモデルの大きさで止まるようになりました。`docs/compatibility.md` は、coneのバイト数の数え方がどのマシンでも同じだと書いています。

`verify` の「OK」が保証する範囲は、mainでさらに広がったと考えます。最終行が、証明した規則の数と、その証明が成り立つ範囲を書くようになりました。証明できなかった規則は、境界を2段まで広げて調べ直されます。「2インスタンスでは通るが3インスタンスで壊れる」規則を、利用者が `--instance-count` を上げなくても捕まえる経路ができました。

一方、`check` の側の穴は、v3.0.0の評価のまま2つ残っています。

1つ目は `Unique_*` です。1インスタンスには行が2つないので、`Unique_*` には満たすべき前提がなく、`Vacuous_` も出ません。mainの `docs/state-derivation.md` も「`Unique_*` needs two rows of the child, so it has no premise at one instance per entity.」と書いています。テスト `at_one_slot_the_rule_holds_without_a_vacuity_warning`（`crates/rdra-ish-core/src/lifecycle/tests/unique_sets.rs`）が、この振る舞いをmainでも意図として固定しています。`one_to_one_shared.rdra` は今も `check` を通り、`verify` で失敗します（`docs/formal-verification.md` のサンプル表）。mainでは、この1インスタンスの検査が言語サーバーにも入りました（`docs/design/lsp-lifecycle-check.md`）。規則ごとのコードレンズは `ok`・`violated`・`not decided` を出し、診断の出所は `rdra-ish check (1 instance)` です。出所に境界が入るのは誠実です。それでも、エディタに並ぶ `ok` は `OK:` 行より目に入りやすいので、この穴の重みは少し増えたと考えます。

2つ目は、どれもwarningだという点です。`check` は終了コード0で終わり得ます。warningをerrorにするのは契約上の破壊的変更なので、この重大度は簡単には変えられません。探索中のモデルでwarningを許す方針（[段階的モデリング](/projects/rdra-ish/incremental-modeling/)）とも噛み合っています。それでも、`OK:` 行だけを見る利用者には空虚さが伝わりません。

## 3. ネイティブ検査器を判定者にし、z3の証明とTLCを添える

### 仕組み

`verify` は、すべての検査を自前の検査器で判定し、JVMを起動しません。不変条件、`after` アサーション、`always` / `eventually` / `leads_to` / `stable` / `unchanged` / `precedes` / `can_reach` の各性質を、BFSが作ったグラフの上で判定します（`docs/formal-verification.md`）。v2.xまではTLCが不変条件と時間性質を判定していたので、v3.0.0でこの判断は逆向きになりました。

mainでは、z3の証明が既定になりました。v3.0.0で `--prove` を付けたときだけ動いた証明が、すべての `verify` で動きます（`CHANGELOG.md` の `Unreleased`）。

| エンジン | いつ動くか | 役割 |
|---|---|---|
| ネイティブ検査器 | 常に | すべての判定 |
| z3 | `verify` の既定。`--no-prove` で止める | 状態の規則を、任意の行数と、モデルが組み立てられるすべての `--int-range-max` について帰納法で証明する |
| TLC | `verify --with-tlc` | 同じconeを検査し、判定が違えば `error[EngineDisagreement]` で失敗させる |

z3が見つからないとき、既定の `verify` は `note: z3 not found ...: the proof was skipped` を出し、証明なしの実行と同じ出力と終了コードで終わります。`--prove` か `--deny-unproved` を付けると、z3がないことはerrorになります。`docs/formal-verification.md` は、証明が必要なCIではどちらかを付けるよう書いています。証明は `proved:` 行に、成り立つ範囲を書きます（`for any number of rows and every --int-range-max from 4 to 254, in the whole model` など）。読み方は [z3による証明](/projects/rdra-ish/theory/z3/) にあります。

結果は `result:` 行（`ok` / `not decided` / `counterexample` / `tool_error`）で示します。TLCの判定を示す `tlc_result:` は `--with-tlc` のときだけ出ます。`--backend tlc` は `--with-tlc` の非推奨の綴りとして残り、警告を出します。

エンジン同士の一致は、テストで押さえます（`docs/engine-agreement.md`）。詳しくは [TLCとの照合](/projects/rdra-ish/theory/tlc-agreement/) にあります。

| 仕組み | 何を比べるか |
|---|---|
| 反例の自己検査 | mainでは、印字するすべてのトレースを実行のステップ関係で再生してから出す。失敗は `LiftFault_<check>`・`LassoFault`・`TraceFault_<finding>` のtool error |
| 敵対的コーパス（`crates/rdra-ish-cli/tests/engine_corpus/`、91件、`expect` 行218） | 各ケースのヘッダに、手で推論したエンジンごとの期待判定を書く。ネイティブとTLCの一致、z3とBFSの一致、ヘッダとの一致を検査 |
| サンプル比較（`engine_equivalence.rs`） | 全サンプルの全coneで、BFSとTLCの到達状態・辺・所見・判定を比べる |
| 縮約のランダム差分（`scripts/reduction-diff.py`） | ランダムなモデルで、縮約あり・なしの判定を比べる。mainでは45個の固定シードで `--with-tlc` 付き |
| ミュータント実行（`cargo mutants`） | 検査器のコードを変異させ、コーパスが落ちるかを見る。リリース前に手で起動 |
| Kani | 比較・メモリ見積もり・状態のパッキングなど、葉の関数を有界に証明 |

### 理由

ネイティブ検査器の記録上の理由は、JVMなしで同じ判定を出すことです。`docs/design/native-temporal-verification.md` は目的を「`verify` gives the verdicts it gives today, at the same bounds, with no external tool」と書き、TLCはテストの神託として残すとしています。判断は2026-11-23に記録されています（`docs/vision.md`）。

速度の差も記録されています。v3.0.0のリリース判定（`CHANGELOG.md` のv3.0.0の節）は、既定の境界での実測を次のように書いています。

| サンプル | ネイティブ | TLC |
|---|---|---|
| patent-ops | 1.0 s / 187 MB | 33.3 s / 795 MB |
| food-permit-ops | 2.7 s / 681 MB | 24.0 s / 1.61 GB |
| insurance-claim-ops | 5.9 s / 867 MB | 127.0 s / 2.10 GB |

証明を既定にした理由そのものは、`CHANGELOG.md` の `Unreleased` には書かれていません。費用は記録されています。`scripts/verify-samples.sh` の43回の実行で、合計は約40秒から85秒に増えます。証明書のキャッシュが温まっていれば59秒です（`RDRA_JOBS=1`）。z3のプロセスは1つあたり29から63 MBを使います。同じ節は、リリースビルドがオーバーフロー検査付きになり、`verify` が約10%遅くなったことも書いています。

### 評価

v1.x版では、TLCを2つ目の探索器にする構成を「探索の実装の正しさ」を押さえるものと評価しました。その保証は残っています。TLCは既定の実行から外れましたが、CIではTLCとネイティブを比べ続けています。`docs/design/native-temporal-verification.md` によれば、CIで `--with-tlc` が回るのは `scripts/tlc-roots.txt` の5つのルートと、フラグ付きのヘッダ行です。ほかのルートは `engine_equivalence` が状態グラフで比べます。ランダム差分は、リリースゲートが書く `0:2000` のシードではなく、45個の固定シードで回ります。

v3.0.0の評価は、CIがすべてのサンプルを `--with-tlc` で回すかのように書いていました。mainの文書に照らすと、これは言い過ぎでした。ここで直します。

得たものは3つあると考えます。

1つ目は、反例の扱いです。ネイティブの反例は出す前に自分で再生されるので、誤った反例は利用者に届きません。mainでは、再生の対象が性質の反例から、デッドロックや `states` の証人まで、印字するすべてのトレースに広がりました（`CHANGELOG.md` の `Unreleased` の「Fixed」）。神託が必要なのは `ok` だけ、という構図がさらに徹底されたと考えます。

2つ目は、z3という別の手法のエンジンが、既定の実行に入ったことです。BFSとTLCは同じ有界の状態グラフを探索しますが、z3は帰納法で行数の上限なしに証明します。v3.0.0の評価で「既定の `verify` では、どの判定にも2つ目の意見がつかない」と書いた点は、状態の規則について部分的に解消しました。

3つ目は、境界の外への1段です。証明できなかった規則を境界を広げて調べ直すので、z3は反例を出さないという弱点を、BFSが補う形になりました。

ただし、z3を既定にした効果には限りがあります。

- 証明が覆うのは状態の規則だけです（[主張の一覧](/projects/rdra-ish/theory/claims/) のB18）。`after` アサーションと時間性質には、既定の実行で2つ目の意見がつきません
- z3がないと、証明は `note:` を1行出して飛ばされ、終了コードは変わりません。証明が回ったと思い込む余地が残ります
- `docs/compatibility.md` は、証明が出す行とどの規則が証明されるかを、今も実験的としています
- 証明は判定を足すだけではありません。メモリの上限で止まったconeは、z3がすべての規則を証明すれば `ok` になります。誤った `proved` は誤った `ok` になり、実行中にそれを見る検査はありません（`docs/theory/README.md` の「Known limitations」のB16）
- mainでは、z3の証明が誤って `proved` を出していた不具合が、少なくとも3件直されました。Intの値を全部列挙した集合を偽と読んだ件（#425）、`present` の書き込みをガードが値域の上限で縛っていた件、値域の上端が折り返していた件（`DomainTooLarge`）です。直されたことは評価できますが、証明を既定にする時点で、この経路の誤りがまだ見つかっていた点は記録しておきます

失ったもの、あるいは弱くなったものもあります。

- 時間性質の判定は、v3.0.0で新しく書かれたコードです。公平性やlassoの扱いを、利用者の実行で毎回TLCと照合する仕組みはありません。mainでは、平の実行の活性の `ok` を、記録したグラフの上で受理条件に照らして確かめるようになりました（`docs/theory/README.md` の「What every run checks」）。ただし、この検査は探索と状態・辺・述語を共有し、インスタンス対称性の下の実行は対象外です
- TLCが終わらないconeには神託がありません。`VERIFY_FALLBACK` は、2インスタンスで300,000状態を超えるため1インスタンスでしか比べないconeの一覧で、mainでは25個です。うち13個は `oidc-auth` のものです
- v3.0.0のリリースゲートは、8項目のうち2項目を免除しました。ランダムなモデルでの一致（項目3）と、判定を直すコミットがない静かな期間（項目7）です。mainの `docs/design/native-temporal-verification.md` は、項目3が書かれたとおりには実行できないこと（`reduction-diff.py` に全モデルのモードがない）を認め、項目2・3・7の書き直しを提案しています。提案は持ち主の判断待ちです
- v3.0.0の「Known issues」にあったフェーズ4と5（#168）は、mainでもまだ開いています

総じて、独立性の中身は「毎回の実行で2つのエンジンが判定する」から「テストとCIで照合し続ける」に変わり、mainでは「状態の規則には毎回z3が添う」が加わったと考えます。利用者にとっての保証は、v3.0.0より少し持ち直しました。ただし、z3は遷移系をBFSと共有するので、組み立ての誤りに対しては独立していません。

### 解釈の誤りは全エンジンに効く

v1.x版で最大の構造的な弱点として挙げたのは、`.rdra` から遷移系を組み立てる段階の誤読です。z3も同じ遷移系から式を作ります。`docs/engine-agreement.md` は「the model builder feeds every engine, so one mistake in either moves every engine at once」と書いています。エンジンが3つになっても、組み立ての誤りに対する独立性は増えていません。

mainでは、プロジェクト自身がこの弱点を最上位に置いています。`docs/theory/README.md` の「Residual risks」は、2つの残存リスクの1つ目を「Common-mode faults」とし、ビルダー、coneの選択、性質のconeの段取り、縮約の商の表、TLA+の名前の対応を挙げています（[検証の理論の残存リスク](/projects/rdra-ish/theory/#残存リスク)）。

この弱点への手当ては3つあります。1つ目は、コーパスの期待判定を実行結果からではなく手の推論から書く規則です。2つ目は、その規則で実際に見つかった誤りの記録です。Intの `@default` が値域外のとき、すべてのエンジンが0から始めていた件（#180）と、EnumとBoolの `@default` が値の外のとき最初の値から始めていた件（#187）は、どちらも全エンジンが同じ誤りを共有していた例です。`docs/engine-agreement.md` の植え込みバグの表でも、6件のうち2件はヘッダの期待判定だけが検出しています。

3つ目は、mainの理論文書が挙げる参照インタプリタです。ビルダーを通さずに `SemanticModel` から遷移系を組み立て直し、ビルダーの出力と比べます（[主張の一覧](/projects/rdra-ish/theory/claims/) のI1）。ただし、対象は言語の部分集合で、20,000状態までです。パーサと `build_model` はビルダーと共有しています。

v1.x版の「評価を変える条件」は、独立した参照実装か仕様ベースのテストを求めていました。手で推論した期待判定を持つコーパスは後者に、参照インタプリタは前者に当たると考えます。どちらも部分的です。コーパスは91件の小さなモデルで、参照インタプリタは部分集合です。大きなモデルの解釈は、今もサンプルの `// expect` ヘッダと人のレビューに頼ります。条件は、v3.0.0の評価より一歩進んだものの、部分的に満たされた段階にとどまると考えます。

## 4. 互換性契約と2回のメジャーリリース

### 仕組み

`docs/compatibility.md` は、次のものをメジャーリリースまで保つと約束します。

- 構文：ロードできたモデルは、ロードでき続ける。廃止は非推奨期間を経てメジャーで行う
- 意味：同じモデル・同じ境界なら、`check` と `verify` は同じ終了コードと同じerror名の集合を返す。`not decided` はまだ判定がないので、minorで判定してよい
- 診断名、lintのルールID、`// expect` ヘッダの文法
- サブコマンドとフラグ、`verify` の既定（ネイティブ検査器）、終了コード、JSONのキーとCSVの列、`bounds:` / `result:` / `tlc_result:` 行
- Mermaid図の符号化
- `codegen --lang ts` が出すTypeScriptの型
- TLA+の不変条件名・性質名・変数名

mainでは、`--tlc-jobs`・`--tlc-workers` とそれぞれの環境変数、ツールのパニックを表す終了コード `101` が契約に加わりました。証明については、`--no-prove`・`--prove`・`--deny-unproved`・`--z3` の意味を保ち、証明が出す行を実験的とする書き方に変わりました。

契約はリリースだけを対象にします。`main` は早期チャネルで、リリースの間の変更はCHANGELOGの `Unreleased` に載ります。

廃止した構文は `crates/rdra-ish-syntax/src/removed.rs` の `LEGACY_FORMS` に1か所で登録されます。各行は非推奨（ロードでき、警告を出す）か削除（書き換え後の行を示すロードエラー）です（`docs/language-reference.md` の「Deprecated and removed forms」）。

### 理由

v1.0.0以後の破壊的変更と、その背景は次のとおりです（`CHANGELOG.md`）。

| 版 | 日付 | 主な破壊的変更 | 背景 |
|---|---|---|---|
| v2.0.0 | 2026-11-06 | `CrossForbidden_*` / `CrossInv_*` を `Multi*` に改名（#111）。イベントで起動するUCは、そのイベントの後にだけ走る（#112） | v1.0で凍結したイベント順序の過大近似が、偽の反例を出していた |
| v3.0.0 | 2026-11-26 | `verify` の判定者をネイティブ検査器に。nullable列・削除・一意性などで判定が変わる。`export --kind typescript-states` を削除 | TLCなしで回す。判定をSQLの意味にそろえる |

間のv2.1.0、v2.2.0、v2.3.0は、どれもCHANGELOGの冒頭で「Upgrading ... needs no change」と書いています。

### 評価

契約は、リリースの範囲では形の上で守られたと考えます。判定や名前を変える変更はすべてメジャーで出ています。v2.0.0とv3.0.0のCHANGELOGには、どちらも「Upgrading from」の節があり、変更ごとに影響と移行の書き換えを表で示しています。v3.0.0では、判定が変わる変更を「Models whose verdict can change」の表にまとめ、どのサンプルも判定が変わらないことまで書いています。破壊的変更の伝え方としては手厚いと考えます。

v1.x版で挙げた「早い凍結」のリスクは、違反ではなくメジャーの頻度として表に出ました。v1.0.0は2026-11-03、v2.0.0は3日後、v3.0.0はその20日後です。契約はメジャーを出すことで守られたので、利用者は約1か月で2回の移行を背負ったことになります。

mainの `Unreleased` には、契約との関係を見ておくべき変更があります。`Unreleased` には `### Breaking` の節がなく、証明の既定化は「Changed」の節に「behavior change」として載っています。一方で、既定の `verify` は、境界の外の反例で失敗するようになりました。`CHANGELOG.md` は「a `--prove` run of such a model that passed before now exits 1」と書き、該当するサンプルはないとしています。`docs/compatibility.md` の「意味」の項と「Bounds」の節は、印字した境界の中で結果が変わることを破壊的変更としています。これに対し、同じ文書の対象外の項は、どの規則が証明されるかがどのリリースでも変わり得るとしています。証明できなかった規則は境界の外で調べ直され、実行を失敗させ得ます。つまり、この対象外の項は、間接に終了コードへ効きます。2つの項の関係は、契約の文面では整理されていないと考えます。v3.0.0で `verify` を通ったモデルが、次のリリースで終了コード1になり得る、という事実は記録しておきます。これをminorで出してよい変更と読むかは、筆者には判断がつきません。

非推奨の経路は、フラグでは使われました。`--backend tlc` がv3.0.0で非推奨になり、次のメジャーで消えます。`docs/compatibility.md` の「Deprecation」の節は、構文の形を「minorで非推奨にし、メジャーで削除する」と書いています。`--backend tlc` は、メジャーで非推奨になったので、この節の手順そのものではありません。構文の側では、mainの `docs/language-reference.md` が「No form is deprecated now」と書いています。`LEGACY_FORMS` の21行も、mainですべて削除の行のままです。構文の非推奨サイクルは、仕組みとしては実装済みのまま、実運用では未検証だと考えます。

`export --kind typescript-states` と `states --format typescript` は、非推奨期間なしにv3.0.0で消えました。メジャーでの削除なので契約違反ではありません。削除したkindは書き換え先を示す使用法エラー（終了コード2）になります。黙って消すより安全な扱いだと考えます。

契約の範囲は、v1.x版の評価よりさらに広がりました。`codegen --lang ts` の型、`result:` 行、`verify` の既定、TLCのスケジューリングのフラグが加わっています。`docs/compatibility.md` は「A minor release does not add a rule form that narrows」と書いており、TypeScriptの型の契約が言語の拡張まで縛っています。一方で、`not decided` を「まだ判定がない」と定義し、minorで判定してよいとしました。証明の出力も実験的として外に出しています。範囲を広げつつ、変わる部分を外に出す工夫は続いていると考えます。

## 5. codegen と check --code でモデルをコードへ延ばす

### 仕組み

`codegen --lang ts|rust|go` は、モデルをドメインコードとして印字します（`docs/codegen.md`、`docs/design/algebraic-codegen.md`）。値の集合、id型、エンティティの行型、状態ごとの型の和、UCごとの遷移関数、規則の検査、ディスパッチャを1つのコンパイル単位に出します。遷移関数は、`check` と `verify` が探索する遷移系から作ります。型で強制できない検証の前提は、名前付きの義務（`Unique_Order_note` など）としてヘッダに並びます。

`check --code[=fresh|build|run]` は、サービスのコードがモデルの要求を満たすかを確かめます（`docs/design/code-check.md`）。

| レベル | 何をするか |
|---|---|
| `fresh` | 生成済みのファイルが、今のモデルから生成したものと同じか比べる |
| `build` | UCごとの契約を実装しているかを、言語のコンパイラでプローブを通して確かめ、エラーをUCに対応づける |
| `run` | 適合テストのハーネスで、サービスを生成したトレースに沿って動かす |

義務には持ち主が要ります。コードの `rdra: obligation <name>` 行か、`rdra.toml` の `[code.obligations]` で宣言します。

mainでは、この経路が大きく育ちました（`CHANGELOG.md` の `Unreleased`）。どれも実験的です。

| 追加・変更 | 内容 |
|---|---|
| 関数の出ないUCの解消（#335） | サンプルの19個のUCすべてに関数が出る |
| 結果の書き込みのデータ化 | 各結果が書く行・実行マーク・イベントを `Writes` として列挙し、コミットの補助関数を出す |
| `codegen --adapter` | 生成コードの型を使わない、ブラックボックスのモデルアダプタを出す |
| `codegen --lang rust --verus` | Verusのクレートを出し、任意の行数でモデルが規則を保つことと、ポートがモデルの1ステップどおりにストアを動かすことを証明する |
| 未実装ポート | 未完成のサービスでもビルドでき、`check --code=run` が未実装のUCを数える |
| 適合トレースの拡充 | モデルが拒むすべての呼び出しを試し、拒否の種類まで照合する。トレースの形式は4、次いで5に上がった |
| `check --code=run` の自己検査 | 変異させたトレースで実行コマンドを回し直し、生き残ると `CodeMutantSurvived` |
| 被覆の明示 | `run` が、トレースの境界と、試した拒否、比べない部分、仮定H1からH5を書く。通過は「bounded conformance」と呼び、等価とは呼ばない |
| エラーの型（実験的出力の破壊的変更） | すべての `<UseCase>Error` に `NotFound` と `StoreFailed` が加わる |

生成物の正しさは次のテストが押さえます（`docs/codegen.md` の「How the generator is tested」）。

| テスト | 内容 |
|---|---|
| `crates/rdra-ish-cli/tests/codegen_builds.rs` | 全サンプルの出力が `tsc --strict`、`clippy-driver -D warnings -D missing_docs`、`go vet`、`gofmt -l` を通る |
| `crates/rdra-ish-cli/tests/codegen_equivalence.rs` | 中間表現が、`check` が通る全サンプルでBFSと同じことをする |
| `crates/rdra-ish-cli/tests/codegen_differential.rs` | 印字したRustとGoを、BFSのすべての手で実行して比べる |
| `crates/rdra-ish-cli/tests/codegen_conformance.rs` ほか | 参照サービスが通り、植え込み不良がハーネスと `check --code` で落ちる |
| `crates/rdra-ish-cli/tests/codegen_contract.rs` | TypeScriptの型の契約を固定する |
| `crates/rdra-ish-cli/tests/codegen_verus.rs` | Verusのクレートが検証を通り、壊した規則やコアを拒み、BFSと一致する |

契約が覆うのは、今もTypeScriptの型だけです。

### 理由

2026-11-07の判断（`docs/vision.md`）は、`check` と `verify` が検証したものに適合し、ビルドが依存できるドメインコードを出すと決めています。`docs/design/algebraic-codegen.md` は、それ以前の `typescript-states` が到達パターンから型を作っていたため、Intの値が有界の値域の型になる、モデルの抜けがコードの規則になる、といった問題を記録しています。

`check --code` は、rdra-ishが利用者のコードを読まないという前提を保ったまま、モデルとコードのずれを検出するためのものです（`docs/design/code-check.md`）。検査はコンパイラに任せます。mainでの追加の多くは、生成物を使って作った3つのサービスの経験から来ています。`CHANGELOG.md` は、結果の書き込みを手で書いた量を、Rustで約160行、TypeScriptで550行と記録しています。

### 評価

モデルとコードの間のずれは、要件モデルのツールが最も手を出しにくい部分です。同じ遷移系から関数を印字し、BFSの辺と突き合わせ、コンパイラで実装の有無を確かめる構成は、判断1の「1つの読み方」をコードまで延ばしたものだと考えます。rdra-ishがコードをパースしない方針も、保守の範囲を限る点で妥当です。

mainで解消した点があります。v3.0.0の評価で挙げた「サンプルの19個のUCはまだ関数が出ない」は、#335で解消しました。適合ハーネスの「通った」が何を意味するかも、はっきりしました。通過を「bounded conformance」と呼び、被覆を毎回書き、自己検査でハーネスが本当にトレースを読んだかまで確かめます。検査そのものを検査する設計は、判断3の反例の自己検査と同じ考え方で、筋がよいと考えます。

Verusの出力は、行数の上限なしにコードとモデルを結ぶ初めての経路です。ただし、Rustだけで、実験的で、`Enum`・`Bool`・キーの列などを使うモデルだけが対象です（`docs/design/verus.md`）。ストアは信頼する部分として残ります。

限界は、設計文書がはっきり書いています。`docs/design/code-check.md` の「What it cannot detect」は、宣言だけで何もしないコード、契約を迂回して直接ストアを書くコード、並行性、行が2つで初めて壊れる振る舞いなどを挙げています。適合ハーネスは1エンティティ1行の範囲で動くので、一意性は見えません。これは判断2の `Unique_*` と同じ形の穴で、mainでも残っています。印字したTypeScriptを辺の上で動かす差分テストも、まだありません（`docs/codegen.md`）。

門の高さのずれも残っていると考えます。`codegen` は `check` が拒むモデルを拒みますが、`check` は1インスタンスで回ります。2インスタンスの `verify` で失敗するモデルからも、`codegen` はコードを出します。mainの `docs/codegen.md` は、ヘッダが `check` の境界を印字し、その境界で見えない規則は `verify` で確かめるよう書いています。文書で明示した点は前進です。それでも、`verify` を通してから生成する運用は、利用者側で決める必要があります。

もう1つ、育ち方の速さに代償があると考えます。mainの `Unreleased` だけで、適合トレースの形式が2回上がり、`<UseCase>Error` に2つの場合が加わり、Goの `ConformancePort` の `Seed` と `Snapshot` の型が変わりました。出力は機能ごとに3%から15%ほど増えています。どれも契約の外なので、手続きとしては正当です。ただし、生成物の上にサービスを作る利用者は、minorのたびに追従を求められます。

TypeScriptの型だけを契約に入れた判断は、型が最も外から依存されやすい部分だという点で妥当です。ただし、判断4で見たとおり、その契約が言語の拡張を縛ります。実験的な機能の一部を早く契約に入れた代償だと考えます。

## 6. 出力の種類ごとのfail-closed

### 仕組み

生成系サブコマンドは2段の門を通ります。1段目はparse/resolveのerrorで、どの出力も書きません。2段目は、出力が読むものによって決まります。判定は `crates/rdra-ish-cli/src/lifecycle_gate.rs` にあり、`crates/rdra-ish-cli/tests/export_gate.rs` が全kindを `docs/cli-reference.md` の「Lifecycle errors」の表と突き合わせます。

| 出力 | 読むもの | ライフサイクルのerrorがあるとき |
|---|---|---|
| `list`、`csv`、ほかの `diagram`、ほかの `export` | 宣言とデータ層 | 探索せずに書く |
| `diagram --kind state` | 到達状態 | 拒む。errorがデッドロックだけなら図の中で示す |
| `export --kind tla` | 遷移系 | noteを出して書く。遷移系の構築errorでは拒む |
| `states` | 探索結果そのもの | `[error]` 行を含めて出し、終了コード1 |
| `codegen` | 遷移系と探索結果 | `check` のerrorがあれば拒む（`--allow-failing` で生成） |

`diagram` と `export` の分類は、出力器が実装するトレイトで決まります。`Emitter` はモデルとビューだけを受け取ります。到達状態を読む出力器は `StatesEmitter` を実装し、門を通った後にしか作られない探索結果を受け取ります（`crates/rdra-ish-emit/src/lib.rs`）。mainのソースでも、`StatesEmitter` を実装する出力器は状態図（`crates/rdra-ish-emit/src/mermaid/state.rs`）だけです。

mainでは、ツール自身の誤りを判定と取り違えない仕組みが増えました（`CHANGELOG.md` の `Unreleased`、`docs/theory/README.md` の「What every run checks」）。

| 仕組み | 内容 |
|---|---|
| パニックの扱い | 最初の行に `tool error: rdra-ish <version> panicked at ...` と、モデルについての所見ではないことを書く。終了コードは `101` |
| オーバーフロー検査 | リリースビルドもオーバーフロー検査付きでビルドする。整数が折り返して誤った判定になる代わりに、パニックで止まる |
| 値域と状態幅の拒否 | 1つの状態に収まらない列の値域を `DomainTooLarge`、パック幅を超える状態を `StateTooWide` として、エンジンが動く前に拒む |
| TLA+のモジュールの自己検査 | 印字するモジュールの名前の対応が単射で全域か、縮約の表が読み戻せるかを確かめる。失敗したモジュールは `ASSUME FALSE` になり、`export` は何も書かない |

### 理由

2026-10-28の判断（`docs/vision.md`）は、ライフサイクルを印字しない出力はライフサイクルを待たず、探索もしないと決めています。v3.0.0では、宣言だけを読む出力は探索そのものを省き、ライフサイクルのerrorについてのnoteも出さなくなりました（#285）。

### 評価

原則は明快です。「その出力が誤ったライフサイクルを印字するなら止める。読まないなら止めないし、探索もしない」。誤った状態図やコードが実装に流れ込むのを防ぎつつ、ライフサイクルが書きかけでもデータ設計のレビューを進められます。段階的モデリングとよく噛み合う判断だと考えます。

分類が型に結び付いているので、人が誤分類する余地は小さいと考えます。`export_gate.rs` が表と実装の一致を検査するので、文書と挙動もずれません。

宣言だけを読む出力からnoteを消した点は、両面があると考えます。探索の費用を払わず、出力と無関係な情報も出さないので、筋は通っています。一方で、`export --kind sql` だけを回す利用者は、ライフサイクルのerrorに気づく機会が1つ減ります。`check` をCIで回す前提なら問題にならないと考えます。

`codegen` の門は、ライフサイクルのerrorだけでなく `check` のすべてのerrorで止まります。コードはビルドが依存するものなので、ほかの出力より厳しい門にした判断は妥当です。門の高さの問題は判断5で扱いました。

mainで増えた仕組みは、fail-closedの考え方を、出力の種類からツール自身の故障にまで広げたものだと考えます。特に `DomainTooLarge` は、実際の誤りを止めています。`CHANGELOG.md` によれば、それ以前は値域の上端の値が最初の値へ折り返し、モデルの破る規則が `ok` と出ていました。v3.0.0では、既定の境界のEnumでも起き得た誤りです。これを判定の前に拒む変更は、この判断の延長として正しいと考えます。代償は、オーバーフロー検査による約10%の速度です。誤った判定を防ぐ費用としては安いと考えます。

`export --kind tla` の `StateModel_<E>` specは、TLC単体でもwitnessの欠如とデッドロックを検査できます。ただし、`Deadlock_` 不変条件のpassはデッドロックがないことを示しません。`docs/theory/README.md` の「Known limitations」も、TLCのデッドロック検査は片側だけだと書いています（T6）。この非対称は設計上の限界のまま残っています。それでも、`verify` がTLCを必要としなくなったので、TLCを手で回す利用者は減り、この限界の重みは小さくなったと考えます。mainでは、`--with-tlc` の下で、縮約しないconeの状態モデルのモジュールについてTLCとBFSの状態数を突き合わせるようになりました。

## 7. nullと一意性と削除の意味をSQLにそろえる

### 仕組み

v2.3.0で `export --kind sql` が入り、エンティティ単位の規則を名前付きの `CHECK` 制約として書くようになりました。v3.0.0では、ライフサイクルの判定をSQLの意味にそろえる変更が入りました（`CHANGELOG.md`、`docs/language-reference.md` の「Null」）。

| 変更 | 内容 |
|---|---|
| nullable EnumとBool（#359） | `@null` の列はnullを値として持ち、既定値がなければnullで始まる |
| nullable列同士の比較（#355） | 2つのnullは等しくない。SQLと同じ |
| 論理 `@derived` の `in`（#374） | 列がnullの間は、真でも偽でもない |
| 削除（#199） | `.on_delete` が `restrict`・`no_action`・未指定のキーで子が親を指す間、親の `deletes` は待つ |
| 一意の列の組（#222） | `@unique`、`@unique(a, b)`、N:Mの中間テーブルのキーを `Unique_<Entity>_<columns>` として検査する。nullの行はどの行とも一致しない |

コーパスには、`safety_null_*`、`safety_delete_restrict`、`safety_unique_sets` などのケースがあり、これらの意味をネイティブ・TLC・z3で固定しています（`docs/engine-agreement.md`）。

mainでは、そろえていない部分を利用者に知らせる診断が加わりました（`CHANGELOG.md` の `Unreleased`、`docs/state-derivation.md`）。

| 診断 | 何を知らせるか | 重大度 |
|---|---|---|
| `DeleteLeavesChildren` | `cascade` の親を消して子を消さない。SQLの `ON DELETE CASCADE` は子を消すが、検証のモデルは子を残す | warning（v3.0.0ではinfo） |
| `DeleteLeavesChildKeys` | `set_null` か `set_default` の親を消して、子を消さず、キーも動かさない | warning |
| `negated-order-admits-null`（lint） | nullable列の順序比較を `not` で包むと、列がnullの間は成り立つ | warning |
| `GoalMetByDelete_*` | `eventually` / `leads_to` の目標が、消えた行の基底値で満たされる | info |

あわせて、目標に存在する行を求める `.present()` が加わり、`docs/language-reference.md` の「Null」の節に、nullに対するすべての比較演算子の真理値表が載りました。表はテストがビルダーと評価器を通して計算し、文書と比べます。

### 理由

`docs/vision.md` の規則2は、削除の待ちを「as the database would」と書いています。`docs/language-reference.md` は、nullで始まることを「as the SQL row does」、2つのnullが等しくないことを「as in SQL」と書いています。`docs/design/code-check.md` は、nullable Enumでnullを値とするかが生成する型を変えるので、コードの契約を固める前に決めたと記録しています。

mainの `docs/theory/README.md` は、これらを「Readings a modeler should know」としてまとめています。比較のnullは2値で読む、検証は参照動作を実行しない、活性の目標は行の存在にかかわらず読む、などです。それぞれを、言語リファレンスに書かれテストで固定された決定として扱い、その読み方の下ではどの判定も書かれたモデルに対して正しい、と位置づけています。定義は [意味論と記法](/projects/rdra-ish/theory/semantics/) にあります。

### 評価

モデル、SQLのスキーマ、生成コードの3つが、nullと一意性と削除について同じ意味を持つようになりました。検証の「OK」が、データベースが実際に許す状態について言っていることになります。判断1の「1つの読み方」を、rdra-ishの外にあるデータベースの意味にまで合わせた判断だと考えます。z3の証明が、SQLのスキーマが強制しない規則に印を付ける点も、この整合の延長として有用です。

代償は2つあります。

1つ目は、判定が変わる変更をメジャーで出す必要があったことです。判断4で見たメジャーの頻度の一因です。

2つ目は、そろえ方が部分的なことです。`.on_delete` は拒否としてだけ働き、`cascade`・`set_null`・`set_default` は実行されません（`docs/formal-verification.md` の「Approximations and limitations」）。一意の列の組のうち、`String` のように値の変数を持たない列を含むものは検査されず、データベースに任されます。`docs/state-derivation.md` は、`samples/` の `@unique` 列の大半が `String` だと書いています。

mainは、この2つ目の代償を、意味を変えずに知らせる方向で手当てしました。参照動作のずれは、どちらもwarningになりました。nullの読み違えはlintが指摘し、削除で満たされる目標はinfoが知らせます。どれもwarningかinfoなので、契約の上ではminorで足せます。v3.0.0の評価で「そろえた範囲では誠実」と書いた点が、そろえていない範囲にも広がったと考えます。

ただし、ずれそのものは残っています。`docs/theory/README.md` の「Known limitations」は、I3として「a rule over the children can be `ok` in the model and broken against that database」と書き、参照動作を実行するかは持ち主の判断だとしています。I2として、`negated-order-admits-null` を出すサンプルやコーパスのケースがまだないことを書いています。`Unique_<Entity>_<columns>` が実際のモデルで効く場面が限られる点も、変わっていないと考えます。

## 8. 保証を命題と証拠で書き出し、読みを実行時の検査に置き換える

<!-- derived-from ./theory/index.md -->

### 仕組み

mainの `docs/theory/` は、検証器が何を判定し、それが何に支えられているかを、形式手法の読者向けに書いた文書群です（`docs/theory/README.md`）。日本語の解説は [検証の理論](/projects/rdra-ish/theory/) にあります。

| 文書 | 内容 |
|---|---|
| `semantics.md` | モデルが表す遷移系 `T_β(M)` を、モデルのテキストから定義する（D1〜D25） |
| `claims.md` | ツールと文書が主張する保証を1行ずつ並べ、証拠の種類・コード・テスト・未解決の穴を書く |
| `cones.md`、`z3.md`、`native.md`、`tlc-agreement.md` | それぞれの主張を命題として述べ、証明か証明の素描か、その代わりになる検査を示す |

`claims.md` は、保証ごとに、紙の証明、機械的な検査、差分テスト、実行時の検査、仮定のどれに頼るかを区別します。一部の主張は、`proofs/lean/` のLean 4の証明が証拠です（`docs/theory/README.md` の「Trust base and assumptions」）。

文書と挙動のずれも構造で押さえています。`docs/theory/README.md` の「Known limitations」は、`claims.md` で未解決の穴を持つ行ごとに1項目を置きます。`crates/rdra-ish-cli/tests/export_gate.rs` は、穴のある行に項目がないとき、または穴のない行に項目があるときに失敗します。

`docs/design/certificate-plan.md` は、その先の計画です。理論文書が「コードを読んで確かめた」としている事実を36の接続点に整理し、実行時の検査、Leanで検証した検査器、独立な導出との比較、Kaniの証明、証人の出力のどれに置き換えるかを決めています。計画は研究段階の草稿で、`6042d0af` の時点で書かれています。いくつかの段階は実装と計測が済んでいます。たとえば、反例の保証、縮約の前提の検査、coneの検査、ステップの書き込みの検査、平の実行の活性の証人です。

mainで、毎回の実行が確かめることは次のとおりです（`docs/theory/README.md` の「What every run checks」から抜粋）。

- 印字するすべての反例を、その実行のステップ関係で再生する
- 組み立てた各アクションが、Leanの証明が前提とする形に収まるかを確かめる
- coneが、定理A1とA2が求める性質を満たすかを確かめ、満たさなければ全体の遷移系で判定する
- ステップが、アクションの書き込み集合の外に書かないかを確かめる
- 縮約の分割が安定かを確かめ、失敗すれば別の分割か縮約なしに戻す
- 平の実行の活性の `ok` を、記録したグラフの上で受理条件に照らして確かめる
- 矛盾した前提からは何も証明しない

### 理由

`docs/theory/README.md` は、各文書が用語を定義してから使い、保証を命題として述べ、その1つずつが何に頼るかを書くと説明しています。証明書の計画は、何も見ていないところで誤った判定が出る経路を、既定の実行で危険が大きく、安く置き換えられる順に潰すと書いています（`docs/design/certificate-plan.md` の「Why this order」）。状態や辺ごとに働く検査は、計測した命令数の増加が1%以下であることを、段階の終了条件にしています。

### 評価

この判断は、mainで最も大きな前進だと考えます。理由は3つあります。

1つ目は、判断3で挙げた弱点を、プロジェクト自身が順位を付けて書いたことです。理論文書は、ほかより重い残存リスクを2つ挙げています。1つ目は判断3で扱った共通モードの故障です。2つ目は、`ok` と `proved` を実行中に確かめる検査がないことです（[残存リスク](/projects/rdra-ish/theory/#残存リスク)）。外から評価する側が推測で書いていた弱点が、引用できる形になりました。

2つ目は、未解決の穴の一覧をテストで文書に結び付けたことです。穴を足したのに一覧を直さない、という誤りがCIで落ちます。注意書きを書き足すのではなく、構造で誤りを防ぐ設計だと考えます。

3つ目は、「コードを読めば分かる」を実行時の検査に置き換える方向を選んだことです。紙の証明とLeanの証明は、コードがその前提を満たすときにだけ効きます。前提をコードが満たすかを毎回の実行で確かめれば、証明とコードの間の隙間が狭まります。計測を終了条件にしたので、この検査が日常の速度を壊すこともないと考えます。

代償と限界もあります。

- 信頼基盤は広くなりました。z3、TLCとJVM、ビルダー、紙の素描、Lean 4.36.0とそのカーネル、Kaniとrustcが並びます（[信頼基盤と仮定](/projects/rdra-ish/theory/#信頼基盤と仮定)）。証拠の種類が増えた分、利用者が読むべき前提も増えています
- Leanの証明は、コードではなくモデルについての証明です。`docs/theory/README.md` の「Known limitations」のA8は、Leanのモデルが畳み込み1つにつき1ビットで、ノードの畳み込みを持たないことと、入れ子の縮約が素描にとどまることを書いています
- 実行時の検査は、検査する側と同じ部品を読むことがあります。coneの検査は、アクションの読み書き集合をconeの選択と共有するので、その集合の誤りは共通モードのまま残ります（残存リスク1）
- 安全性の `ok` と `proved` には、今も実行時の検査がありません（残存リスク2）
- 文書の間に小さな食い違いがあります。証明書の計画の「What stays trusted at the end」は、リリースビルドが整数を黙って折り返すと書いています。`CHANGELOG.md` と `docs/theory/README.md` は、リリースビルドもオーバーフロー検査付きだと書いています。計画は草稿で、`docs/theory/README.md` は理論文書がノートと食い違えば理論文書を正とすると書いています

もう1つ、プロセスの弱さが文書から読み取れます。`docs/theory/README.md` の「Known limitations」の「Process」は、どのCIの検査も必須ではないと書いています。mainにはブランチ保護がなく、緑のCIでマージするのは慣習です。ランダム差分やミュータント実行が必須の検査でないことも、同じ項目に並んでいます。判断3で見たTLCとの照合の多くはCIに頼るので、この弱さはそこに直接効くと考えます。

## 総合評価

mainのrdra-ishは、要件モデル・論理データ・ライフサイクル・ドメインコードを1つのテキストモデルから導き、その上の検証結果の意味を厳しく管理しようとするツールです。最も強い判断は、遷移系を1つにして、検査器とコード生成器と言語サーバーにそれを読ませたことだと考えます。境界を毎回印字し、上限到達を判定にせず、自らの穴を一覧にして検査で文書に結び付ける姿勢は一貫しています。

v3.0.0からmainへの大きな変化は3つです。z3の証明が既定の `verify` に入ったこと、理論文書と証明書の計画で判定の支えを書き出したこと、実験的な `codegen` が実際のサービスに使える形へ育ったことです。証明の既定化で、状態の規則には毎回の実行で2つ目の意見が戻りました。理論文書で、プロジェクト自身が最大の残存リスクを引用できる形で書くようになりました。

最も弱いのは、今も `check` の「OK」が保証する範囲の伝え方です。`Unique_*` は1インスタンスで黙って成り立ち、その結果は言語サーバーにも出ます。`codegen` は `verify` を待たずにコードを出します。加えて、証明の既定化は2つのことを持ち込みました。z3がない環境では `note:` 1行だけで証明が飛ばされることと、境界の外の反例で終了コードが変わることです。

### 未解決のリスク

v3.0.0の評価で挙げたリスクを、mainで確かめ直した結果です。

| # | リスク | mainでの状態 |
|---|---|---|
| 1 | `check` のOKの過信 | 変わらない（`verify` 側は小さくなった） |
| 2 | 解釈の誤りが全エンジンを素通りする | 少し小さくなった |
| 3 | 早い凍結と広い契約 | 形を変えて残っている |
| 4 | TLCを手で回す経路の見落とし | 変わらない |
| 5 | 規模の天井が要件を削る | 少し小さくなったが残っている |
| 6 | ネイティブ検査器の `ok` に神託がない範囲 | 少し小さくなった |
| 7 | 生成コードと検証の間の隙間 | 一部解消、一部は残っている |
| 8 | 既定の証明への過信 | 新しいリスク |
| 9 | 必須でないCI | 新しく文書に現れたリスク |

1. **`check` のOKの過信**：`check` の側は変わっていません。`Unique_*` は1インスタンスで警告なしに成り立ち、どの警告も終了コードを変えません。言語サーバーが同じ1インスタンスの結果をコードレンズで出すようになりました。`verify` の側は、証明と境界の外の調べ直しで小さくなりました。
2. **解釈の誤りが全エンジンを素通りする**：z3も同じ遷移系を読むので、組み立ての誤りに対する独立性は増えていません。コーパスは91件に増え、参照インタプリタが部分集合でビルダーを確かめるようになりました。プロジェクト自身がこれを残存リスクの1つ目に挙げています。大きなモデルの解釈は、今もサンプルのヘッダと人のレビューに頼ります。
3. **早い凍結と広い契約**：リリースの範囲では契約が守られましたが、v1.0.0から約1か月で2回のメジャーが出ました。構文の非推奨サイクルはまだ一度も使われていません。mainでは、既定の `verify` が境界の外の反例で失敗するようになりました。契約の「意味」の項と、証明の出力を対象外とする項の関係は、文面で整理されていません。
4. **TLCを手で回す経路の見落とし**：`StateModel_<E>` specのデッドロックのpassは、今も証明になりません（T6）。`verify` がTLCを必要としないので、この経路を使う利用者は少ないと考えます。
5. **規模の天井が要件を削る**：insurance-claim-opsの支払期限を理由に結び付ける規則は、今もモデルにありません（`samples/insurance-claim-ops/README.md`）。インスタンス対称性（`--symmetry always`）は実験的で、既定は `never` です。一方、insurance-claim-opsの22の規則は、`.lemma()` なしで証明されるようになりました（`CHANGELOG.md` の `Unreleased`）。行数の上限のない証明が、有界の探索の天井を一部補い始めたと考えます。
6. **ネイティブ検査器の `ok` に神託がない範囲**：`VERIFY_FALLBACK` は25個になりました。v3.0.0のゲートで免除した項目3と7は、mainで書き直しが提案され、持ち主の判断を待っています。フェーズ4と5は開いたままです。平の実行の活性の `ok` には、実行時の証人の検査が入りました。安全性の `ok` には、今もありません。
7. **生成コードと検証の間の隙間**：19個のUCに関数が出るようになり、適合ハーネスは拒否と自己検査まで見るようになりました。`codegen` の門は今も `check` の高さで、`verify` の結果を見ません。適合ハーネスは1エンティティ1行で動き、TypeScriptを辺の上で動かす差分テストもありません。
8. **既定の証明への過信**：証明が覆うのは状態の規則だけです。z3がなければ `note:` を1行出して飛ばされ、終了コードは変わりません。証明の出力は今も実験的です。誤った `proved` は、メモリの上限で止まったconeを誤った `ok` にし得ます。mainで誤った `proved` の不具合が少なくとも3件直されたことは、この経路にまだ誤りが残り得ることを示すと考えます。
9. **必須でないCI**：どのCIの検査も必須ではなく、ブランチ保護もありません（`docs/theory/README.md` の「Process」）。TLCとの照合、ランダム差分、ミュータント実行はCIか手作業に頼るので、その実効性はマージの慣習に依存します。

### 評価を変える条件

v3.0.0の評価で挙げた条件と、その状態です。

| 条件 | mainでの状態 |
|---|---|
| `Unique_*` が1インスタンスで「この境界では検査していない」と知らせる | 満たしていない |
| 構文の形を1つ、minorで非推奨にしてメジャーで削除する | 満たしていない（非推奨の形はない） |
| 免除したゲートの項目3と7を満たした状態でminorを出す | 満たしていない（書き直しの提案が判断待ち） |
| `codegen` が `verify` の結果を門に使うか、ヘッダに記録する | 満たしていない（文書で `verify` を勧めるようになった） |
| insurance-claim-opsの支払期限の規則を判定するか、対称性を既定にする | 満たしていない |
| 組み立てを独立した参照実装か仕様ベースのテストで押さえる | 一部満たした（部分集合の参照インタプリタ、91件のコーパス） |

表の満たしていない条件は、そのまま残します。mainの変更を受けて、条件を次のように足します。

- 境界の外の反例で終了コードが変わることを、契約の文面がどう扱うかを明記すれば、リスク3の新しい部分は解消します
- ゲートの書き直しが決まり、書き直した項目を満たしてリリースすれば、リスク6は小さくなります。フェーズ4と5が入れば、さらに小さくなります
- 参照インタプリタの部分集合が言語全体に広がれば（証明書の計画の段階8）、リスク2の評価を改めます
- 既定の `verify` が、z3がないことを `note:` より強く伝えるか、証明の出力を契約に入れれば、リスク8は小さくなります。証明書の計画の段階7aが入り、`proved` を実行中に確かめる経路ができれば、さらに小さくなります
- mainにブランチ保護が入り、TLCとの照合の検査が必須になれば、リスク9は解消します
