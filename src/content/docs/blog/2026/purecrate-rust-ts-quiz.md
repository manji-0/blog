description: 同じ見た目の純粋関数が、RustとTypeScriptでは違う値を返す。整数、浮動小数、文字列、コレクションから18問をクイズ形式で集め、すべて実際に動かした結果と、PureCrateがどう揃えているかをまとめる
---

[PureCrate](https://github.com/manji-0/purecrate-ts)は、純粋なRustのドメインロジックを素のTypeScriptへ翻訳し、両者が同じ値を返すことを確かめる変換器である。作っていて一番面白かったのは、「同じに見えて答えが違う」例を集める作業だった。[1本目](/blog/2026/purecrate-semantics-preservation/)では、その一部を表にまとめた。今回は一段掘り下げて、クイズにする。

ルールは次のとおりである。

- **Rust**: 各問のRustの式が返す値。
- **素朴なTS**: 同じ式を、見た目の近いJSの演算子と標準のメソッドに、そのまま置き換えた場合の値。
- **PureCrate**: 変換器が実際に出力したコードと、その扱い。

答えはすべて、手元で実際に動かして確かめた。環境はrustc 1.98.1（`-C overflow-checks=on`）、Node 24.20.0、PureCrate 0.23.0である。

## 整数編

### 第1問: `-7 / 2` は？

```rust
pub fn half(n: i32) -> i32 {
    n / 2
}
```

`half(-7)` の値を問う。

- **Rust**: `-3`。整数の除算は0の方向へ切り捨てる。
- **素朴なTS**: `-7 / 2` は `-3.5` になる。整数にしようと `Math.floor` を付けると `-4` になる。

`Math.floor` は負の無限大の方向へ丸めるので、負の数では1ずれる。正の数だけでテストしていると気づかない。正しくは `Math.trunc` である。

PureCrateは、整数の演算をすべて幅ごとの関数に置き換える。

```ts
export const half = (n: I32): I32 => Int.i32.div(n, 2 as I32);
```

`Int.i32.div` は0の方向へ切り捨て、0で割ればRustと同じメッセージでpanicする。

### 第2問: `1i32 << 32` は？

```rust
pub fn shift(n: u32) -> i32 {
    1i32 << n
}
```

- **Rust**: `shift(32)` はpanicする（`attempt to shift left with overflow`）。32ビットの値を32ビット以上ずらすことはできない。
- **素朴なTS**: `1 << 32` は `1` になる。JSはずらす量の下位5ビットしか見ないので、32は0と同じ扱いだ。

33ビットずらそうとすると、JSは黙って1ビットだけずらし、`2` を返す。PureCrateの出力は `Int.i32.shl(1 as I32, n)` で、`shift(32)` はRustと同じメッセージでpanicする。`shift(31)` は、どちらも `-2147483648` である。

### 第3問: `0xFFFF_FFFFu32 >> 1` は？

- **Rust**: `2147483647`。`u32` の右シフトは、上から0を詰める。
- **素朴なTS**: `0xFFFFFFFF >> 1` は `-1` になる。JSの `>>` は値を符号付き32ビットとして読むからだ。

`>>>` を使えば一致するが、`i32` では逆に `>>` が正しい。つまり、型によって使い分けるしかない。PureCrateは型を知っているので、`Int.u32.shr(x, 1)` と幅ごとの関数を出力する。

### 第4問: `9007199254740993` を足すと？

```rust
pub fn total(xs: &[u64]) -> u64 {
    xs.iter().sum()
}
```

`total(&[9007199254740993, 0])` の値を問う。

- **Rust**: `9007199254740993`。
- **素朴なTS**: `9007199254740992`。JSの `number` は2^53を超えると整数を正確に表せず、1つ隣の値に丸める。

この値はJSONの `JSON.parse` を通しただけでも丸まる。PureCrateは、64ビット以上の整数を `bigint` で表す。

```ts
export const total = (xs: ReadonlyArray<U64>): U64 => Iter.sum(xs, Int.u64.add, 0n as U64);
```

`total([9007199254740993n, 0n])` は、Rustと同じく `9007199254740993n` を返す。桁あふれもRustと同じく確かめる。

### 第5問: `i32::MAX + 1` は？

これは引っかけ問題である。

- **Rust（debugビルド）**: panicする。
- **Rust（releaseビルド、既定の設定）**: `-2147483648`。桁あふれは黙って折り返す。
- **素朴なTS**: `2147483648`。

Rustの中でさえ、ビルドの設定で答えが変わる。サーバーは普通 `--release` で動くので、本番の答えは `-2147483648` になる。

PureCrateが出力するTSは、桁あふれで必ずpanicする。そこで、releaseビルドでも桁あふれを確かめるよう設定されていないクレートは、変換の前に拒否する。

```text
crate/Cargo.toml: [profile.release] does not set overflow-checks = true
  generated TypeScript panics on overflow as a Rust debug build does; a --release server that wraps will disagree.
```

`Cargo.toml` の `[profile.release]` に `overflow-checks = true` を書けば、両方の答えが「panic」で揃う。

## 浮動小数編

### 第6問: `(-2.5).round()` は？

- **Rust**: `-3`。`round` は0から遠いほうへ丸める。`(-0.5).round()` は `-1` である。
- **素朴なTS**: `Math.round(-2.5)` は `-2` になる。`Math.round` は、ちょうど半分のとき正の無限大の方向へ丸めるからだ。`Math.round(-0.5)` に至っては `-0` になる。

正の数では `Math.round(2.5)` も `3` なので、ここでも負の数でしか差が出ない。PureCrateの出力は `Int.f64.round(x)` である。絶対値を丸めてから符号を戻すので、`-2.5` は `-3` になる。

### 第7問: `300.7 as u8` は？

```rust
pub fn to_byte(x: f64) -> u8 {
    x as u8
}
```

| 入力 | Rust | 素朴なTS（`Math.trunc`） |
|---|---|---|
| `300.7 as u8` | `255` | `300` |
| `f64::NAN as i32` | `0` | `NaN` |
| `-5.5 as u32` | `0` | `-5` |

Rustの `as` で浮動小数を整数にすると、値は型の範囲の端に寄せられる。NaNは0になる。JSには「`u8` に入れる」という操作そのものがないので、範囲の外の値がそのまま残る。

PureCrateの出力は `Int.u8.castFloat(x)` である。`toByte(300.7)` は `255` を返す。

### 第8問: `1e21.to_string()` は？

- **Rust**: `"1000000000000000000000"`。
- **素朴なTS**: `String(1e21)` は `"1e+21"` になる。`1e-7` も、Rustは `"0.0000001"`、JSは `"1e-7"` と書く。

浮動小数を文字列にする規則は、RustとJSで大きい数と小さい数の扱いが違う。正しく揃えるには、JSの側で数値の文字列化を作り直すことになる。PureCrateは、ここを揃えずに拒否している。

```text
`.to_string()` on `f64` is not in v0: `Display` of a float differs from JS past 1e21 and below 1e-7, as `format!` does
```

揃えられないものを黙って訳すより、拒否して書き方を変えてもらうほうがよい。PureCrateはそう考えている。

### 第9問: NaNを持つ構造体は、自分自身と等しいか？

```rust
#[derive(PartialEq)]
pub struct P {
    pub x: f64,
}
```

| 比較 | Rustの `==` | Nodeの `util.isDeepStrictEqual` |
|---|---|---|
| `P { x: NaN }` と `P { x: NaN }` | `false` | `true` |
| `P { x: 0.0 }` と `P { x: -0.0 }` | `true` | `false` |

ちょうど逆になる。Rustの `derive(PartialEq)` は、フィールドを `==` で比べる。浮動小数の `==` では、NaNは自分自身とも等しくない。`0.0` と `-0.0` は等しい。一方、Nodeの深い比較は `Object.is` に近い規則を使う。NaNどうしを等しいとし、`0` と `-0` を区別する。

PureCrateの出力は `Eq.deep(a, b)` である。数値を `===` で比べるので、Rustの `==` と同じ答えになる。

## 文字列編

### 第10問: `"😀".len()` は？

- **Rust**: `4`。`len` はUTF-8のバイト数を数える。
- **素朴なTS**: `"😀".length` は `2` になる。JSの `length` はUTF-16のコード単位を数える。

ちなみに文字数は、Rustの `"😀".chars().count()` もJSの `[..."😀"].length` も `1` である。「長さ」の答えが3通りある。PureCrateは `Str.len(s)` を出力し、UTF-8のバイト数を返す。

### 第11問: `trim` は何を削るか？

文字列の先頭に、見えない文字を1つ置いて `trim` する。

| 先頭の文字 | Rustの `trim` | JSの `trim` |
|---|---|---|
| U+0085（NEL、次の行） | 削る | 残す |
| U+FEFF（BOM） | 残す | 削る |

これも逆である。Rustは、Unicodeの空白（`White_Space`）を削る。U+0085はこれに含まれ、BOMは含まれない。JSの `trim` は、自分の仕様で決めた空白の一覧を使い、その中にBOMが入っている。

ファイルの先頭にBOMが付いたCSVを `trim` すると、RustではBOMが残る。PureCrateは、Rustと同じ空白の一覧で削る `Str.trim(s)` を出力する。

### 第12問: `"ab".split("")` は？

- **Rust**: `["", "a", "b", ""]`。
- **素朴なTS**: `["a", "b"]`。

空の文字列で区切ると、Rustは両端に空の要素を付ける。PureCrateは、空の文字列のリテラルで `split` することを拒否し、代わりの書き方を示す。

```text
`split("")` is not in v0: Rust gives an empty piece at each end (`"ab".split("")` is `["", "a", "b", ""]`); iterate `s.chars()`
```

一方、`"a,b,".split(',')` は、どちらも末尾の空の要素を残して `["a", "b", ""]` を返す。空でない区切りなら、そのまま `split` で揃う。

### 第13問: `"｡" < "😀"` は？

半角の句点 `｡`（U+FF61）と、絵文字 `😀`（U+1F600）を比べる。

- **Rust**: `true`。文字列はコードポイントの順に比べるので、U+FF61のほうが前である。
- **素朴なTS**: `false`。JSの `<` は、UTF-16のコード単位を比べる。`😀` は2つのコード単位 `0xD83D 0xDE00` で表されるので、`0xFF61` と `0xD83D` を比べて、`😀` のほうが前になる。

U+E000〜U+FFFFの文字（半角カナや私用領域の文字）と、絵文字などのBMP外の文字の順番が入れ替わる。JSの `<` で日本語のテキストを並べ替えると、半角カナが絵文字の後ろに回る。PureCrateは `Str.cmp(a, b) < 0` を出力する。最初に違うコード単位で、この入れ替わりを戻して比べる。

### 第14問: `format!("[{:5}]", "😀")` は？

- **Rust**: `"[😀    ]"`。幅5のうち、絵文字が1文字分、空白が4つである。
- **素朴なTS**: `"😀".padEnd(5)` は空白を3つしか足さない。`padEnd` はUTF-16のコード単位で幅を数えるので、絵文字を2文字分と見る。

PureCrateの出力は `` `[${Str.pad(s, 5, "<")}]` `` で、Rustと同じくコードポイントの数で幅を数える。

### 第15問: `"-0".parse::<u32>()` は？

文字列を整数に読む。

| 入力 | Rustの `parse::<u32>()` | JSの `Number` か `parseInt` |
|---|---|---|
| `"-0"` | `Err` | `Number("-0")` は `-0` |
| `"+5"` | `Ok(5)` | `Number("+5")` は `5` |
| `" 12"` | `Err` | `Number(" 12")` は `12` |
| `"10abc"` | `Err` | `parseInt("10abc")` は `10` |
| `""` | `Err` | `Number("")` は `0` |
| `"0x10"` | `Err` | `Number("0x10")` は `16` |
| `"1e3"` | `Err` | `Number("1e3")` は `1000` |

Rustの `parse` は厳しい。符号のない型に `-` を付けると、`-0` でも受け付けない。JSは前後の空白や16進数、指数表記を読み、空の文字列まで何かしらの数にしてしまう。

PureCrateの出力は `Int.u32.parse(s)` である。Rustと同じ文法を、ASCIIだけの正規表現で確かめる。範囲は `bigint` で確かめる。

## コレクション編

### 第16問: `[10, 9, 1]` を並べ替えると？

- **Rust**: `vec![10, 9, 1]` を `sort()` すると `[1, 9, 10]`。
- **素朴なTS**: `[10, 9, 1].sort()` は `[1, 10, 9]` になる。JSの `sort` は、比較関数を渡さないと要素を文字列として比べる。

有名な落とし穴だが、変換器では、比較関数を必ず型から決めればよい。PureCrateの出力は `Slice.sortBy(v2, Ord.cmp)` である。Rustの `sort` と同じく安定な並べ替えになる。

### 第17問: キー `"b"`、`"10"`、`"9"` の順番は？

キーを `"b"`、`"10"`、`"9"` の順で入れる。

- **Rust**: `BTreeMap<String, _>` の `keys()` は `["10", "9", "b"]`。文字列の辞書順である。
- **素朴なTS**: オブジェクト `{ b: 1, "10": 2, "9": 3 }` の `Object.keys` は `["9", "10", "b"]` になる。JSのオブジェクトは、整数に見えるキーを数の小さい順に先頭へ並べ、残りを入れた順に並べるからだ。

どちらの規則とも違う「入れた順」を返す `Map` もある。PureCrateは `BTreeMap` を `Map` で表し、読むときに `BTree.keys` でキーをRustと同じ順に並べ直す。JSONに書くときも、この順でキーを書く。

### 第18問: `Some(None)` は `None` と同じか？

- **Rust**: 違う。`Some(None).is_some()` は `true` である。
- **素朴なTS**: `Option<T>` を `T | null` で表すと、`Some(None)` と `None` がどちらも `null` になり、区別できない。

PureCrateは `Option<T>` を `T | null` で表す。TSで自然に書ける形で、`!== null` で確かめれば、0や空の文字列も `Some` として扱える。その代わり、入れ子の `Option` は拒否している。

```text
`Option<Option<_>>` is not in v0: both `None` and `Some(None)` would be `null` in TS
```

## おまけ: 実は同じだったもの

差を探していると、疑ってかかったのに同じだったものもある。

- `"ß".to_uppercase()` は、どちらも `"SS"` になる。1文字が2文字に増える。
- `"ΣΑΣ".to_lowercase()` は、どちらも `"σας"` になる。語の終わりのΣだけが `ς` になる規則まで一致する。
- `-7 % 2` は、どちらも `-1` である。JSの `%` も、0の方向へ切り捨てた商の余りを返す。
- `"a,b,".split(',')` は、どちらも末尾の空の要素を残す。
- `"Ab" < "a"` は、どちらも `true` である。大文字は小文字より前にある。

大文字・小文字の変換が揃うのは、どちらもUnicodeの同じ版（17.0）の表を使っているからだ。片方の版が上がれば、新しく割り当てられた文字で差が出うる。PureCrateの設計文書では、これも既知の差として書いている。

## 答え合わせ

| 問 | 式 | Rust | 素朴なTS | PureCrate |
|---|---|---|---|---|
| 1 | `-7 / 2` | `-3` | `-3.5`、`Math.floor` で `-4` | `Int.i32.div` |
| 2 | `1i32 << 32` | panic | `1` | `Int.i32.shl` |
| 3 | `0xFFFF_FFFFu32 >> 1` | `2147483647` | `-1` | `Int.u32.shr` |
| 4 | `9007199254740993 + 0` | そのまま | `…992` | `bigint` |
| 5 | `i32::MAX + 1` | 設定次第 | `2147483648` | `overflow-checks` を求める |
| 6 | `(-2.5).round()` | `-3` | `-2` | `Int.f64.round` |
| 7 | `300.7 as u8` | `255` | `300` | `Int.u8.castFloat` |
| 8 | `1e21.to_string()` | 22桁 | `"1e+21"` | 拒否 |
| 9 | NaNの構造体 `==` | `false` | `true` | `Eq.deep` |
| 10 | `"😀".len()` | `4` | `2` | `Str.len` |
| 11 | U+FEFFを `trim` | 残す | 削る | `Str.trim` |
| 12 | `"ab".split("")` | 両端に空 | 空なし | 拒否 |
| 13 | `"｡" < "😀"` | `true` | `false` | `Str.cmp` |
| 14 | `{:5}` で `"😀"` | 空白4 | 空白3 | `Str.pad` |
| 15 | `"-0".parse::<u32>()` | `Err` | `-0` | `Int.u32.parse` |
| 16 | `[10, 9, 1]` の `sort` | `[1, 9, 10]` | `[1, 10, 9]` | `Slice.sortBy` |
| 17 | キーの順番 | `10, 9, b` | `9, 10, b` | `BTree.keys` |
| 18 | `Some(None)` | `None` と違う | 同じ `null` | 拒否 |

18問のうち3問は、揃えられないので拒否している。第5問は、クレートの設定を変えるよう求める。残りの14問は、型に合わせた補助関数でRustの答えに揃える。どれも、例外や型エラーを出さずに違う値を返す差である。手で二重に実装していれば、テストで負の数や絵文字を試すまで気づかない。

PureCrateでもまだ揃えられない差（再帰の深さや、2^53以上の `usize` など）は、[1本目の「それでも残る差」](/blog/2026/purecrate-semantics-preservation/#それでも残る差)にまとめている。
