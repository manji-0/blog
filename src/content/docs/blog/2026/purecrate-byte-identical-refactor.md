[PureCrate](https://github.com/manji-0/purecrate-ts)は、純粋なRustのドメインロジックを素のTypeScriptへ翻訳し、両者が同じ値を返すことを確かめる変換器である。[1本目](/blog/2026/purecrate-semantics-preservation/)では意味を保つための制約を、[2本目](/blog/2026/purecrate-wire-serde-json/)ではJSONの境界を扱った。今回は変換器そのものの話で、リファクタの進め方を書く。

PureCrateは0.10から0.23までの約10日で、リリースごとに機能を継ぎ足して育った。継ぎ足すたびに、同じ規則を2〜3か所に書いた状態が増えていく。そこで2回、まとまったリファクタをした。

| 版 | 日付 | `crates/` 以下の差分 | 主な中身 |
|---|---|---|---|
| 0.10.4 | 2026-10-05 | 127ファイル、+6,407 / −7,312 | 木を辿る処理の共通化、大きなファイルの分割、テスト基盤 |
| 0.20.1 | 2026-10-15 | 85ファイル、+2,935 / −4,010 | 重複の除去、その途中で見つかったバグ5件の修正 |

どちらも、書き換えのコミットの合格条件は1つだけにした。**例とテスト用フィクスチャから生成したTypeScriptが、1バイトも変わらないこと**である。動作を変える修正は、書き換えとは別のコミットにした。

## なぜ「テストが通る」では足りないのか

PureCrateのテストは主に2種類ある。RustとTSの返す値を突き合わせる差分テストと、生成したTSを `tsc` と型情報つきの `oxlint` に通すテストである。どちらも「正しいか」は見るが、「前と同じか」は見ない。

変換器の出力には、正しさとは別の性質がたくさんある。行をどこで折り返すか、一時変数に何という名前を付けるか、括弧をどこに置くか、`import` をどの順で並べるか、である。これらが変わっても値は同じで、`tsc` も通る。しかし利用者から見れば、変換器の版を上げただけで生成物に差分が出る。リファクタの目的は書き方を変えることで、出力を変えることではない。それなら出力そのものを比べればよい。

## ゲートの作り方

使ったのは `scripts/output-snapshot.sh` という短いシェルスクリプトである。やることは次の3つだけだ。

1. すべての例と、すべてのテスト用フィクスチャを、スキーマなしとzod・valibot・arktypeの4通りで生成する。変換器が拒否する入力は、拒否のメッセージをファイルに書いて、それも生成物として扱う。
2. 各クレートについて `survey`（どの関数が書けて、どれが何の理由で拒否されるかの集計）をJSONで書き出す。
3. 書いたファイルすべてのSHA-256を、パスの順に並べた一覧（manifest）にする。

```bash
(cd "$out/gen" && find . -type f | LC_ALL=C sort | xargs shasum -a 256) >"$out/manifest.txt"
```

リファクタを始める前に1回、各コミットのあとにもう1回走らせ、2つのmanifestを `diff` で比べる。0.10.4の時点で1,639ファイル、0.20.1では2,754ファイルだった。いまの0.23.0では3,128ファイルになる。

要約値を1つだけ出すのではなく、ファイルごとの一覧にしたのには理由がある。差が出たとき、どのファイルが変わったかがすぐ分かるからだ。合否だけでなく、どこを見ればよいかまで教えてくれる。

0.10.4では、これに生成テストの入力も足した。PureCrateには、シードから関数をランダムに組み立ててRustとTSの値を比べる生成テストがある。そのシードで作ったクレートを固定の入力として書き出し（`PURECRATE_GEN_DUMP`）、その生成物の一覧もゲートに含めた。人が書いた例には出てこない形の式まで、出力の一致を確かめられる。

## ゲートが拾った誤り

0.10.4で、整形器（`tidy`）の行の折り返しを整理していたときのことだ。`if (..)` と `for (..)` の括弧の中身を読む処理が3か所に書かれていたので、1つの関数にまとめた。

```rust
// まとめた直後（誤り）
fn paren_head<'a>(line: &'a str, keyword: &str) -> Option<(&'a str, &'a str, &'a str)> {
    let pad_len = line.len() - line.trim_start().len();
    let rest = line[pad_len..].strip_prefix(keyword)?.strip_prefix(" (")?;
    let d = depths(rest);
    let close = (0..rest.len()).find(|&j| d[j] == Some(0) && rest.as_bytes()[j] == b')')?;
    Some((&line[..pad_len], &rest[..close], &rest[close + 1..]))
}
```

ゲートを走らせると、一覧に差が出た。

```text
GATE: examples/fixtures digest changed
< 2227758c…  ./crates_cli_tests_fixtures_chars_rs/none/src/classify.ts
> dddab75e…  ./crates_cli_tests_fixtures_chars_rs/none/src/classify.ts
< b50d009f…  ./crates_cli_tests_fixtures_for_each_rs/none/src/first-pair.ts
…
GATE: generated digest changed
< 7a2a1d8f…  ./expressions_13/src/s13f1.ts
…
```

原因は、括弧の深さを数え始める位置だった。元の3か所は、開き括弧 `(` を含めた位置から深さを数えていた。まとめた関数は `" ("` を取り除いた後ろから数えている。そのため、条件の中に括弧があると、対応する閉じ括弧を取り違える。すると括弧を読む処理が失敗し、別の折り返し規則に回る。結果として、例とフィクスチャ、生成テストの入力で、いくつかの行の折り返し方が変わった。

直し方は、開き括弧を残したまま深さを数えることだ。

```rust
    let rest = line[pad_len..].strip_prefix(keyword)?.strip_prefix(' ')?;
    if !rest.starts_with('(') {
        return None;
    }
    let d = depths(rest);
    let close = (1..rest.len()).find(|&j| d[j] == Some(0) && rest.as_bytes()[j] == b')')?;
    Some((&line[..pad_len], &rest[1..close], &rest[close + 1..]))
```

もう一度走らせると、一覧は元どおり一致した。

この誤りで値と型は変わらない。変わるのは改行の位置だけだ。値と型を見るテストにとっては、見つけにくい種類の誤りである。出力を直接比べていたから、コミットする前に気づけた。

## 0.10.4: 木を辿る処理を1つにする

0.10.4の中心は、式・型・パターンの木を辿る処理の共通化である。変換器の各段階は、それぞれ自分で再帰を書いていた。数えると約25本あった。中には、まったく同じものの写しもあった。

- 「クロージャの外へ抜ける `?` か `return` があるか」を調べる再帰が4つ。
- 「このループを抜ける `break` があるか」を調べる再帰が3つ。

これらを、IRの側に置いた共通の道具に置き換えた。`Expr::search` / `any` / `walk`、`Ty::children`、`Pattern::children` である。各段階は「何を探すか」だけを書けばよくなった。

あわせて、1,550行あった文の出力（`stmt.rs`）などの大きなファイルを、関心ごとに分けた。分割はファイルの移動だけで、中身は変えていない。20個の `if ... return` を並べていた行の折り返しも、試す順に並べた表へ直した。上の誤りは、この作業の途中で出たものである。

## 0.20.1: 重複をまとめたら、写しはすでに食い違っていた

0.20.1は、0.20.0のあとに「無駄な記述をなくし、同じことは一般的な概念にまとめる」ことを目的に始めた。進め方は次のとおりである。

1. クレートごとに、コードを読むだけのレビューを5本並行で走らせる。担当はAIエージェントで、まだ何も書き換えない。
2. レビューの結果をもとに、担当ごとに受け持つファイルが重ならないよう分ける。各担当は別々のgit worktreeで書き換える。IRのように複数の段階が使う部分は、1人の担当だけが触る。
3. まず、生成物を変えない書き換えだけを入れる。各担当は、ゲートの一覧が基準と一致することを確かめてからコミットする。
4. 動作が変わる修正は、そのあとに1件1コミットで入れる。各コミットには回帰テストと変更履歴を付ける。

結果として約1,000行が減った。一方で、読むだけのレビューの段階で、重複している箇所の3つが **すでに中身が食い違っていて、正しいRustを拒否している** ことが分かった。重複を残したまま機能を足していくうちに、片方の写しだけが更新されていたのである。

### 1. `str` のメソッドの戻り値の表が2つあった

`BTreeMap` の `insert` に渡す引数は、二度型付けされていた。2回目は、マップのキーと値の型を知らないまま、別の表を引いていた。その表は、`&str` のメソッドのうち4つの戻り値を `bool` としていた。

```rust
m.insert(String::from(s.trim()), 1); // expected `&str`, found `bool` で拒否された
```

いったん型を書いた `let` で受ければ通る、という回り道が必要だった。直したあとは、各引数を、マップが持つキーか値の型に対して一度だけ型付けする。

### 2. 型の別名を展開する検査が、3つのうち1つだけ片側しか展開していなかった

```rust
type Id = u32;
xs.iter().map(|x: &Id| *x + 1).collect::<Vec<u32>>()
```

これは「`map` のクロージャは `Id` を受け取るが、要素は `Id` である」という、自分自身と食い違うメッセージで拒否された。クロージャの引数の型を確かめる検査は3か所にあり、そのうち1か所だけが、書かれた側の別名しか展開していなかった。3つを1つの検査にまとめ、両側の別名を、`Vec` や `Option` の中まで展開するようにした。

### 3. タプル構造体の構築だけが、ジェネリックの経路を通っていなかった

```rust
pub struct Wrap<T>(pub T);
```

この型は受け付けられたが、出力したTSには、どこにも束縛されていない `T` が残っていた。

```ts
export type Wrap = T & { /* .. */ };
```

さらに `Wrap(x)` は `expected T, found u32` で拒否された。構造体リテラル `Wrap { 0: x }` はジェネリックな型を扱う経路を通るのに、タプル構造体の構築はフィールドの型を書かれたまま使っていたからである。構築を同じ経路に通すと、`export type Wrap<T> = T & { .. }` と出力し、`T` を `x` から推論するようになった。

### 読んでいて見つけた残りの2件

残りの2件は重複の食い違いではなく、コードを読む過程で見つかったものである。

- `#[serde(..)]` の属性で、後のキーが前のキーの拒否を消していた。キーを並べる順番によって、受け付けたり拒否したりが変わっていた。
- 非公開モジュールの中の `pub const` が、`index.ts` からエクスポートされていた。隣の `pub fn` は内部に留まるのに、定数だけがRustの公開範囲に従っていなかった。

5件とも、直したあとは、その形を使う最小の例を回帰テストとして足している。

### ゲートの例外は、一覧が教えてくれる

0.20.1では、生成物のうち `examples/` に同梱するランタイムのコピーだけが変わった。ランタイムの補助関数2つを1つにまとめたためである。例とフィクスチャのTSは、すべて1バイトも変わっていない。

一覧をファイルごとに比べているので、こうした意図した差も「どのファイルが、なぜ変わったか」として説明できる。差が出たときに、それを許すかどうかを1ファイル単位で判断できる。

## あえてまとめなかったもの

重複を探していると、似ているが同じではない処理がたくさん見つかる。それらはまとめなかった。

**`pure` と `is_inlinable`**。どちらも「評価しても何も起きない式か」を答える関数に見える。しかし聞いている段階が違う。

```rust
// emit_ts の join: 整数の演算は、この段階ではすでに呼び出しになっている
pub(super) fn pure(expr: &Expr) -> bool {
    let here = matches!(expr, Expr::Lit(_) | Expr::Var(_) | Expr::Field { .. } /* … */
        | Expr::Unary { .. } | Expr::Binary { .. });
    here && expr.children().into_iter().all(pure)
}

// ir: Binary は整数の演算を含み、オーバーフローで panic しうる
pub fn is_inlinable(&self) -> bool {
    match self.unpositioned() {
        Expr::Var(_) | Expr::Lit(_) | Expr::Closure { .. } => true,
        // …
        _ => false,
    }
}
```

`pure` が呼ばれる時点では、panicしうる整数の演算は関数呼び出しに置き換わっている。そのため、残った `Binary` は比較などの無害なものだけである。一方 `is_inlinable` の時点の `Binary` は、オーバーフローでpanicするかもしれない。同じ `Binary` という名前でも、段階によって意味が違う。1つにまとめれば、どちらかの段階で誤った答えを返す。

**`replace_var` と `subst`**。どちらも「式の中の変数を別の式に置き換える」関数である。`subst` は、内側で同じ名前が束縛し直されていれば、その先は置き換えない。`replace_var` はそれを気にしない。名前がすでに重複しないと分かっている場所でだけ使っている。

**拒否メッセージを組み立てる処理**。引数の数が合わないときのメッセージは、似た形のものが何か所かにある。まとめると、利用者に見えるメッセージの文面が変わる。文面もゲートの一覧に含まれる出力の一部なので、リファクタの範囲を超える。

**網羅的な `match` を受け皿の `_ =>` に置き換えること**。式の種類ごとに全部を書いた `match` を、`_ => children()` で辿る形にすれば短くなる。しかしそうすると、式の種類を新しく足したとき、扱いを決め忘れてもコンパイラが教えてくれない。短くなる代わりに、将来の誤りを見つける仕組みを1つ失う。

まとめるかどうかの判断基準は、「同じ問いに答えているか」である。見た目が似ていても、問いが違えばまとめない。問いが同じなら、写しが1つだけ更新されて食い違う前にまとめる。0.20.1の3件のバグは、後者を放っておいた結果だった。

## まとめ

- リファクタの合格条件を「生成物が1バイトも変わらない」に置くと、テストでは見えない種類の誤り（改行の位置や名前の付け方）も、コミットの前に拾える。
- 生成物の比較は、要約値1つではなくファイルごとの一覧にすると、差がどこに出たかまで分かる。意図した差も、ファイル単位で説明できる。
- 生成物を変えない書き換えを先に入れ、動作を変える修正はそのあとに1件ずつ入れる。こうすると、出力の差がすべて、どれか1つの修正に結び付く。
- 重複は、残しておくと写しの片方だけが更新されて食い違う。0.20.1では、その食い違いが3件のバグになっていた。
- ただし、似ているだけで違う問いに答えている処理は、まとめない。まとめるとどちらかが誤るか、コンパイラの網羅性の検査を失う。
