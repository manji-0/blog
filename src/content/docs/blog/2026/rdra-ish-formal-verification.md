## 要旨

本稿は、要件定義手法RDRAを簡略化したDSL「RDRA-ish」の形式検証機構（`docs/formal-verification.md`）を、論文の体裁で整理・解説する。RDRA-ishはモデルのライフサイクルを遷移システムとして導出し、幅優先探索（BFS）とTLA+/TLCの2つの探索系で検査する。本機構の特徴は次の3点にある。第一に、全体モデルではなく検査対象ごとの影響円錐（cone of influence）に分割してTLCを実行する。第二に、独立な副ライフサイクルを停滞同値（divergence-blind stuttering equivalence）で商集合に縮約し、状態空間を削減する。第三に、時相性質を公平性の仮定とともに円錐上で判定し、判定不能な場合のみ全体モデルへ退避する。あわせて、インスタンス数・整数範囲といった有界性に由来する限界と、既知の検証ギャップを整理する。

対象文書は次のとおり。

https://github.com/manji-0/rdra-ish-dsl/blob/main/docs/formal-verification.md

## 1. はじめに

要件定義の成果物が「実際に矛盾なく動く」ことを、実装前に機械的に確かめたい。RDRA-ishは、エンティティ・ユースケース・状態遷移・制約を記述するDSLであり、記述から状態遷移システムを導出する。対象文書は、この遷移システムを **TLA+** として出力し、模型検査器 **TLC** で検査する仕組みを定めている。

検査系は二本立てである。`rdra-ish states` と `check` は、エンティティ当たり1インスタンスでBFSを行い、TLCに依存しない即時のフィードバックを与える。一方 `verify` は既定で2インスタンスのTLCを走らせ、BFSが評価しない時相性質を追加で検査する。両者は同一の遷移システムを探索するため、同じ境界内では同じ違反を見つけることが設計上の不変条件とされている。

本稿の貢献は、この文書が述べる設計判断を、問題設定・手法・正当性の議論・限界の四点から再構成する点にある。第2章で枠組みを、第3章でRDRAからTLA+ への写像を述べ、第4〜7章で状態爆発への対処と検査項目を論じる。第8章で限界を、第9章で考察を述べる。

## 2. 検証の枠組み

### 2.1 コマンド体系

検証機構は次の4つのコマンドで構成される。

| コマンド | 役割 | TLC 依存 |
| --- | --- | --- |
| `export --kind tla` | 全体モデルの `RdraSpec.tla` と `.cfg`、およびデッドロックとウィットネスを調べる `StateModel_<E>` を出力する | なし（出力のみ） |
| `verify --backend tlc` | 検査対象ごとの円錐と時相性質ごとの仕様を出力し、`tlc` / `tlc2` を実行する | あり |
| `states` | 同一システムの BFS による状態探索 | なし |
| `check` | 同一システムの BFS による検査 | なし |

境界は2つのパラメータで与えられる。`--instance-count`（既定2、範囲1〜255）は各エンティティのインスタンス数 `InstanceCount` を、`--int-range-max`（既定5）は整数域 `IntRange == 0..N` を定める。`verify` の「OK」はこの境界内でのみ成立する主張であり、出力の `bounds:` 行と最終行 `OK: no errors within ...` がそれを明示する。

### 2.2 `.cfg` の方針

生成される `.cfg` は `SPECIFICATION Spec`、`INVARIANT TypeOK`、制約ごとの `INVARIANT`、`after` 表明および時相性質ごとの `PROPERTY`、そして `CHECK_DEADLOCK FALSE` を指定する。デッドロック検査をTLC側で切るのは、ライフサイクルモデルが終端状態（実行可能な動作を持たない状態）で終わるのが通常であり、`Spec` が停滞（stuttering）を許すためである。デッドロックの有無は、後述する状態モデルの検査が別途担う。

### 2.3 二つの探索系の関係

BFSとTLCは同一の遷移システムを異なる実装で探索する。文書は、`engine_equivalence` テストが全サンプルの全円錐について、到達状態・初期状態・辺集合（遷移元・遷移先・ユースケースの組）・状態モデルの所見・各不変条件と `after` 表明の判定を、1および2インスタンスで両系統が一致することを検証すると述べる。この二系統の差分検証が、本機構の信頼性の主要な根拠である。

## 3. RDRA から TLA+ への写像

写像の骨格は、「状態 = 変数の組」「ユースケース = 動作（action）」「制約 = 不変条件または性質」の3つに集約される。主な対応を次に示す。

| RDRA の要素 | TLA+ での表現 |
| --- | --- |
| エンティティ | id 集合 `<E>_Ids == 1..InstanceCount` と、存在状態 `<E>_exists`（`absent` / `present` / `deleted`） |
| 列（Enum・Bool・Int など） | `<E>_<col>`:id 上の関数。Int 系は `IntRange` を値域とする |
| `relate`（N:1・1:N・1:1） | `<Child>_owner_<Parent>`:子 id から親 id への関数 |
| ユースケース | トランザクション群ごとに 1 つの演算子 `<UC>(p0, ...)`。`Next` はそれらの選言 |
| 複数群に分かれるユースケース | 実行印 `<E>_run_<UC>` により `<UC>_1 .. <UC>_k` を順に実行 |
| `creates` / `deletes` | `FirstAbsent` による空きスロット確保、`deleted` への遷移。削除済みスロットは再利用しない |
| `transitions(UC, E.col, a -> b)` | 遷移元 `col = a` をガードとし `b` を書き込む。`UNCHANGED` で他変数を固定 |
| `applies_to` と `holds` 条件 | ユースケース演算子へのガード連言 |
| `forbidden` / `invariant` / `required` / `exclusive` | 存在するインスタンス上の量化として各 1 つの `INVARIANT` |
| `after(UC).assert(...)` | `PROPERTY AfterAssert_<UC>_<n>`:`[][(\A p : UC(p) => post')]_vars` |
| `property`（`always` / `eventually` / `leads_to`） | 名前付き式と `PROPERTY`。`eventually` / `leads_to` がある場合 `Spec` に `WF_vars(Next)` を含める |

### 3.1 設計上の要点

第一に、**原子性の単位はトランザクション群**である。1つのユースケースの書き込み対象を複数のトランザクション群に分けると、それは `<UC>_1 .. <UC>_k` という `k` 個の動作となり、他の動作が間に割り込める。文書のサンプル `cross_order_payment_split` では、`Pay` を2つのAPIに分けた結果、`Cancel` が `Pay_1` と `Pay_2` の間に割り込み、不変条件違反が検出される。これはモデルの欠陥を割り込みの問題として可視化する例である。

第二に、**イベント駆動の順序は「印（mark）」で表現される**。追跡対象イベント `Ev` に対し、`<E>_raised_<Ev>` という真偽値の関数を置き、初期値は `FALSE`、発火後は決して `FALSE` に戻らない。トリガされるユースケースの最初のステップは、この印が真であることをガードとして要求する。ただし印は掛け金（latch）であり、イベントの回数は数えない点に注意が必要である（第8章）。

第三に、**整数と時刻は有界の TLC 整数で近似される**。`now` は大域変数であり、`Tick` 動作が上限まで1ずつ加算する。`col < now` を含む制約は、時計が列値を追い越すことで違反が検出され得る（`now_coupon.rdra`）。

第四に、**型不変条件 `TypeOK` を業務ルールから分離する**。すべての変数の定義域は `TypeOK` のみが担い、業務上の制約は個別の不変条件として名前付き（`Forbidden_Order_0` など）で出力される。これにより、違反した制約名からモデル上のどの規則が破られたかが直接分かる。

## 4. 影響円錐による分割検証

### 4.1 動機

全体モデルを一度にTLCへ渡すと、状態数が急増する。文書によれば、`InstanceCount=2` の全体モデル実行はec-siteで62秒・11 GBを要し、clinic-opsでは300秒で完走しなかった。そこで `verify` は、各不変条件と `after` 表明を、それが読む変数の**影響円錐**に制限して検査する。

### 4.2 円錐の性質

円錐は「検査対象が読む変数を含み、それらを書く動作が読む変数もすべて含む、最小の閉じた変数集合」として定義される。この円錐は、全体モデルの状態を円錐へ射影したものと同じ状態集合に到達する。したがって次が成り立つ。

- すべての円錐が `ok` であれば、全体モデルも `ok` である。
- ある円錐での違反は、全体モデルでの違反である。

ただし例外がある。円錐内の動作が、円錐の読まないエンティティを生成する場合、その生成は円錐から落とされ、円錐はそのエンティティのスロットを数えない。このとき円錐は上位集合に到達するため、`bounds:` 行が「検査が読まないエンティティは非有界」と明示する。円錐での違反は、境界を超える数の未読インスタンスを伴う可能性がある。同じ変数集合を持つ円錐は1回の実行を共有する。

### 4.3 違反の報告

違反した不変条件や `after` 表明は、まずモデルの言葉で報告される。規則の `path:line:col`、ステップごとのユースケースと束縛インスタンス（例：`Place [Order#1, Payment#1]`）、そして各ステップで変化した値である。これはTLCの状態列を復号し、BFSが用いるステップ関係に再生して得られる。再生できないステップは「ツールのバグ」とみなされ、エンジン間の不一致として報告される。この再生による検算は、TLCの出力を信頼する範囲を明確にする設計である。

## 5. 時相性質の検証と公平性

### 5.1 問題の所在

`always`・`eventually`・`leads_to` といった時相性質は、BFSでは評価されない（`check` は検査しなかった旨の `note:` を出す）。`eventually` と `leads_to` が成立するには公平性の仮定が要り、`Spec` は `WF_vars(Next)`（`Next` 全体に対する弱公平性）を含む。ところが、この仮定は円錐へ素直には制限できない。円錐外の動作が永久に動き続ければ、円錐内のインスタンスが静止していても `WF_vars(Next)` は満たされるからである。逆に、円錐側で `WF_vars(Next)` を課すと、全体モデルが許す実行を排除してしまう。

### 5.2 三段階の判定

`verify` は、時相性質ごとに最大3回の実行で判定する。

1. **`Cone_<P>`**:円錐上で `Spec == Init /\ [][Next]_vars`（公平性なし）とし、性質 `Fair_P => (...)` を検査する。`ok` ならそれが全体モデルの判定である。
2. **`Cone_<P>_WF`**:1で反例が出た場合に、同じ円錐へ `WF_vars(Next)` を加えて再検査する。ここでの反例は全体モデルの反例である。`ok` が決定的になるのは、円錐がある動作の書くすべての変数を含む場合に限られる。
3. **`RdraSpec_<P>`**:円錐では決まらない性質のみ、全体モデルで実行する。`--temporal-budget` 秒（既定300）または2,097,152個の相異状態で打ち切られ、その場合は `not decided` となる。

`always` は1の実行のみで足りる。反例は有限の接頭辞で示されるため、`WF_vars(Next)` の有無によらず全体モデルへ持ち上げられるからである。

### 5.3 `.fair` による円錐の維持

性質に `.fair(UC, ...)` を付けると、列挙したユースケースの各動作・各インスタンスに対する弱公平性 `Fair_P` が、性質の式の中に組み込まれる（`P == Fair_P => (...)`）。この場合、円錐はそれらのユースケースを丸ごと保持し、判定が円錐上で完結する。文書の実測では、food-permit-opsの `HygieneManagerEventuallyAppointed` は243状態の円錐で判定され、`verify` 全体が18秒で終わる。一方 `.fair` なしでは、patent-opsなどの大規模サンプルで全体モデル実行が予算内に完走せず `not decided` となる。

`.fair` を使うときの注意として、`ok` は「指名したユースケースが飢餓状態に置かれない実行」に対してのみ成立する。そのため `verify` は `assumes weak fairness per instance on ...` と出力して仮定を明示する。

### 5.4 反例の表現

時相性質の反例はlasso（有限の接頭辞に続くループ）である。TLCが `Back to state K` を示す場合、`verify` はそれをモデルの言葉で再生し、最後のステップの後に `then loops back to step K`（ステップKから最後までを永遠に繰り返す）と表示する。停滞で終わる場合は `then nothing changes forever` となる。サンプル `temporal_unmet.rdra` では、Order#1が取消しと再開を永遠に繰り返すlassoが `leads_to` 違反として示される。性質の評価は、無限列上でインスタンスごとに定義される（`always x` は `[](present => x)`、`leads_to x y` は `(present /\ x) ~> y`）。

## 6. 独立副ライフサイクルによる縮約

### 6.1 着想

円錐の中には、検査対象が書き込まず一部しか読まない第二のライフサイクルを含むものがある。たとえばinsurance-claim-opsのClaimの円錐には事案の示談が、clinic-opsのChargeの円錐には予約と診察が含まれる。この副ライフサイクルの各状態は、対象側の各状態と交互配置されるため、円錐を厳密に保つ限り、その状態数は両者の直積より小さくならない。文書はこれに対し、副ライフサイクルを**商集合**に縮約してから探索する方法を採る。

### 6.2 分割と商

円錐の変数を、対象側Tと残りSに分ける。Tは対象が読む変数と、対象が保持する動作の書き込み、およびその閉包から成る。SはTから書かれず、`obs`（Tの動作や検査式が読むSの変数）を通してのみ読まれる、独立した遷移システムである。Sの到達状態は、`obs` に関する**分岐非依存の停滞同値**（divergence-blind stuttering equivalence）で割られる。これは、`obs` の値が一致し、かつ一方が別のクラスへ抜ける動作をもう一方も（有限個のSの動作の列で）同じクラスへ実現できる、という最粗の分割である。縮約後の円錐は、クラスごとに1つの代表状態を保ち、Sの動作をクラス間の移動表 `Succ_<A>` に置き換える。TLA+ では副ライフサイクルが変数 `S_class` と、観測変数ごとの `Rep_<var>` 表になる。

### 6.3 入力（inputs）への拡張

Sの動作が、単調にのみ増えるTの変数（入力）を読む場合にも、縮約を拡張する。変数が単調であるとは、円錐内の書き込みを値間の辺とみなしたとき閉路を成さないことである。この場合、Tの動作のうち入力を書くものは、クラス間の「上昇（rise）」として表に記録される。ハンドラの `Triggered` 行や関連エンティティへの量化を通じた読み取りは、行の鍵ごとの真偽値1つに**畳み込まれる**。表の大きさは `TLA_CELL_BUDGET`（200,000セル）で抑えられ、超える場合は縮約を用いず非縮約の円錐で検査する。実測では、2,428クラス（72,840セル）と4,368クラス（104,832セル）の表がTLCの1 GBヒープで動作した。一方、24,000クラスの乱数モデルは326,400セルでヒープ不足となった。

### 6.4 正当性の議論

文書は、非縮約の円錐Cと縮約円錐Rの状態間の関係 `(t, s) ~ (t, rep(class(s)))` が、Tと `obs` を保存する分岐非依存の停滞双模倣であると論じる。要点は次の4つである。

1. 関連づけられた状態はTと `obs` について一致する（クラスは `obs` による細分化から始まる）。
2. Tの動作が読むのはTと `obs` だけであり、書くのはTだけである。そのため、CとRの双方で有効であり、関連する状態へ遷移する。
3. Sの動作は、同じクラスに留まる（Rでは停滞）か、別のクラスへ入る。後者は代表状態からのSの動作の列で実現され、その最後の動作がRのクラス間移動に対応する。
4. 初期状態は互いに対応し、Rに余計な初期状態はない。

停滞双模倣は「次状態（next）演算子を持たないCTL\*」を保存する。縮約円錐が報告する所見（状態に到達する、辺が取られる、到達済みの状態から動ける道がある）はこの形の式であるため、縮約円錐での判定が非縮約円錐のそれと一致する。

### 6.5 限界:`WF_vars(Next)` の非保存

双模倣が保存しないのは `WF_vars(Next)` である。クラス内で永久にループする状態は、Cでは `WF_vars(Next)` 下で停滞しないが、Rでは静止してしまう。そのため `_WF` 実行は非縮約の円錐上に残り、縮約円錐の `Cone_<P>` が反例を出した場合は、非縮約円錐で `Cone_<P>_Full` として再確認される。

縮約円錐上の反例は、印字の前に非縮約円錐の経路へ**持ち上げ（lift）**られる。Tの動作はそのまま、クラス間移動はそれを実現するSの動作列に展開される。違反は持ち上げた最後の状態で再評価されるため、メッセージは実在の状態から作られる。持ち上げた反例は縮約円錐のものより長くなり得る。

## 7. 状態モデルの検査:ウィットネスとデッドロック

### 7.1 検査項目

`verify` はTLCの前に、各エンティティの円錐をBFSで探索する（1円錐あたり上限8,388,608状態、`Caps::VERIFY`）。ここで状態モデルの各状態について次を調べる。

- **ウィットネス（witness）**:状態モデルの各状態に到達する実行が存在するか。なければ `NoWitness` エラーとなる。
- **デッドロック**:ある状態にあるインスタンスについて、そこから抜け出す経路が存在するか。抜け口があるのに、どの経路でもインスタンスが動かせない状態は誤りとして報告される。空きスロットの不足という境界のみが原因の場合は警告に留まる。
- **決して実行されないユースケース**:警告として報告される。

TLC自身のデッドロック検査を切る理由は第2章のとおりで、有界モデルはどれも動作不能で終わり、常に有効なループは行き詰まったインスタンスを隠すからである。

### 7.2 TLC 単体での検査

`export --kind tla` は、各円錐を `StateModel_<E>.tla` として出力する。`Witness_<E>_<col>_<s>` 不変条件は「どのインスタンスも `s` にいない」を述べ、健全なモデルでは到達によって違反されるためTLCは非ゼロで終了する。違反が報告されない `Witness_` は、ウィットネスのない状態を指す。`Deadlock_<E>_<col>_<s>` 不変条件は、`s` にいるインスタンスがあるとき、その列の円錐を変える動作がまだ有効である、ことを `ENABLED (Next /\ c' # c)` で述べる。

### 7.3 TLC と BFS の判定が食い違う場合

文書は、TLC単体の判定がBFSと異なる2つの場合を明示している。

第一に、**円錐内に閉路があるとデッドロックが隠れる**。たとえばShipが `review == ok` のときのみOrderを `paid` から `shipped` に動かし、FlipとFlopが `review` を `a` と `b` の間で永久に往復させるとき、支払済みのOrderは動けない。BFSは「どの経路でもインスタンスが `s` を離れない」ことを検出して `Deadlock_Order_status_paid` を報告する。しかしTLCでは円錐内の動作が常に有効なので、不変条件は破られず、何も報告されない。これは `engine_equivalence` が固定するケースである。インスタンスの経路の有無を問うBFSの検査は、TLCの不変条件では表現できない。

第二に、**境界のみが抜け口を塞ぐ場合の扱い**が異なる。BFSは警告とするが、TLCは不変条件違反としてエラー扱いにする。

このため `verify` は、これらの仕様をTLCには実行させず、BFSの所見で判定する。TLC単体の検査は、BFSを持たない環境での補助的な手段という位置づけである。

## 8. 近似と限界、既知の検証ギャップ

形式検証の結果は、探索しなかった範囲について何も語らない。文書はこの点を「既知の検証ギャップ」として列挙し、各項目に「どう見えるか」「どう対処するか」を併記している。ここでは主要なものを分類して示す。

| 区分 | 内容 | 見え方 | 対処 |
| --- | --- | --- | --- |
| 有界性 | `InstanceCount` と `IntRange` の範囲内でのみ OK。`check` は既定 1 インスタンスのため、2 インスタンスを要する `Unique_*` は空虚に成立する | `bounds:` 行 | `verify` を使うか `--instance-count` を増やす |
| 整数と時刻 | Int・Money・Decimal・Date・DateTime は 0..5、`now` は有界の時計 | `IntLiteralOutOfBounds` | `--int-range-max` で拡張 |
| イベント順序 | 印は掛け金で回数を数えない。ハンドラは 2 回目の発火を待たず、発火元はハンドラを待たない | `triggers` 行の info、反例の `note:` | 発火元が立て、ハンドラが解消する遷移元状態を `transitions` で設ける |
| BFS の打ち切り | 1 円錐 8,388,608 状態。超えると所見は決定されない | `not checked:` と `warning:` | `--deny-undecided`、または円錐を縮小 |

### 8.1 公平性の粒度

`WF_vars(Next)` は `Next` 全体への弱公平性であり、動作ごとではない。別のインスタンスの無限ループがこれを満たすため、あるインスタンスに関する性質が「他のインスタンスだけが動く実行」で破られ得る（`temporal_fair.rdra`）。`.fair` はこれを補うが、強公平性は存在しない。つまり、有効と無効を永遠に繰り返す動作は、実行を強制されない。

### 8.2 サンプルによる実証と規模

文書は、サンプルごとに `check` とTLCの期待結果を `// expect` 行で宣言し、`scripts/verify-samples.sh` がそれに合致するか検査する方式を採る。31のルートの63回の実行で、約220秒を要する。BFSとTLCは、同じ境界内の全サンプルで同じ判定を返す。さらに、`scripts/reduction-diff.py` が、乱数生成モデルで縮約あり・なしの `verify` を比較する差分試験として、縮約の導入による誤りの検出を担う。

縮約の効果は大きい。clinic-opsの全 `verify` は2.5分・3.7 GBから約17秒・0.5 GBになった。Chargeの円錐は、非縮約では8,388,608状態を超えるが、縮約後は38,533状態になる。Prescriptionは4,266,635状態から1,690状態に減る。一方で、EligibilityCheckの円錐（905,528状態）のように、まったく縮約できない例は残る。

## 9. 考察とまとめ

### 9.1 設計の評価

本機構の設計は、「検査の対象を絞り、絞った範囲での判定を全体の判定と等価に保つ」という一貫した原則に立つ。円錐による分割は、閉じた変数集合上で全体モデルと同じ判定を与える。縮約は、停滞双模倣という標準的な意味論的道具で、保存される性質の範囲を明示しつつ状態数を削る。公平性だけは双模倣が保存しないため、縮約の対象から外して非縮約の円錐に残す。こうして、効率化の導入ごとに「何が保存されるか」が議論され、保存されない部分は別系統の実行で補われている。

第二の特徴は、**二つの独立な実装による相互検証**である。BFSとTLCが同じ遷移システムを別々に探索し、状態・辺・所見・判定を突き合わせる。縮約についても、縮約あり・なしの比較と乱数モデルによる差分試験が置かれている。単一の実装の正しさを信じる代わりに、実装間の一致を証拠とする構成である。

第三に、**未検査の範囲の明示**が徹底されている。`bounds:` 行、`not checked:`、`not decided` といった出力が、「OK」の意味を境界内に限定する。検査が決定できなかった場合に、通過ではなく未決定として報告する姿勢は、形式検証ツールの利用者にとって重要である。

### 9.2 留意点

留意すべき点は3つある。第一に、有界の検証は無限のインスタンスに対する正しさを保証しない。2インスタンスで見つからない違反が3インスタンスで現れ得る。第二に、イベントの印が掛け金であるため、「イベントごとに1回」といった意味論をモデル化するには、利用者が遷移元状態の設計で補う必要がある。第三に、大規模サンプルの一部円錐は2インスタンスでの二系統の突合が行えず、1インスタンスの突合に留まる。これらの `verify` 判定はTLC単独のものとして扱うのが妥当である。

### 9.3 まとめ

RDRA-ishの形式検証機構は、要件モデルの遷移システムをTLA+ に写像し、影響円錐による分割、独立副ライフサイクルの縮約、時相性質の三段階判定によって、実用的な規模のモデルを現実的な時間とメモリで検査する。その結果は有界であり、保存される性質と保存されない性質が文書上で区別されている。モデラーは、`check` による即時の確認から `verify` による網羅的な検査へと段階を進め、出力に現れる境界と未検査の項目を読み解くことで、結果の意味を正しく解釈できる。
