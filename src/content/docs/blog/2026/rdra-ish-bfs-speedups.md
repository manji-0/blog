## 要旨

本稿は、要件定義DSL「RDRA-ish」の検証器が内蔵する明示状態の幅優先探索（BFS）について、2026年11月にrdra-ish-dslへ入った一連の高速化を整理する。出発点として、状態をヒープ上のバイト列で持ち、標準のハッシュ集合で重複を判定する「安直なBFS」を置く。改善は、CPU命令の削減・データ型の縮小・メモリ配置の改善・並列化の4つの観点に分類する。各改善の効果は、リポジトリのCHANGELOG・コミットメッセージ・設計文書が報告する計測値で示す。

主な結果は次のとおりである。food-permit-opsの最大の円錐（約460万状態、3,900万辺）の探索は、4コアで100秒から20秒になった。最大円錐の1状態当たりの保持バイト数は288.7から62.3へ、およそ4.6分の1に減った。一方で、メモリを削る変更は、いずれも退役命令数を数%から24%増やしている。本稿はこの交換が妥当である理由を、本ツールでは「メモリ上限内に収まるかどうか」が判定可否そのものを決める点から論じる。また、改善前と最新の版を同じマシンで実測した。その結果、最新の版は同じ探索を2〜3倍速く、約4.6分の1のメモリで行った（第9.1節）。

対象としたリポジトリは次のとおり。

https://github.com/manji-0/rdra-ish-dsl

## 1. はじめに

RDRA-ishは、エンティティ・ユースケース・状態遷移・制約で要件モデルを記述し、そこから遷移システムを導出して性質を検査する。検査系にはTLA+/TLCへの出力と、Rustで書かれた内蔵BFSの二系統がある（前稿「[RDRA-ishの形式検証(TLA+/TLC)を論文調で読み解く](/blog/2026/rdra-ish-formal-verification/)」を参照）。`check`・`states`・`verify` はいずれも、検査対象ごとの影響円錐（cone）に対してBFSを走らせる。

BFSの性能は、利用者の体験を2つの点で左右する。1つは待ち時間である。もう1つは判定できる範囲である。RDRA-ishは状態数の上限ではなく、`--memory`（既定4〜16 GiB）によるメモリ上限で探索を打ち切る。上限に達した円錐の所見は「未決定」として報告される。したがって、1状態当たりのバイト数を減らすことは、そのまま「決定できる円錐を増やす」ことを意味する。

本稿の構成は次のとおりである。第2章で基準となる安直なBFSを定式化し、そのコストを分解する。第3〜6章で、CPU命令・データ型・メモリ配置・並列化の各観点の改善を述べる。第7章で正しさの担保の方法を、第8章で命令数とメモリの交換について考察する。

## 2. 基準実装:安直なBFS

### 2.1 定義

本稿でいう「安直なBFS」は、教科書どおりの次の実装である。これは、改善前のコードの性質をコミットメッセージの記述から再構成したモデルであり、特定のコミットの写しではない。

```rust
// A naive explicit-state BFS: the baseline of this article.
fn bfs(ts: &System) -> Graph {
    let mut seen: HashMap<Box<[u8]>, u32> = HashMap::new(); // SipHash
    let mut states: Vec<Box<[u8]>> = Vec::new();            // one heap block per state
    let mut edges: Vec<(u32, u32, u32)> = Vec::new();       // (from, to, binding): 12 bytes
    let mut queue = VecDeque::new();
    for s in ts.initial_states() {
        let id = states.len() as u32;
        seen.insert(s.clone(), id);                         // a second copy as the key
        states.push(s);
        queue.push_back(id);
    }
    while let Some(from) = queue.pop_front() {
        let s = states[from as usize].clone();
        for action in &ts.actions {
            for binding in action.all_bindings(ts) {         // every combination of params
                if !action.guards.iter().all(|g| ts.eval(g, &s, &binding)) {
                    continue;                                // walks each guard's tree
                }
                let next = ts.step(action, &s, &binding);   // allocates a new state
                for check in &ts.checks { ts.eval_check(check, &s, &next); }
                let to = *seen.entry(next.clone()).or_insert_with(|| {
                    states.push(next);
                    queue.push_back(states.len() as u32 - 1);
                    states.len() as u32 - 1
                });
                edges.push((from, to, binding.id()));
            }
        }
    }
    Graph { states, edges }
}
```

状態は、遷移システムの各変数スロットに1バイトを割り当てたバイト列である。円錐の状態幅は30〜60バイト程度になる。

### 2.2 コストの所在

コミット `d63852e` は、改善前の実装を計測し、次のように報告している。food-permit-opsの1円錐は460万状態・3,900万辺であり、1スレッドで100秒を要した。その間、他のコアは遊んでいた。プロファイルでは、命令の約3分の1が `malloc` と `free` にあり、約5分の1が `Pred::reads_next` にあった。`Pred::reads_next` は、全状態の全束縛について、各ガードの構文木をヒープ上のスタックで走査していた。

安直なBFSのコストは、次の5つに分解できる。

| 記号 | コスト | 安直なBFSでの発生源 |
| --- | --- | --- |
| C1 | 辺当たりの動的確保 | 後続状態の `Box<[u8]>`、束縛、走査用スタック |
| C2 | ガード評価 | すべての束縛の組み合わせについて構文木を評価 |
| C3 | ハッシュと比較 | SipHashで30〜60バイトを処理。新状態は複数回ハッシュされる |
| C4 | 状態の保持 | 状態ごとのヒープブロックと、集合のキーとしての複製 |
| C5 | 逐次性 | 1スレッドのみで探索 |

C1〜C3は命令数の問題であり、C4はメモリの問題であり、C5は並列性の問題である。以下の各章はこの分類に対応する。

### 2.3 計測の方法

以降の数値は、断りがない限り、リポジトリのCHANGELOG・コミットメッセージ・設計文書 `docs/design/native-bfs-parallel.md` が報告するものである。命令数は `RDRA_JOBS=1`（1スレッド）での `verify` の退役命令数である。設計文書の計測は、18コア・128 GBのApple M5 Maxで、各点3回の中央値をとっている。「1状態当たりのバイト数」は、ストアが `--memory` に対して計上するバイト数（後述）であり、常駐メモリ（RSS）とは別の量である。

## 3. CPU命令の削減

### 3.1 ハッシュ関数:SipHashからFxHash系へ

Rust標準の `HashMap` が使うSipHashは、攻撃者が選んだキーによるハッシュ衝突攻撃に耐えるよう設計されており、1バイト当たりのコストが高い。BFSのキーはモデル自身が生成する状態・パターン・束縛であり、攻撃者が選ぶものではない。そこで、FxHashと同じ乗算と回転の方式に置き換えた（`fasthash.rs`）。

```rust
// One round per 8-byte word: rotate, xor, multiply.
fn add(&mut self, word: u64) {
    self.0 = (self.0.rotate_left(5) ^ word).wrapping_mul(SEED);
}
// The multiply leaves the low bits weak, and the table indexes by them.
fn finish(&self) -> u64 {
    self.0.rotate_left(26)
}
```

入力は `as_chunks::<8>()` で8バイトのワードに分割し、1ワードを1回の乗算で処理する。設計上の要点は2つある。第一に、乗算は上位ビットに強く混ざり、下位ビットには弱く混ざる。hashbrownは下位ビットでバケットを選ぶため、`finish` で26ビット回転して上位の良いビットを下位に移している。第二に、FxHashの反復順序は標準のマップと異なる。そのため、出力に届くマップは反復しないという制約を型の注釈で明記している。

### 3.2 辺当たりの動的確保の除去

コストC1に対しては、辺の処理で一切ヒープ確保しない構造に改めた（`d63852e`）。

- 束縛の列挙は、選択をスタック上の配列に保持する。
- 選択肢のないステップは、後続状態を再利用するスクラッチ領域に構築する。
- 後続状態とその付随情報は、フラットなバッファ（`Moves`）に連続して書き込む。
- `reads_next` は、ヒープ上のスタックではなく再帰で木を走査する。

同じ方針は、縮約側の `Fold::holds` にも適用された（`0f7949d`）。この関数は呼び出しごとに3つの `Vec`（引数、自由変数、その基数）を確保していた。引数を16個までスタック上のバッファに置き、自由変数の束縛を基数表記で直接復号するように改めた。その結果、insurance-claim-opsの退役命令数は458.8 Gから364.5 Gへ21%減った。対称性の正準形の計算も、同じく確保なしの実装に置き換えられている（`c482470`）。

### 3.3 ガード評価:256ビットのバイト検査

コストC2は、すべての束縛候補に対して構文木の評価器 `eval` を呼ぶことに起因する。ユースケースのガードの多くは「引数 `p` が指す行の列 `col` が値 `a` である」といった、1つの行の1つの変数だけを読む連言である。そのような連言の真偽は、状態中の1バイトの関数になる。

そこで、系ごとに1度だけ、各ガードの連言のうち「1つの引数の行の1つの変数と、リテラルだけを読む」ものを抜き出す。そして、それを256ビットのビット集合 `RowTest` に変換する（`plan.rs`、#253）。

```rust
/// A conjunct that reads one var of one param's row: it holds on a slot exactly when the
/// byte the var holds there is in `values`.
pub(crate) struct RowTest {
    pub var: VarId,
    pub offset: usize,
    /// Bit `b` is set when the conjunct holds on a slot whose byte is `b`.
    pub values: [u64; 4],
}

impl RowTest {
    pub fn admits(&self, byte: u8) -> bool {
        self.values[usize::from(byte >> 6)] >> (byte & 63) & 1 == 1
    }
}
```

ビット集合は、`eval` 自身を0〜255のすべてのバイト値で実行して作る。したがって、表は評価器と構成上一致する。探索時は、引数の各候補スロットをこの検査でふるい落とし、残った候補についてのみ直積を作る。検査1回は、シフト2回と論理積1回で済む。量化子・計数・後続状態の参照・`now` を含む連言は、従来どおり `eval` が判定する。

この変更により、`verify` の退役命令数はfood-permit-ops・patent-ops・oidc-auth（1インスタンス）でそれぞれ29%・30%・25%減った。

### 3.4 読まれない計算をしない

次の変更は、計算の高速化ではなく、計算そのものの省略である。

- **呼び出し元が読む検査だけを評価する**（#251）。エンティティだけを対象とする円錐や、縮約のための実行は、不変条件と `after` 表明を評価しない。
- **すべての検査が反例を得たら停止する**（#213）。安全性だけを答える円錐は、各検査に反例が見つかった時点で探索を打ち切る。BFSが最初に見つける反例は最短なので、出力は変わらない。違反済みの検査は、文字列の集合 `HashSet<String>` ではなく、検査名ごとの1ビットで管理する。
- **ビューのパターンは、それを読む実行だけが集める**（#296項目1.4）。`verify` はビューを読まない。この変更で、patent-opsの命令数は12%減った。
- **同じ系に縮約される円錐は1度だけ探索する**（#296項目1.2）。エンティティ・安全性・性質の各パスが同じ系に縮約した円錐は、最初のパスがすべての検査つきで最後まで探索し、後のパスはその結果を読む。patent-opsの命令数は59.0 Gから36.9 Gへ37%減った。

### 3.5 パッキングの命令設計

第4章で述べる状態のビットパッキングは、命令数を増やす。その増分を抑えるため、パッキング自体に次の工夫がある（`packing.rs`、`d2fe301`）。

**ワード単位の詰め込み。** 状態が96セル以下であれば、64ビットのワードを1つレジスタに保持し、セルの値をシフトとORで詰める。ワードが満ちたときにだけメモリへ書く。セルの幅に依存する分岐はない。

```rust
for (&b, &v) in bits.iter().zip(cells) {
    let v = u64::from(v);
    over |= v >> b;          // nonzero iff some value does not fit its width
    acc |= v << held;
    held += u32::from(b);
    if held >= 64 {
        words[w] = acc;       // one store per word, not per cell
        w += 1;
        held -= 64;
        acc = (v >> 1) >> (u32::from(b) - held - 1);
    }
}
```

値が定義域の外にあるかどうかの検査も、セルごとの分岐ではなく `over |= v >> b` の累積で行い、最後に1回だけ判定する。

**XOR差分による部分更新。** 1回の遷移が変える変数は通常少数である。そこで後続状態は、遷移元の詰め込み済みバイト列を複製し、変化したセルだけを書き換えて作る。変化したセルは、遷移元と遷移先を8バイトずつXORし、非ゼロのバイトを `trailing_zeros` で拾って見つける。

```rust
let mut diff = word(a) ^ word(b);
while diff != 0 {
    let c = j * 8 + (diff.trailing_zeros() >> 3) as usize; // the first changed cell
    diff &= !(0xff << ((c & 7) * 8));                     // clear that byte
    // ... write cell c's bits into the packed copy
}
```

これはSWAR（SIMD within a register）の典型的な手法であり、8セルの比較を1回のXORで済ませる。加えて、新しい状態の詰め込みは3回から1回に減った。重複判定と格納が、同じ詰め込み済みのバイト列を共有するためである（`Seen::find_packed`、`States::push_packed`）。デッドロックの走査なども、状態全体を展開せず、詰め込まれたビット列から必要なセルだけを読む（`Packing::cell`）。

## 4. データ型の縮小

### 4.1 状態:1セル1バイトから定義域のビット数へ

状態の各セルは、定義域が `n` 個の値をとる変数のスロットである。3値のステータスなら2ビット、真偽値なら1ビットで足りる。そこで、セルを `ceil(log2(n))` ビットで隙間なく詰め、全体をバイト境界に切り上げて格納する（#296項目2.3）。

```rust
/// The bits a domain of `size` values needs: 0 for one value, 8 for 256 or more.
pub(crate) fn bits_for(size: usize) -> u8 {
    match size {
        0 | 1 => 0,
        s => (usize::BITS - (s - 1).leading_zeros()).min(8) as u8,
    }
}
```

定義域が1値の変数は0ビットになる。つまり、格納されない。計測対象の最大円錐では、状態の幅が30〜60バイトから6〜12バイトになった。重複判定のハッシュと比較も、詰め込み済みのバイト列に対して行う。そのため、C3のコストも幅に比例して下がる。

### 4.2 重複判定表:状態のキーから状態番号へ

安直なBFSの `HashMap<Box<[u8]>, u32>` は、状態をキーとして複製して持つ。改善後は、hashbrownの `HashTable<u32>` に状態番号だけを格納する。ハッシュと等価判定は、番号が指すストア上の行を参照して行う（`fee3f3f`）。

```rust
self.table
    .find(hash(packed), |&i| states.packed_row(i as usize) == packed)
```

hashbrownの1バケットは、ハッシュの上位7ビットを入れる制御バイト1バイトと、4バイトの番号からなる。つまり5バイトである。負荷率7/8で倍々に拡張されるので、表の大きさは要素数だけで決まる。

### 4.3 辺:始点を暗黙にし、束縛IDを可変幅にする

安直なBFSの辺は `(from, to, binding)` の12バイトである。改善後は、辺を次のように表す（#296項目2.1）。

- **始点を持たない。** 辺は遷移元の状態ごとにまとめて格納され、状態ごとに「最初の辺の位置」を記録する。ある辺の始点は、最初の辺の位置がその辺以前である最後の状態として求まる。
- **終点は4バイトで持つ。** これは従来と同じである。
- **束縛IDは1・2・4バイトのいずれか。** 実行中に現れた最大のIDが収まる最小の幅を使う。IDは初出順に振るので、幅が広がる時点はどの機械でも同じである。
- **親は辺の番号（4バイト）。** 以前は8バイトだった。
- **検査だけの実行は辺のリストを持たない。** すべての検査が失敗した時点で止まる安全性円錐は、反例の復元に親だけを読む。そのため、親に始点と束縛を持たせ、辺のリストは作らない。

束縛IDの幅の拡張は、次のように列挙型で表されている。

```rust
pub(crate) enum Ids {
    One(Buf<u8>),
    Two(Buf<u16>),
    Four(Buf<u32>),
}
```

| --- | ---: | ---: | ---: | ---: |
| patent-ops | 159.4 | 115.7 | 78.3 | 42.3 |
| food-permit-ops (`view BusinessPermit`) | 288.7 | 187.7 | 106.3 | 62.3 |

3段階を通じて、1状態当たりのバイト数は3.3〜4.6分の1になった。項目2.2（セグメント）は第5章で扱うが、表の連続性のためここに含めた。

## 5. メモリ配置の改善

### 5.1 1つのバッファに1度だけ保持する

安直なBFSは、各状態を2度保持していた。1度目は `states` 内のヒープブロックとして、2度目は `seen` のキーとしてである。さらに、ヒープブロックごとに確保器のヘッダと端数が付く。改善後は、すべての状態を1本の連続バッファに端から端まで並べ、重複判定表は番号だけを持つ（`fee3f3f`）。Rustの型では、`str` と `String` の関係にならい、借用形 `StateSlice` を導入して読み手に渡す。

この変更だけで、1,000状態以上の円錐の1状態当たりのストアは、`check` の境界で中央値215バイトから125バイトに、`verify` の境界で248バイトから159バイトに減った。

### 5.2 行が動かないセグメント・バッファ

倍々に伸びる `Vec` には2つの欠点がある。第一に、拡張のたびに全行を2倍の領域へ複製し、その間は新旧の両方が生きている。第二に、最大でほぼ同じ行数ぶんの未使用領域を抱える。

項目2.2の `Rows<T>` は、最初の行を倍々に大きくなるセグメント（4行・4行・8行・16行と続き、16,384行まで）に置く。その後は16,384行のセグメントを1つずつ追加する。行は一度押し込まれたら動かない。

```rust
/// The segment that holds row `i`, and the row's place in it.
pub(crate) fn locate(i: usize) -> (usize, usize) {
    if i < 4 {
        (0, i)
    } else if i < DOUBLED {
        let log = i.ilog2() as usize;
        (log - 1, i - (1 << log))
    } else {
        let past = i - DOUBLED;
        (HEAD + (past >> SHIFT), past & (SEG - 1))
    }
}
```

行の位置は `ilog2` とシフト、マスクで求まる。32,768行までは倍々の `Vec` と同じ領域を持ち、それを超えると未使用領域は高々1セグメント未満になる。計上バイト数は表の項目2.2の列のとおり大きく減った。ただし、RSSの変化は2%以内だった（insurance-claim-opsのみ6%減）。CHANGELOGが述べるとおり、倍々の `Vec` が確保して書かなかった領域は、計上されてはいたが常駐してはいなかったためである。それでもこの変更には2つの意義がある。第一に、`--memory` の停止点が後ろへ動き、決定できる円錐が増える。第二に、「行が動かない」という不変条件が、第6章の並列化設計の前提になる。

コミット `3ba1366` は、さらにアクセスの分岐を整理した。押し込みは常に最後のセグメントへ行い、読み出しは固定長のセグメントを先に判定する。

### 5.3 決定的なメモリ計上

RDRA-ishのメモリ上限は、OSから見たRSSではなく、ストアの長さと容量から計算した式で判定される。例えば、`fee3f3f` の時点の式は次のとおりである。

```text
store_bytes = (w + 12)·p2(n) + 5·buckets(n) + 12·p2(e)
  w: state width, n: states, e: edges, p2: next power of two
```

この方式により、停止する状態は「どの機械でも、何スレッドでも」同じになる。この決定性は、データ構造の選択に制約を課す。例えば、重複判定表の成長規則は要素数だけの関数でなければならない（`Seen::bytes_with`）。そうでないと、計上値がスレッドのタイミングに依存してしまう。項目2.1〜2.3はいずれも、この式を新しいレイアウトに合わせて更新している。その結果、メモリ上限で止まっていた実行は、より後ろで止まるか、最後まで完了するようになった。具体的には、`check --memory 4KiB` は38状態ではなく64状態で止まり、`verify samples/patent-ops` は `256MiB` で `OfficeAction` の円錐を完了する。

### 5.4 停止した円錐の領域を返す

同じ考え方は円錐の間にも及ぶ（`7fbc67e`、#284）。従来、メモリ上限で止まったエンティティ円錐は、その状態と辺を保持し続けた。そのため、後続の円錐に使える領域は残らなかった。ある計測では、1つの円錐が8,348万状態・7.9 GBを抱え、その後の17円錐はまったく領域を得られなかった。改善後の `verify` は、止まった円錐の所見を読み取った時点で状態と辺を解放する。その結果、clinic-ops（3インスタンス、`--memory 8GiB`）で未決定だった117件の所見のうち17件が決定できるようになった。代償として、実行時間は1,707秒から5,578秒に延びた。それまで領域を得られずに飛ばされていた円錐を、実際に探索するようになったためである。

## 6. 並列化

### 6.1 展開と確定の分離

BFSの1ステップは、「状態を展開して後続状態を得る」段階と、「後続状態を重複判定して番号を振り、辺を記録する」段階に分かれる。前者は展開する状態だけの関数であり、並列化できる。後者は、それまでに確定した状態集合に依存し、順序が出力を決める。

`d63852e` は、この境界で処理を分けた。読み手（reader）のスレッドが、未展開の状態を128状態のチャンクに区切って作業スレッドへ渡す。作業スレッドは、展開結果を `Moves` のフラットなバッファに書いて返す。読み手は、渡した順にチャンクを読み戻して確定する。各作業スレッドには最大4チャンクまで先行を許す。状態の後続は状態だけで決まるので、状態番号・辺・束縛・親・所見・停止点は、1スレッドの実行と完全に一致する。この性質は、1, 2, 4, 7スレッドで、上限ありとなしの場合について、テスト `a_run_is_the_same_on_any_number_of_threads` が確認している。

4コアでの計測結果を示す。

| 円錐 | 状態数 | 改善前 | 改善後 | 改善後（`RDRA_JOBS=1`） |
| --- | ---: | ---: | ---: | ---: |
| food-permit-ops BusinessPermit | 4,648,771 | 100 s | 20 s | — |
| clinic-ops 最大円錐 | 2,238,170 | 31 s | 7.5 s | 10.4 s |
| food-permit-ops Disposition | 138,246 | 2.2 s | 0.34 s | 0.71 s |

`RDRA_JOBS=1` の列からわかるとおり、この高速化の大半は並列化によるものではない。第3章の確保除去とハッシュ変更による、1スレッドの高速化から来ている。

### 6.2 スレッド予算

並列化の直後、CIの `engine_equivalence` が13分40秒から20分47秒に悪化した。このテストは4つの円錐を同時に探索する。各BFSがそれぞれ `jobs()` 本の作業スレッドを起動したため、4コアの上で16本の展開スレッドが競合していた。`5a7eee7` は、作業スレッドをプロセス全体で1つの予算（`jobs() - 1`）から借りる方式に改めた。予算を得られなかった実行は、自分のスレッドで展開し、次のチャンクで再度借りようとする。

### 6.3 アムダールの法則による上限

並列化の効果は、読み手が逐次に行う確定処理で頭打ちになる。設計文書の計測（`c51f2543`、food-permit-ops、1スレッド）によれば、読み手の `Bfs::take` が実行全体の36.0%を占める。その内訳は、重複判定9.7%、束縛IDの割り当て8.7%、表の再ハッシュ3.7%などである。さらに、BFSの外側（所見と隣接表の構築、起動と終了）が10.2%ある。したがって、上限は `1 / (0.360 + 0.102) = 2.16` 倍である。実測は1.94倍で、8スレッドのとき、7本の作業スレッドはそれぞれ81〜83%の時間を待機に費やしていた。

### 6.4 設計段階の次の一手

この上限を押し上げるため、設計文書は、読み手の仕事の大部分を作業スレッドへ移す案（#296項目3.1）を示している。現時点では「設計、未実装」である。要点は次のとおりである。

- 作業スレッドが、後続状態の詰め込み・ハッシュ・重複判定表への問い合わせまで行う。表は、読み手1本が書き、多数のスレッドが読む専用の実装とする。hashbrownは挿入中の読み取りを許さないためである。
- 表のバケットは1度しか書かれず、要素は削除されない。そのため、作業スレッドが得た「既出（Hit）」は最終的な答えである。「未出（Miss）」は手がかりにすぎず、読み手が問い合わせ直す。これにより、出力は1スレッドの実行と帰納的に一致する。
- 作業スレッドはさらに、同じチャンク内の重複（`SameAs`）を解消する。計測によれば、辺の13〜43%は同じチャンク内で生まれた状態への到達である。

推定では、読み手の占有率は36.0%から15.4%に下がり、food-permit-opsの8スレッドでの速度向上は3.5〜3.9倍になる。第5.2節で述べた「行が動かない」セグメントは、作業スレッドが読み手の追記と並行して格納済みの行を読むための前提である。

## 7. 正しさの担保

高速化は、検証器にとって最も危険な変更の1つである。速くなった代わりに判定が変わってしまっては意味がない。rdra-ish-dslは、次の4つの層で正しさを担保している。

1. **影の双子（shadow twin）。** 高速化した関数ごとに、置き換え前の関数を `reference.rs` として残す。`--features shadow` のビルドでは、すべての呼び出しで両者を実行し、結果が異なれば呼び出しを名指しして停止する。例えば、重複判定表は順序付きマップと、パッキングは展開済みの状態と、辺は12バイトの旧形式のリストと照合される。CIには、この構成でサンプルとエンジンコーパスを走らせるジョブがある。
2. **Kaniによる有界証明。** パッキングについては、0〜8ビットのすべてのセル幅での往復、64ビットのワード境界をまたぐセル、差分更新が全体の詰め込みと一致することを証明している。ストアの計上バイト数についても証明している。
3. **スレッド数に対する不変性のテスト。** 1スレッドとNスレッドで、状態・辺・停止点が一致することを確認する。
4. **出力の同一性。** すべてのサンプルとコーパスについて、ヘッダが指定するフラグで出力がバイト単位で変わらないことを確認する。変わる場合（停止点の移動など）は、CHANGELOGに明記する。

ここで重要なのは、性能の変更が満たすべき性質を「出力が同じであること」と定義している点である。メモリ上限での停止点だけは例外であり、その移動は決定的な計上式の変更として文書化される。

## 8. 考察:命令数とメモリの交換

第4〜5章の変更は、いずれも命令数を増やしている。

| 変更 | 1状態当たりの計上バイト数 | ピークRSS | 退役命令数（`RDRA_JOBS=1`） |
| --- | --- | --- | --- |
| 2.1 辺の縮小 | −24〜49% | −13〜23% | +2〜7% |
| 2.2 セグメント | −31〜43% | ±2%（1例で−6%） | +3〜8% |
| 2.3 ビットパック | −29〜51% | −6〜29% | +15〜24% |

辺は3つのバッファから読むことになり、行の位置はセグメントの計算を経て求まり、状態は読むたびに展開される。それぞれが命令を足す。特に項目2.3は、food-permit-opsの命令数を104.0 Gから127.0 Gへ増やした。CHANGELOGはこれを「オーナーが受け入れた交換」と明記している。

この交換が妥当である理由は、第1章で述べた本ツールの性質にある。命令数の増加は、待ち時間を定数倍延ばすにすぎない。一方、メモリ上限を超えた円錐は「未決定」となり、利用者は答えを得られない。つまり、1状態当たりのバイト数は、待ち時間よりも判定能力を左右する。さらに、命令数の増分は、第3章の削減と第6章の並列化で吸収できる。第3章の削減とは、ガードのバイト検査による−25〜30%や、縮約の改善による−33%などである。この意味で、第3章と第4〜5章の最適化は独立していない。両者は、命令を削って得た余裕をメモリの削減へ支払う関係にある。

もう1つの観察は、改善の多くが「より速いアルゴリズム」ではなく「より適切な表現」によるものだという点である。BFSそのものは最後まで教科書どおりの幅優先探索であり、変わったのは、状態・辺・表・バッファのビット単位の表現と、読まれない計算の省略である。

## 9. まとめ

本稿は、RDRA-ishの状態探索BFSを、安直な実装を基準として、4つの観点で改善した過程を整理した。

- **CPU命令:** SipHashをFxHash系の乗算ハッシュに置き換えた。辺当たりのヒープ確保を除去した。1行1変数のガードを256ビットの表引きに変換した。読まれない検査とビューの計算を省いた。パッキングはワード単位の処理とXOR差分で行う。
- **データ型:** 状態はセルごとに定義域のビット数で詰めた。重複判定表は4バイトの番号だけを持つ。辺は始点を暗黙にし、束縛IDを1〜4バイトの可変幅にした。
- **メモリ効率:** 状態を1本のバッファに1度だけ保持する。行が動かないセグメントを使う。計上は長さと容量だけで決まる決定的な式で行う。止まった円錐の領域は解放する。
- **並列化:** 展開を作業スレッドへ、確定を読み手へ分けた。出力は1スレッドの実行と一致する。現在の上限は読み手の逐次部分であり、それを崩す設計が進行中である。

これらを通じて、CHANGELOGが報告する最大円錐の1状態当たりの計上バイト数は3.3〜4.6分の1になった。各段階では、影の双子・Kani・スレッド不変性テスト・出力の同一性によって、判定が変わらないことを確認している。

### 9.1 実測:改善前と最新の比較

ここまでの数値は、それぞれ別のマシンと別の時期に計測されている。そのため、掛け合わせても合計の効果にはならない。そこで筆者は、改善前と最新の2つの版を同じマシンでビルドし、同じモデルで実行した。

- **改善前:** `fb9f793`（2026-11-22）。作業スレッド化（`d63852e`）の直前であり、SipHash・状態ごとのヒープブロック・辺ごとの動的確保が残る。第2章の安直なBFSに最も近い版である。
- **最新:** `cdfb376`（2026-11-25の `main`）。
- **環境:** Intel Xeon 2.10 GHz・4コア・メモリ15 GBのコンテナ。Rust 1.97のreleaseビルド。各点1回の計測である。
- **モデル:** `samples/food-permit-ops` に対する `check --instance-count 2` 。`check` の境界では円錐が縮約されないので、`BusinessPermit` の円錐は7,500万状態を超える。

| 計測 | 改善前 | 最新 | 比 |
| --- | ---: | ---: | ---: |
| `--entity Disposition`（完走）の実行時間、1スレッド | 112.6 s | 37.9 s | **3.0倍速** |
| 同、4スレッド | 97.5 s | 33.0 s | **3.0倍速** |
| 同、ピークRSS（4スレッド） | 2,315 MB | 870 MB | 2.7分の1 |
| `--entity BusinessPermit` を1,000万状態で打ち切り、1スレッド | 147.3 s | 65.5 s | **2.2倍速** |
| 同、4スレッド | 111.2 s | 56.0 s | **2.0倍速** |
| 同、ピークRSS（1スレッド） | 2,457 MB | 538 MB | **4.6分の1** |
| `--entity BusinessPermit` を打ち切りなしで実行 | 13.6 GBでOSに強制終了され、結果なし | 4 GiB内に7,496万状態を保持して停止し、未決定を報告 | — |

`Disposition` について、2つの版の判定の出力は一致した（違いは、案内文の1行だけである）。

端的にまとめると、改善前の版に対して最新の版は、同じ探索を**2〜3倍速く**、**約4.6分の1のメモリ**で行う。言い換えると、同じメモリに約4.6倍の状態を収められる。最大の円錐では、改善前はRSSで1状態当たり約250バイトを使い、15 GBのコンテナでは探索の途中で強制終了された。最新の版は、ストアの計上で1状態当たり57バイトを使う。既定の4 GiBの上限内に7,500万状態を収め、未決定であることを正しく報告して終了した。

速度の比が2〜3倍にとどまり、第6章で引用した「100秒から20秒」の5倍に届かない理由は2つある。第一に、本計測のマシンは4コアであり、第6章で述べた読み手の逐次部分が並列化の効果を頭打ちにする。第二に、第4〜5章のメモリ削減は命令数を増やしている。第8章で論じたとおり、最近の変更は、速度よりも1状態当たりのバイト数を優先している。
